# Agent Guide for Mercora

Mercora is a themeable reference storefront on Cloudflare — Next.js on Workers, D1, R2, Vectorize,
Workers AI, Clerk, and Stripe — built to render any catalogue. The outdoor-gear catalogue shipped
in this repository is sample data, not the product; the visual identity you'll see by default is
one of seven presets the storefront can render, chosen by an admin without touching component code.
Read this file end to end before changing anything.

## Prerequisites

- **Node.js `24.18.1`**, pinned in three files that must always agree: `.node-version`, `.nvmrc`,
  and `package.json`'s `engines` field (`>=24.18.1 <25`). A version manager that reads the plain
  version file — `mise`, `nvm`, `asdf` with the nodejs plugin — is enough; no extra config file
  (no `.mise.toml`) exists or is needed.
- **npm** — ships with Node, no separate install.
- **The Cloudflare CLI (`wrangler`)** — invoked through the local binary (`npx wrangler`, or the
  `npm run` scripts that call it); it needs no global install.
- **Three accounts**, only needed for the features that touch them:
  - **Cloudflare** — required to deploy; not required to run `npm run dev` and browse the
    storefront locally.
  - **Stripe**, in test mode — required for checkout; without it, browsing and cart still work,
    but the payment step fails.
  - **Clerk**, a development instance — required for sign-in and the admin dashboard; without it,
    the storefront still renders for anonymous visitors.

## Setup

1. Clone the repository and enter it:
   ```bash
   git clone <repo-url> && cd mercora
   ```
2. Install the pinned Node version (adjust to your version manager):
   ```bash
   mise install
   ```
3. Install dependencies:
   ```bash
   npm install
   ```
4. Create `.dev.vars` in the repo root — this file is never committed. At minimum it needs these
   five keys, with values from your Stripe and Clerk dashboards:
   - `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`
   - `CLERK_SECRET_KEY`
   - `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`
   - `STRIPE_SECRET_KEY`
   - `STRIPE_WEBHOOK_SECRET`
5. Start the dev server:
   ```bash
   npm run dev
   ```

`npm run dev` runs a `predev` hook automatically: it builds the theme CSS barrel and manifest, then
prepares the local D1 database, applying local migrations and the development seed. There is no
separate seed command for local development — do not add one or tell someone to run one.

## Gates

CI (`.github/workflows/ci.yml`) runs these commands, in this order, on every push and pull request
to `main`:

```bash
npm audit --omit=dev --audit-level=high
npm run check:migrations -- --base <base-sha>   # pull requests only
npm run build:themes:check
npm run scan:tokens
npm run lint
npm run typecheck
npm run cf-typecheck
npm test
npm run test:workers
npm run test:observability-worker
npm run build
```

Contributors run a subset of these before every commit — see `CONTRIBUTING.md` for the exact list
rather than a second copy of it here.

## Rules

- Migrations are **expand-only**: add a new, higher-numbered file under `migrations/`; never edit
  or remove one that's already applied. See `docs/database-migrations.md` for the full policy.
- `npm run deploy` never applies remote migrations. Only `npm run deploy:ci` does, and only
  Cloudflare Workers Builds runs `deploy:ci` — never run it from a developer machine.
- The production-migration gate variable, `MERCORA_ALLOW_PRODUCTION_MIGRATIONS`, belongs only in
  the Cloudflare dashboard's Build variables. It must never appear in `wrangler.jsonc`.
- No secret belongs in `wrangler.jsonc`. Only public, non-secret values (`NEXT_PUBLIC_*` and
  similar) belong in its `vars` block. Secrets go in `.dev.vars` locally or in Worker secrets
  (`wrangler secret put`) in production. See `docs/runtime-configuration.md` for the full
  public-variable contract.
- The storefront renders exclusively through the token classes documented in `docs/theming.md` —
  never a hardcoded palette. The admin dashboard is explicitly excluded from the token contract and
  keeps its own fixed palette by design; do not "fix" this.
- The Node version is pinned in three files (`.node-version`, `.nvmrc`, `package.json` `engines`).
  Changing it means changing all three together, never just one.

## Files you must not edit

- `lib/themes/manifest.generated.ts` and `themes/index.generated.css` — both regenerated by
  `npm run build:themes` from `themes/*.css`. Edit a theme file instead.
- Any file under `migrations/` that is already applied — extend the schema by adding a new,
  higher-numbered file, never by editing an existing one.
- `.planning/` — the project's planning tree; out of scope for code changes.
- `cloudflare-env.d.ts` — regenerated by `npm run cf-typegen`.

## Environment

`docs/runtime-configuration.md` is the single source of truth for every public (`NEXT_PUBLIC_*`)
and non-secret configuration value; read it rather than expecting a duplicate list here.

Secrets — names only, no values, no examples that look like values:
- `CLERK_SECRET_KEY` — Clerk's server SDK reads this automatically.
- `STRIPE_SECRET_KEY` — the Stripe server SDK.
- `STRIPE_WEBHOOK_SECRET` — verifies the Stripe webhook signature.
- `ADMIN_VECTORIZE_TOKEN` — bearer / `X-API-Key` token for admin and server-to-server calls.
- `RESEND_API_KEY` — only needed if `EMAIL_PROVIDER=resend`; otherwise email sends through the
  Cloudflare `EMAIL` binding.
- `EMAIL_UNSUBSCRIBE_SECRET_CURRENT` and `EMAIL_UNSUBSCRIBE_SECRET_PREVIOUS` — HMAC signing keys
  for unsubscribe links.
- `ORDER_STATUS_SECRET` — signs guest order-status links; must be at least 32 characters, or the
  deploy check aborts.
- `GIFT_CARD_CODE_HMAC_CURRENT_VERSION` and `GIFT_CARD_CODE_HMAC_KEYS_JSON` — gift-card
  bearer-code signing keys.

Worker bindings you need to create (Cloudflare dashboard or `wrangler` CLI), by binding name and
resource kind — no resource identifier is written here, so don't copy one out of this file:
- `DB` — D1 database.
- `MEDIA` and `NEXT_INC_CACHE_R2_BUCKET` — R2 buckets (the same bucket backs both bindings).
- `VECTORIZE` — Vectorize index.
- `AI` — Workers AI.
- `EMAIL` — Email Sending.
- `WEB_VITALS` — Analytics Engine dataset.
- `AI_RATE_LIMITER` and `PUBLIC_RATE_LIMITER` — rate limiting.
- The `commerce-observability-tail` Worker must exist and be deployed as a tail consumer before
  this Worker is deployed; see `docs/observability.md`.
