<objective>
Wire the signed-in checkout path end to end on the server: bind the shopper to a Stripe Customer,
create the PaymentIntent against it, create a Customer Session alongside it, and return its client
secret in the same response as the PaymentIntent's — per D-04, D-05, D-06 and D-06a.

Purpose: this is the phase's tracer. It proves the whole architecture (D1 binding → Stripe
Customer → Customer Session → wire response) on one real path before any other layer is built on
top of it. If Stripe rejects this shape, it is caught here after one commit, not after five.
Output: one modified route, two new telemetry events, an extended route test suite.
</objective>

<interface_contract>
The JSON body of a successful non-zero-cash `POST /api/payment-intent` gains exactly one optional
field. Plan 17-03 consumes it and nothing else:

`{ clientSecret: string; paymentIntentId: string; orderId: string; amount: WireMoney; quote: {...}; customerSessionClientSecret?: string }`

The field is present only when the shopper is signed in AND a Stripe customer binding was
obtained AND the Customer Session call succeeded. It is absent — not null, not empty string — in
every other case, including every guest checkout.
</interface_contract>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `/api/payment-intent` | Untrusted shopper input; the Clerk session is the only identity signal |
| server → Stripe API | Secret-key calls; the customer id sent here decides which Stripe Customer a card attaches to |
| server → browser (JSON response) | Carries two short-lived client secrets out to the page |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-17-06 | Spoofing | `ensureStripeCustomerForShopper` call site | critical | mitigate | The customer id argument is the server-derived Clerk `userId` from `await auth()` and never a value read out of the request body, matching the `getCustomer(userId)` line directly above it (D-04) |
| T-17-07 | Information Disclosure | `recordTelemetry` calls in the two new catches | high | mitigate | Neither catch passes the PaymentIntent client secret nor the Customer Session client secret; the field set is the closed telemetry vocabulary only, asserted by a test in Task 3 |
| T-17-08 | Information Disclosure | guest response payload | high | mitigate | The Customer Session call is gated on `userId && stripeCustomerId && paymentIntent`; a guest response has no `customerSessionClientSecret` key, asserted in Task 2 (D-07, 17-RESEARCH.md Pitfall 3) |
| T-17-09 | Denial of Service | checkout availability | high | mitigate | Both new Stripe calls are best-effort in their own try/catch; neither can turn a working checkout into a 503 (D-04) |
| T-17-10 | Tampering | PaymentIntent save semantics | medium | mitigate | The save-for-later parameter is left unset so the Customer Session drives it; setting both is a documented Stripe integration error (D-06a) |
| T-17-11 | Information Disclosure | card data reaching our servers | critical | accept | No card number, PAN or CVC crosses this boundary at all — the browser posts card data straight to Stripe from inside the Payment Element iframe; this route only ever handles Stripe identifiers |
| T-17-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is installed by this plan; all three Stripe packages are already installed and audited OK in 17-RESEARCH.md's Package Legitimacy Audit |
</threat_model>
