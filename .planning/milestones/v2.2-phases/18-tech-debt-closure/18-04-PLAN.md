<objective>
Close DEBT-03. Today a saved cart line whose gift note fails re-validation on load is deleted
without a word: `normalizeCartItemForStore` returns nothing on a parse failure and
`migrateCartState` drops it from the rebuilt array. The shopper opens their cart and an item
they added is simply gone.

This is not hypothetical. Broken-windows ledger entry #10 records the live trigger: gift notes
containing a link are rejected by `parseGiftCardCustomization` (a deliberate anti-phishing
rule added in Phase 12), and the same parser runs over persisted cart state on every load — so
a browser holding a pre-deploy cart with a link in the note silently loses that line.

Purpose: keep the line, mark it, and tell the shopper what to do, using the warning pattern the
cart already has. Output: a flagged-but-surviving cart line and a visible remediation prompt.
</objective>

<interface_contract>
Added to `CartItem` in `lib/types/cartitem.ts`, and therefore to `StableCartItem`:

```ts
giftCardNoteInvalid?: boolean;
```

Set to `true` only by `normalizeCartItemForStore`, only when `parseGiftCardCustomization`
rejected a customization that was actually present. Absent in every other case — never `false`.
Read by `components/cart/CartItemCard.tsx` and by `projectCartLineForCheckout`.

**Deliberate deviation from D-03's literal wording, to be recorded in the SUMMARY.** D-03 says
the flagged item keeps "the customization preserved as-is". It does not. `giftCardCustomization`
is typed `GiftCardCustomization` — a parsed, validated shape — and writing an unvalidated blob
into it would be a type lie and, worse, would hand every downstream reader a value that looks
trusted. On the invalid path the flagged item carries the flag and **no** `giftCardCustomization`
key. What D-03 actually wants is that the *line* survives and the shopper is told, and both hold.
The note text itself is not recoverable in the cart, which is exactly why the remediation copy
is remove-and-re-add.
</interface_contract>

**Step 1 — the type.** In `lib/types/cartitem.ts`, add the optional boolean from the interface
contract above to `CartItem`, with a one-sentence doc comment saying it marks a line whose
stored gift note failed re-validation on load and that its customization was therefore not
carried forward.

**Step 2 — split the catch.** In `lib/gift-cards/line-identity.ts`, `normalizeCartItemForStore`
currently wraps the price conversion and the customization parse in one `try` whose `catch`
returns nothing. Restructure so the two failures are handled separately:

  - the price conversion keeps today's behaviour — a failure returns nothing and the line is
    dropped;
  - the customization parse gets its own handling: on rejection, do not abandon the item.
    Continue building it with no customization, and set the new flag to `true`.

Compute the line-id facts from whatever customization actually survived, so a flagged line's id
is derived from the product and variant alone. Add the flag to the returned object only on the
invalid path, using the same conditional-spread style the file already uses for the
customization field — never emit the key with a false value.

**Step 3 — the checkout projection must refuse a flagged line.** This is the security-critical
half and it is easy to miss. `projectCartLineForCheckout` re-normalises the item and today
relies on a nothing-return to throw. After step 2 a flagged line normalises successfully, its
customization is gone, and the existing conditional spread would simply omit it — producing a
projection for a *bare* line. The server would then price a gift-card variant with no recipient
and the shopper would pay for a gift card nobody receives. Extend the guard so the thrown
"invalid line" error also fires when the normalised item carries the flag. Keep the existing
line-id format check and the existing error message.

**Step 4 — the store keeps the line.** In `lib/stores/cart-store.ts`, `migrateCartState`'s
reduce keeps its null guard as-is — steps 2 and 3 leave plenty of ways to normalise to nothing.
The change here is to make sure a flagged item is carried through the merge-and-collision tail
with its flag intact: when a flagged normalised item merges into an existing accumulated line,
the accumulated line must end up flagged too, and when it is pushed fresh the flag must be on
the pushed object alongside the possibly-suffixed line id. Read the existing tail carefully
before editing; the push already spreads the normalised item, so confirm rather than assume the
flag rides along, and fix the merge branch if it does not.

**Step 5 — tests.** Extend the two existing unit test files, following their current structure:

  - in `tests/unit/lib/gift-cards/line-identity.test.ts`: a case that a link-bearing note
    produces a flagged item with no customization and a stable id; a case that a bad price still
    produces nothing; a case that a valid customization produces no flag key at all; and a case
    that `projectCartLineForCheckout` throws for a flagged line. Name the link case explicitly
    after the ledger entry it closes so the trigger is findable from the test.
  - in `tests/unit/lib/stores/cart-store-lines.test.ts`: a case that migrating a persisted state
    holding one valid line and one link-bearing line returns both lines, with the flag on the
    second only; and a case that migrating is still deterministic across two runs for that input.

Do not change the existing cases in either file.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser localStorage → cart store | Fully attacker-controlled persisted state enters the app on every load |
| Cart store → `/api/payment-intent` | The checkout projection is the only path from cart state into a priced order |
| Cart item → rendered warning | Stored text reaches the DOM |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-18-15 | Tampering | `lib/gift-cards/line-identity.ts` | critical | mitigate | The change stops a parse failure from deleting the line, which previously also guaranteed the line never reached checkout. Task 1 step 3 restores that guarantee explicitly: `projectCartLineForCheckout` throws on the flag. Without it, a tampered or stale cart would submit a gift-card variant with no recipient and the shopper would be charged for a card nobody receives. Covered by a named test. |
| T-18-16 | Elevation of privilege | `lib/types/cartitem.ts` | high | mitigate | The unvalidated note is never written into the typed `giftCardCustomization` field, so no downstream reader can mistake it for a parsed, validated value. The interface contract makes the flagged shape carry no customization at all; the type system enforces it. |
| T-18-17 | Tampering | `lib/services/checkout-pricing.ts` | high | accept | The server remains the authority. A caller that bypasses the client projection entirely still meets the pricing service's own gift-card validation, which re-parses the customization and rejects an invalid one. This plan changes nothing there and adds no new trust in the client. |
| T-18-18 | Information disclosure | `components/cart/CartItemCard.tsx` | medium | mitigate | The warning is fixed copy. The rejected note text is deliberately not rendered — it is not carried forward onto the flagged item at all — so no attacker-supplied string reaches the DOM through this path. |
| T-18-19 | Denial of service | `lib/stores/cart-store.ts` | medium | mitigate | Keeping previously-dropped lines means a hostile persisted state can now retain more lines through migration. The existing bounds are unchanged and still apply: the quantity ceiling, the bounded identifier and image-URL lengths, and the collision-suffix loop over an array the store already caps. No unbounded growth is introduced. |
| T-18-20 | Spoofing | `lib/gift-cards/customization.ts` | medium | accept | The link-rejection rule that triggers this whole path exists to stop a buyer-authored phishing link riding out on the store's authenticated sending domain. This plan does not relax it by one character — the note is still rejected, the difference is only that the shopper is told. |
