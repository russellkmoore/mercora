<interface_contract>
New export from `scripts/lib/migration-safety.mjs`, following the module's existing
pure-function style (no filesystem access, no process access):

```js
export function findDuplicateNumbers(addedFiles, allFiles) { ... }
```

`addedFiles` — the migration paths this change adds. `allFiles` — every migration path present
in `migrations/` after the change, including the added ones. Returns an array of report objects,
one per added file that collides, each naming the added file, its extracted number, and the
other filenames sharing that number. An added file with no collision produces no entry. A
collision between two files that are both pre-existing produces no entry — that is the rule
that keeps the `0023` pair quiet (D-16).
</interface_contract>

  </read_first>
  <behavior>
    - An added file whose leading number is already used by a different existing file produces one report naming both.
    - Two added files sharing one number, with no pre-existing file at that number, produce reports too — a change that introduces its own collision is still a collision.
    - An added file with a number no other file uses produces nothing.
    - Two pre-existing files sharing a number, with nothing added at that number, produce nothing.
    - A filename that does not start with digits followed by an underscore is ignored rather than crashing.
    - The function touches no filesystem and reads no process state.
  </behavior>
  <action>
Add `findDuplicateNumbers` to `scripts/lib/migration-safety.mjs`, placed beside
`inspectMigration` and written in the same style — a small named function, a short doc comment
stating what it is for, no imports added to the module.

Extract each path's leading migration number with a single anchored expression over the
basename, so a path prefix like `migrations/` does not interfere. Treat a basename that does not
match as having no number and skip it entirely rather than throwing.

Build the report by, for each added file, finding every *other* file in `allFiles` that shares
its number. The comparison must be against the full set, not the added set — a new file
colliding with an already-applied file is the main case this exists for, and comparing only the
added files against each other would miss it completely.

Equally important, and the thing a naive implementation gets wrong: do **not** scan `allFiles`
for duplicates on its own. A blanket "no two files may share a number" rule would fail this
repository's gate immediately and permanently on the already-applied `0023` pair. The rule fires
only when at least one side of the collision is a file the change under review added (D-16).

Compare filenames, not paths, when deciding whether two entries are "different files", and
normalise so the same path appearing in both arguments is not reported as colliding with itself.

Then extend `tests/unit/scripts/migration-safety.test.ts` with a new `describe` block for the
new function, following the file's existing `it(...)` style, covering every bullet in this
task's behaviour list. Use a fixture pair for the collision case as D-14 requires. Include one
case built from this repository's real situation: the two `0023` filenames present in `allFiles`
with an unrelated new higher-numbered file added, asserting no report — that is the regression
guard that the gate stays green on `main`.
  </action>

    <fails_when>The function reports the pre-existing 0023 pair when nothing at that number was added, misses a new file colliding with an applied one, misses two added files colliding with each other, reports a file as colliding with itself, or throws on a filename without a leading number.</fails_when>
