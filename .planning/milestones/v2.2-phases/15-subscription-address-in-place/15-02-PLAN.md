  <name>Task 1: nextAddressSelection — the single selection rule</name>
  <files>components/subscriptions/acquisition-client.ts, tests/unit/components/subscriptions/acquisition-client.test.ts</files>
  <behavior>
    - `nextAddressSelection(list, preferredId)` returns `preferredId` when an entry in `list` has that id.
    - When `preferredId` is absent from `list`, it returns the id of the entry flagged default.
    - When `preferredId` is absent and no entry is flagged default, it returns the first entry's id.
    - With an empty list it returns the empty string, whatever `preferredId` is.
    - Called with `ADD_NEW_ADDRESS_VALUE` as `preferredId`, it never returns that value — it falls through to default-then-first.
    - `ADD_NEW_ADDRESS_VALUE` can never collide with a real saved address id, because `ID_PATTERN` requires an alphanumeric first character.
  </behavior>
  <action>
Add to `components/subscriptions/acquisition-client.ts`, next to the other pure exports (no new imports needed):

- `export const ADD_NEW_ADDRESS_VALUE = "__add_new__";` with a one-line comment saying it is a select-only sentinel that is never an address id and never sent to a server.
- `export function nextAddressSelection(addresses: readonly SavedSubscriptionAddress[], preferredId?: string): string`. Implement it as: treat `preferredId` as usable only when it is a non-empty string, is not `ADD_NEW_ADDRESS_VALUE`, and matches the id of some entry in `addresses`; if usable, return it; otherwise return the id of the first entry whose `is_default` is true, else the first entry's id, else `""`. The explicit sentinel rejection is the T-15-03 mitigation and stays even though `ID_PATTERN` already makes a collision impossible — it is one line and it is what the test pins.

Then extend `tests/unit/components/subscriptions/acquisition-client.test.ts`: import both new exports and add a `describe("nextAddressSelection")` block covering the six behaviours above. Build the fixtures as plain `SavedSubscriptionAddress` objects in the style the file already uses for its `fetchSavedAddressesForPlan` cases. Add one assertion that `ID_PATTERN`'s first-character rule rejects the sentinel by testing it through the public surface: a list containing entries whose ids are real-shaped, queried with the sentinel, returns a real id and not the sentinel.

Write the test block first and watch it fail before adding the implementation, then make it pass.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> account-addresses API | The modal writes across this boundary using the wave-1 helper only. No new API surface, no new route, no route edit. |
| select value -> application state | The select can now emit a value that is not an address id. The sentinel must be intercepted before it reaches state or a request. |
| signed-out -> signed-in branch | The dialog must be unreachable for a guest. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15-03 | Tampering | select `onChange`, `nextAddressSelection` | high | mitigate | The sentinel branch returns before writing `addressId`, so it can never enter `selectedSavedAddress`, the `facts` idempotency key or a setup-intent request; `nextAddressSelection` rejects it explicitly as a second layer. Both pinned by Task 1's behaviour test and Task 3's region contract. |
| T-15-01 | Spoofing | `AddAddressDialog.tsx` | high | mitigate | The dialog performs no request of its own; every write goes through the wave-1 `saveAddress`, which sends same-origin credentials to the pre-existing guarded route. Asserted by the Task 3 dialog contract (no field markup, no network call, imports the shared form). |
| T-15-02 | Information disclosure | panel, dialog | high | mitigate | No browser-storage write and no console write in either file; the existing panel contract's negative match plus the new dialog negative enforce it. |
| T-15-04 | Elevation of privilege | panel signed-in branch | high | mitigate | The dialog is rendered inside the `isLoaded && isSignedIn && !setup` branch, so it cannot mount for a guest; the post-save handler re-checks `ownerRef.current` after its await before writing any address into state, so a session change mid-save cannot show one account's addresses under another (D-06). |
| T-15-07 | Information disclosure | post-save refresh | medium | mitigate | The refresh goes through `fetchSavedAddressesForPlan`, so the new entry passes the same shape and bounds validation as on load; `setAddressesOwner(owner)` re-scopes visibility rather than bypassing the owner guard (D-05, RESEARCH pitfall 2). |
