  <behavior>
    - `giftCardReissueId` is deterministic: the same old card id always yields the same new card id, and two different old ids never collide.
    - `writeAdjustment` writes exactly one negative `adjustment` entry for a given business key; a second call with the same key returns the existing entry with `created: false`.
    - `writeAdjustment` for an amount larger than the available balance is refused by the database balance guard and surfaces as `GiftCardConflictError`.
    - `reissue` on a disabled card with no open and no committed-unsettled reservation drains the old card to zero available balance and issues a new card for the same amount.
    - `reissue` called twice on the same old card leaves exactly one adjustment entry and one new account.
    - `reissue` on an active card, or on a disabled card with an open or committed-unsettled reservation, throws without writing anything.
  </behavior>
  <action>
In `lib/gift-cards/domain.ts` add, beside the existing business-key helpers: `giftCardReissueAdjustmentBusinessKey(oldGiftCardId)` returning the D-06 key `gift-card-reissue-out/{oldGiftCardId}`, and `async giftCardReissueId(oldGiftCardId): Promise<string>` — a stable derivation over the literal `gift-card-reissue`, a version marker and the old id, hashed with `crypto.subtle.digest('SHA-256', ...)` and rendered as a hex-suffixed id in the same style as the `stableId` helper in `lib/services/gift-card-fulfillment.ts`. Per D-19 this deterministic id is where reissue idempotency comes from: `issueAccount` derives `issuance_business_key` from the card id it is given, so a stable id makes the naturally derived key unique per old card without the custom-key parameter D-06 originally assumed existed.

In `lib/gift-cards/repository.ts` add `writeAdjustment({ giftCardId, amount, businessKey, entryId?, createdAt })` modelled line for line on `restoreRedemption`: look up by `business_key` first, return `{ created: false, entry }` when present, otherwise one `INSERT INTO gift_card_ledger_entries (...) VALUES (..., 'adjustment', ..., NULL, NULL, NULL, ...) ON CONFLICT DO NOTHING RETURNING id` inside a try, with the catch rereading for a lost race and throwing `GiftCardConflictError` when there is still no row. `reservation_id` and `related_entry_id` must be NULL for an adjustment or the 0022 entry-type CHECK rejects it; `order_id` is unconstrained and stays NULL. Do not compute whether the drain would overdraw — the `gift_card_ledger_balance_guard` trigger is the safety net and its rejection is the correct failure.

Then add `reissue({ oldGiftCardId, now, codeHash, codeSuffix, delivery })` returning `{ created: boolean; newGiftCardId: string; amount: Money }`. Order of operations, per D-06 and D-19:
1. Read the old account; throw `GiftCardUnavailableError` when absent, and `GiftCardConflictError` when its status is not `disabled`.
2. Read `findReservations` and classify each with `classifyGiftCardReservation`; throw `GiftCardConflictError` naming the blocking class when any is `open` or `committed_unsettled`.
3. Read `readBalance` for the available balance; throw `GiftCardConflictError` when it is not positive.
4. `writeAdjustment` for the negation of that balance with `giftCardReissueAdjustmentBusinessKey(oldGiftCardId)`.
5. `issueAccount` with `id: await giftCardReissueId(oldGiftCardId)`, the same currency, the caller's `codeHash`/`codeSuffix`, no `issuedOrderId` and no `issuedLineId`, `purchaserCustomerId` unset, and the caller's delivery block.
Run steps 4 and 5 as two sequential, individually idempotent calls rather than one combined `database.batch()` — `issueAccount` owns its own batch, and nesting them is a pattern this codebase does not use. A retry after a partial failure converges because both writes key off values derived from `oldGiftCardId`.

Cover every behavior bullet with integration cases in `tests/integration/lib/gift-cards/repository.test.ts`. The double-reissue case must call `reissue` twice and then count rows in `gift_card_ledger_entries` and `gift_card_accounts` directly, not trust the return value.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repository -> D1 money tables | the only place ledger, account and delivery rows are written; the 0022 triggers are the enforcement point behind it |
| admin request -> reissue | a repeated or concurrent request must not mint a second card |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-12 | Tampering | double reissue of one card | high | mitigate | Deterministic new-card id (D-19) makes the account INSERT converge; the adjustment business key is unique per old card; plan 14-01's partial UNIQUE index blocks the paired event. Integration case counts rows after two calls |
| T-14-13 | Tampering | reissue of an active card or one with open reservations | high | mitigate | `reissue` reads status and `classifyGiftCardReservation` before writing anything and throws `GiftCardConflictError`; integration cases assert no ledger row is written |
| T-14-14 | Tampering | overdrawing a card through `writeAdjustment` | high | mitigate | The 0022 `gift_card_ledger_balance_guard` trigger, not application arithmetic, rejects a drain past zero; the repository surfaces it as a conflict |
| T-14-15 | Tampering | release of a committed reservation | high | mitigate | `classifyGiftCardReservation` reports `committed_unsettled` distinctly, and the existing 0022 reservation transition trigger refuses the release outright; the repository adds no bypass |
| T-14-16 | Tampering | re-queue resetting attempts on a delivery that is not `needs_review` | medium | mitigate | The UPDATE carries `AND status = 'needs_review'` in its WHERE clause; integration case asserts a `sent` row is untouched |
| T-14-17 | Information Disclosure | arbitrary text reaching `code_suffix` | medium | mitigate | `assertGiftCardCodeSuffix` restricts the field to four characters of the code alphabet before `issueAccount` binds it, so a caller cannot store free text or a longer code fragment in the column |
| T-14-18 | Elevation of Privilege | re-enabling a disabled card | high | mitigate | No re-enable method is added; the 0022 status transition guard forbids disabled-to-active at the database (D-05) |
</threat_model>
