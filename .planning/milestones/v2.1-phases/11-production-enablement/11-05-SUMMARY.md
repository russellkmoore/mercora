## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - blocking issue] `.env.local` restore glob failed to match a dotfile during the move-aside wrapper, stranding it in the temp holding directory.**
- **Found during:** Task 2, Step 2 (regenerate types with env files moved aside).
- **Issue:** The restore command used `mv "$HOLD_DIR"/*.local .` to move the local env file back into the repo root. Under this shell's default glob settings, `*.local` does not match a leading-dot filename (`.env.local`), so the restore silently no-opped (`rmdir` then failed with "directory not empty," and a follow-up check confirmed `.env.local` was missing from the repo root and still sitting in the temp directory).
- **Fix:** Used the same dot-matching glob form as the move-out step (`.env*.local`) for the restore direction as well, moved the file back from the known temp path, verified its presence, and removed the now-empty temp directory. `.dev.vars` restored correctly on the first attempt (its glob had no leading-dot ambiguity). The second full run of the same wrapper later in Task 2 restored both files correctly with the corrected glob form, and Task 3's `cf-typecheck` re-run used the same corrected form throughout.
- **Files affected:** None (temp-directory-only issue; no repo file was lost, `.env.local` was recovered from the known holding path before any command that depended on its absence or presence ran).
- **Commit:** N/A (operational recovery, not a code change).

**2. [Observation, not a bug — no fix needed] The single push produced two deployment entries in `wrangler deployments list`, one minute apart.**
- **Found during:** Task 2, Step 4, final self-check re-verification.
- **Observation:** `git push origin main` carried two commits at once (`b3815e6`, the 11-04 docs-only closeout, and `f7d5067`, this plan's flag change). Two Worker versions subsequently appeared: `31555fd0-5bcc-44bd-b1f7-3839a652c460` (created 18:52:25 UTC) and `b5602b7b-ae47-441d-bf4d-bb3492b26ce8` (created 18:53:24 UTC, now current) — most likely Workers Builds triggering one build event per pushed commit rather than one per push.
- **Why this is not a config-drift risk:** Both versions build from the same `git` tip (`f7d5067`); `b3815e6` touched no path this plan cares about (`wrangler.jsonc`, `cloudflare-env.d.ts` are unchanged by it). The two deployments are functionally identical.
- **Why the cron proof still holds for the current version:** The `wrangler tail` capture was already running (confirmed receiving events by 18:53:26 UTC) before the second deployment's creation timestamp (18:53:24 UTC), and the drain success line was observed later, at 18:55:26 UTC — after both deployments were live. The health proof therefore covers whichever version is actually serving traffic.
- **Action taken:** None — recorded here and reflected accurately in this SUMMARY's D5/D6 coverage entries, which now cite the current version (`b5602b7b`) rather than the first-observed one.

No other deviations. Both tasks with file changes executed exactly as written; the Step 0 drift observation above is a planning-time assumption mismatch (the check assumes a fully-pushed prior plan), not a code issue, and is recorded per the instruction that such mismatches must be proven, not silently worked around.
