    - A GET with `?category=appearance` against a database where the filtered select resolves empty and the unfiltered select resolves non-empty returns status 200 with an empty settings array, and the insert method on the mocked database is never called.
    - A GET with `?category=system` against a database where the filtered select resolves empty inserts only rows whose category is `system`, and inserts strictly fewer rows than the full defaults array holds.
    - A GET with no category against a database where the unfiltered select resolves empty inserts the full defaults array, unchanged from today's behaviour.
    - A GET with `?category=appearance` against a database where the filtered select already resolves non-empty returns those rows and never calls insert.
    - A GET whose permission check resolves unsuccessful returns status 403 and never calls the database factory at all.
    - After a category-scoped seed insert, the re-select that builds the response is itself category-scoped, so the response never leaks rows from a category the caller did not ask for.
  </behavior>
  <action>
Change the seed branch in the GET handler only. Everything above it stays exactly as it is: the
permission check, the 403 return, the URL parsing, the category read, the database factory call and
the two-branch select.

Inside the branch that fires when the selected rows are empty, compute the seed set first: when a
category was requested, filter the defaults array down to rows whose category equals the requested
one; when no category was requested, the seed set is the whole defaults array. Only run the insert
when the seed set has at least one row — this guard is the point of the fix, because the requested
category may legitimately have no defaults at all, and it means the empty-values behaviour of the
database driver is never exercised. Keep the existing console log, but move it inside the guard so a
no-op read no longer claims it initialised anything.

Then rebuild the response with a re-select that matches the original request's scope: category-scoped
when a category was requested, unfiltered otherwise. Today's code re-selects the whole table even for
a filtered request, which would hand the caller every other category's rows; scoping the re-select is
part of the same fix, not an extra.

Do not add an import, do not change the response shapes, do not touch the permission gate, and do not
change the schema or add a migration — the appearance category having no defaults is correct and
stays correct.

Write the regression test as a new file next to the existing one for this route, copying its mocking
boilerplate verbatim: the hoisted mock object, both module mocks, the import-after-mock ordering and
the `beforeEach` auth reset. Build the mocked database as a chainable object whose `select().from()`
resolves one array and whose `select().from().where()` resolves another, so a single mock can model a
partially-seeded table: unfiltered non-empty, filtered empty. Give `insert()` a `values()` spy so the
tests can assert both that it was not called and, in the scoped case, exactly which rows it received.
Build requests with a query string on the URL rather than a body, and use the GET export.

Cover every row in the behavior block, one case each. The insert-argument assertions must compare
against the categories actually present in the defaults array, read at test time from the imported
array — never against a hardcoded row count, which would rot the moment a default is added.
