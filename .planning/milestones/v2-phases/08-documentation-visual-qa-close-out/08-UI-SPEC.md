# Phase 8 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This phase builds no new UI surface.** DOCS-01/02/03 are documentation and verification work
against surfaces Phase 6, 6.1, and 7 already built and already specified in their own UI-SPECs.
This document does **not** restate those contracts. It specifies only the two things this phase's
own output must satisfy design-quality review on:

1. **The visual QA matrix** (D-03/D-04/D-05) — a documentation artifact (`08-QA-MATRIX.md`), not a
   screen. Its "UI" is a findings table; the contract below is that table's pass criteria and format.
2. **`docs/theming.md` and the `docs/CLAUDE.md` edits** (D-01/D-02) — a static prose document. Its
   "UI" is the reading experience: section order, code-block/table legibility, copy tone.

Per the CONTEXT's autonomous-run note, no `AskUserQuestion` blocked this research; unresolved
judgement calls are recorded as flagged assumptions in `## UI Considerations` below, not silently
decided.

**Reference, do not restate:** the seven presets' token contracts and light-preset QA precedent
live in `06-UI-SPEC.md` §Preset Token Contracts and `06.1-UI-SPEC.md` §Preset Token Contracts /
§Light-Preset QA Checklist. The eight layout variants' anatomy and the three packed combinations
(A/B/C) live in `07-UI-SPEC.md` §Storefront Variant Anatomy and `07-SCREENSHOTS.md`'s Variant
Coverage Table. This phase's QA matrix (`## QA Matrix Pass Criteria` below) is the superset run
across all seven presets using those same three combinations — it inherits their per-surface
judgement precedent (Phase 6's scrim-polarity finding, Phase 6.1's three acid tests) rather than
re-deriving new criteria.

## QA Matrix Pass Criteria (D-04) — the core design-quality contract for this phase

### Scope and structure (D-03)

21 harness runs = 7 presets (`volt-dark`, `luxe`, `midnight`, `clinical`, `retro`, `atelier`,
`market`) × 3 packed layout combinations, reusing `07-SCREENSHOTS.md`'s exact definitions verbatim:

| Combination | `categoryLayout` | `homeHero` | `productGallery` |
|---|---|---|---|
| A (defaults) | `grid-3` | `minimal` | `left` |
| B | `grid-2` | `split` | `top` |
| C | `list` | `full-bleed` | `left` |

Each run captures the full seven-route grid `screenshot-routes.mjs` already defines (`home`,
`category`, `product`, `cart`, `checkout`, `account`, `order-status`) at both viewports (1280,
390) and their existing per-route states (`resting`/`nav-open`, plus `cart-open` for the `cart`
cell) — the same grid Phase 6/6.1/7 used, not a new one. `--include-content` cells (blog index,
one blog post, one CMS page) are additive per D-03 ("plus `--include-content` cells") and get the
same per-cell pass criteria below; their absence (no seeded blog post/CMS page in the local
fixture) is recorded as a MISSING row with reason, exactly like the existing `order-status`
MISSING pattern already established in every prior phase's manifest — never silently omitted from
the coverage grid.

### Per-cell pass criteria (D-04), evaluated for every rendered cell

A cell is a specific (preset, combination, route, viewport, state) tuple. Judge each rendered cell
(MISSING cells are exempt — record the reason, not a pass/fail) against all six criteria below.
Any single failing criterion makes the cell a **finding**, not a silent pass:

| # | Criterion | What "pass" looks like | What to check for a fail |
|---|---|---|---|
| 1 | Renders without error | No error boundary, no blank/white-screen crash, no console-visible unhandled exception captured in the screenshot | A visibly broken page, a stack trace rendered to the DOM, or a route that 500s instead of rendering |
| 2 | No overflow/clipping | Text, cards, the gallery strip, and the hero band stay within their container at both viewports; no horizontal scrollbar on the page body | A word/number spilling past its container edge; a card cut off at the grid edge; `CategoryList`'s image/CTA row squeezed off-screen at 390px (per `07-UI-SPEC.md`'s own flagged overflow row) |
| 3 | Text legible on its surface | Body/heading text visibly contrasts its background by inspection (not a computed WCAG ratio re-derivation — that was already done per-token in `06-UI-SPEC.md`/`06.1-UI-SPEC.md`); any visible `ring`/`border` (focus states, card hairlines, thumbnail selection) is visibly present, not invisible-by-omission | Light-on-light or dark-on-dark text; a hairline `border` that has vanished into its `surface` (the exact class of defect Phase 6.1's Clinical acid test targeted) |
| 4 | Scrims read dark | `Dialog`/`AlertDialog`/`Sheet` overlays and the category hero overlay visibly recede the backdrop behind them, regardless of preset polarity; `HomeHeroFullBleed`'s literal `bg-black/50` scrim (07-UI-SPEC.md §Color) reads as a dark backdrop under every preset, light or dark | A light-preset scrim reading as a pale wash that fails to visually separate the modal/drawer/hero-copy from the page — this is Phase 6's own named finding (D-04), now being re-verified across four *more* presets (`clinical`, `atelier`, `market` are light; `retro`/`midnight` are dark and inherit `volt-dark`'s already-passing polarity) |
| 5 | Display face present on headings | The active preset's `font-display` value visibly renders on heading elements — a genuinely different typeface for `luxe`/`retro`/`atelier`/`market` (Cormorant Garamond / Orbitron / Fraunces / Nunito), or a confirmed intentional same-face-as-body render for `volt-dark`/`midnight`/`clinical` (all three reuse Geist for `font-display` by design — see `06-UI-SPEC.md`/`06.1-UI-SPEC.md`) | A heading rendering in the fallback stack (Georgia/system-ui/sans-serif) instead of the loaded webfont — the exact regression 6.1-03/6.1-04 already found and fixed once (`S-TYPE-01`); re-verify it held, don't re-fix it from scratch |
| 6 | Layout matches its variant's anatomy | The active combination's three variants (`categoryLayout`, `homeHero`, `productGallery`) visibly match `07-UI-SPEC.md`'s described anatomy for that combination — column count, hero shape (minimal/split/full-bleed), gallery orientation (left/top) | A variant rendering as a different variant than the one the admin setting/URL selected (a wiring bug, not a visual-polish judgement call) |

### Findings-table format (D-05)

Reuse `06.1-SCREENSHOTS.md`'s exact column set verbatim — do not invent a new format:

```
| # | Site | File:line | Class in play | What it looks like under the preset | Judgement | Reason |
```

- **Fix or leave-it, never fix-only:** a row that reads "Leave it" after inspection is as much a
  finding as a row that reads "Fixed" — a table containing only changes is itself a defect in the
  record (D-04, same instruction 06.1's Findings section already enforced).
- **Each fix is its own commit** with a written reason in the commit message — never bundled with
  unrelated fixes, matching the "F4" precedent in `06.1-SCREENSHOTS.md` (one bug, one commit, one
  named reason).
- **`scan:tokens` stays at 0** for the duration of the phase; **no contract change** — if a finding
  can only be resolved by adding/renaming a token or changing a `themes/*.css` value outside a
  typo-level correction, it is out of scope for this phase and gets recorded as a flagged,
  unresolved finding for a future milestone, not implemented here.
- **Summary table** (preset × combination → pass/notes) is copied into `docs/theming.md` verbatim
  once `08-QA-MATRIX.md` is complete (D-05) — a compact grid, not the full findings table.

### Coverage-grid ordering (list-collection shape, see `## UI Considerations`)

The 21-run coverage grid in `08-QA-MATRIX.md` is ordered **preset-major, then combination**
(`volt-dark`×A, `volt-dark`×B, `volt-dark`×C, `luxe`×A, …) — matching the preset order REQUIREMENTS
and both prior UI-SPECs already use (`volt-dark, luxe, midnight, clinical, retro, atelier, market`)
and the combination order A→B→C `07-SCREENSHOTS.md` already established. This ordering is stable
across the whole record; do not re-sort mid-document.
