<objective>
Build the completion gate for the whole-phase sweep: a zero-dependency scan script that finds
every hardcoded palette value in storefront code, with a fail-first proof that it actually
has teeth.

Purpose: TOKEN-03's success criterion is "a whole-tree scan finds zero hardcoded palette
values". That claim is only worth something if the scan is proven to fail on a dirty tree
before it is ever seen passing on a clean one. This plan builds the gate first, while the
tree is still dirty, so its fail-first behaviour is demonstrated against real code rather
than asserted.

Output: `scripts/scan-hardcoded-colors.mjs`, the `scan:tokens` npm script, and a fixture-based
unit test proving the gate catches violations, ignores the admin tree, honours region
sentinels, and never silently skips a manual-review file.
</objective>

  <name>Task 1: Build the whole-tree hardcoded-palette scanner</name>
  <files>scripts/scan-hardcoded-colors.mjs, package.json</files>
  <read_first>
    - `scripts/check-deploy-config.mjs` — the exit-code, tag-prefix, and try/catch convention to copy
    - `scripts/build-with-public-env.mjs` — the `process.argv` flag-parsing shape to copy
    - `.planning/phases/05-token-contract-component-sweep/05-TOKEN-MAP.md` §6 — the authoritative scan scope, source-of-truth allowlist, path exclusion, sentinel rule, comment-stripping rule, and manual-review registry
    - `package.json` — the existing `scripts` block; the new entry goes alongside `check:migrations`
    - `app/globals.css` — confirm the admin rule block that the sentinel exclusion will later wrap
    - `lib/utils.ts` — confirm its palette strings all live inside JSDoc, which comment stripping must remove
  </read_first>
  <action>
    Create `scripts/scan-hardcoded-colors.mjs` following the repo script convention named in
    `<interfaces>`, using the tag `scan-tokens` and importing only `node:fs` and `node:path`.

    Walk roots `app`, `components`, `lib`, `themes`, and the single file `tailwind.config.ts`,
    visiting files with extensions `.ts`, `.tsx`, `.css`.

    Skip any directory segment named `admin` — this covers both storefront admin trees and is
    the only path-based exclusion the phase permits (D-14).

    Treat `themes/` and `lib/themes/tokens.ts` as the theme source of truth: hex literals are
    legal there and produce no finding. Every other in-scope file must be free of them.

    Process each file in this order, because the order is load-bearing:
    1. Split into lines, keeping 1-based line numbers.
    2. Apply region sentinels first: a line containing `gsd:scan-ignore-start` opens a skipped
       region, a line containing `gsd:scan-ignore-end` closes it. Lines inside are excluded.
       An unclosed region at end-of-file is an ABORT, not a silent skip.
    3. Then blank out comment bodies — `//` to end of line outside a string, and `/* */`
       block comments spanning lines — replacing each stripped character with a space so
       column numbers stay accurate. This is what keeps the `cn()` JSDoc examples in
       `lib/utils.ts` and the shade annotations in the admin CSS block from registering.

    Match four finding classes against what remains, collecting every match with its path,
    1-based line, and 1-based column:
    - hex literals of 3, 4, 6, or 8 hex digits following a `#`;
    - `rgb(`, `rgba(`, `hsl(`, `hsla(` immediately followed by a digit;
    - raw Tailwind palette utilities: any of the prefixes `bg`, `text`, `border`, `ring`,
      `from`, `to`, `via`, `fill`, `stroke`, `divide`, `outline`, `decoration`, `caret`,
      `accent`, `shadow`, `placeholder` joined by a hyphen to any of the family names
      `gray`, `neutral`, `zinc`, `slate`, `stone`, `orange`, `red`, `green`, `blue`, `amber`,
      `yellow`, `emerald`, `lime`, `teal`, `cyan`, `sky`, `indigo`, `violet`, `purple`,
      `fuchsia`, `pink`, `rose`, `white`, `black`, with an optional numeric shade suffix.
      Allow an arbitrary Tailwind variant chain before the prefix (segments ending in `:`)
      so modified forms are caught too;
    - the shadcn vocabulary this codebase never defined: family names `popover`, `accent`,
      `muted`, `destructive`, `card`, `secondary`, `input`, `background`, and the
      `-foreground` compounds `primary-foreground`, `secondary-foreground`,
      `accent-foreground`, `card-foreground`, `popover-foreground`, behind the same prefix
      and variant-chain rules. `muted-foreground` is a real contract token and must NOT be a
      finding; `primary`, `foreground`, `surface`, `border`, `ring` and the other contract
      stems must NOT be findings either.

    Sort all findings by path, then line, then column, and print one `path:line:col  <match>`
    row each. Sorting is what makes two runs over an unchanged tree byte-identical.

    Maintain a `MANUAL_REVIEW` array of `{ file, reason }` entries seeded from
    `05-TOKEN-MAP.md` §6 with exactly two rows, and print every entry as a
    `MANUAL-REVIEW  <file>  — <reason>` line on every run, before the verdict line and
    regardless of whether any violation was found.

    Print `[scan-tokens] 0 violations` and exit 0 when the finding list is empty; print
    `[scan-tokens] ABORT: N violation(s) in M file(s)` and exit 1 otherwise.

    Support `--path <dir-or-file>` to scope the walk to one subtree (the tests use it) and
    `--json` to emit the findings array instead of the human rows. Neither flag may weaken
    the exclusion rules.

    Register the scanner in `package.json` as `"scan:tokens": "node scripts/scan-hardcoded-colors.mjs"`.
    Use exactly that key — an npm lifecycle-prefixed name would never fire on this repo's real
    deploy path, which calls `build:worker` (RESEARCH Pitfall 5).
  </action>
  <acceptance_criteria>
    - `scripts/scan-hardcoded-colors.mjs` exists, begins with a `#!/usr/bin/env node` shebang, and imports only from `node:fs` and `node:path`
    - `package.json` contains the key `scan:tokens` mapped to a command invoking `scripts/scan-hardcoded-colors.mjs`
    - `mise exec -- npm run scan:tokens` exits 1 against the current pre-sweep tree and lists at least 50 distinct files
    - No row in that output has a path beginning `app/admin/` or `components/admin/`
    - No row in that output points at `lib/utils.ts` (its palette strings are all JSDoc)
    - No row in that output points at a file under `themes/`
    - The output contains exactly two lines beginning `MANUAL-REVIEW`, naming `lib/utils/image-placeholders.ts` and `lib/types/mach/Promotion.ts`
    - Running `mise exec -- npm run scan:tokens` twice and diffing the two stdout captures produces no differences
  </acceptance_criteria>
  <verify>
    <automated>mise exec -- npm run scan:tokens; test $? -eq 1</automated>
    <fails_when>the scanner exits 0 while the tree is still un-swept, or exits with a code other than 1 (a crash), or prints a stack trace</fails_when>
    <automated>mise exec -- npm run scan:tokens 2>&1 | /usr/bin/grep -c '^MANUAL-REVIEW'</automated>

    <automated>mise exec -- npm run scan:tokens 2>&1 | /usr/bin/grep -E '(^|[[:space:]])(app|components)/admin/' | /usr/bin/wc -l</automated>
    <fails_when>the printed count is anything other than 0</fails_when>

    <fails_when>diff prints any line, meaning the finding order is not deterministic</fails_when>
