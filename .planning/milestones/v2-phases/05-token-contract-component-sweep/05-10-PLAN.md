<objective>
Sweep the checkout flow and bridge the theme tokens across the server-to-client boundary so
Stripe Elements can be themed.

Purpose: the Stripe Elements iframe cannot read the page's CSS custom properties, so it is one
of the four consumers that need hex at runtime (D-09). How those values reach it matters beyond
this phase: computing them server-side and passing them through the existing provider means
Phase 6 can make the active theme a per-request D1 read without changing a single caller. A
direct client-side import would work today and foreclose that.

Output: the provider carrying theme tokens, Stripe's appearance fully token-driven, eleven
checkout files scan-clean, and a checkout screenshot set.
</objective>

`lib/store/StoreConfigProvider.tsx` is a 17-line client module exporting:

  StoreConfigProvider({ config: StoreConfig, children: ReactNode })
  useStoreConfig(): StoreConfig     // throws outside the provider

It is instantiated once, in `app/layout.tsx`, wrapping the entire tree. Extending it with a
second value is a one-file change that reaches every client component in the storefront.

`components/checkout/StripeProvider.tsx` is a `"use client"` component building a
`StripeElementsOptions` object. Its `appearance.variables` holds five colour literals
(`colorPrimary`, `colorBackground`, `colorText`, `colorDanger`, plus a font stack) and its
`appearance.rules` holds four more inside `.Input`, `.Input:focus`, `.Input--invalid`, and
`.Label`. It also carries an `rgba()` focus shadow. It is consumed by both
`components/checkout/CheckoutClient.tsx` and `components/subscriptions/SubscriptionAcquisitionPanel.tsx`.

`lib/themes/tokens.ts` exports `getThemeTokens()` returning the 23-field `ThemeTokens` object.
Plan 05-03 asserted it reads no environment variable and imports nothing server-only.

The Stripe mapping is `05-TOKEN-MAP.md` §3b — the same inverse mapping the emails use (D-11).
The payment form stays light under volt-dark.

Checkout UI files are all main-set surfaces. Measured scope: `CheckoutClient.tsx` 21 occurrences
over 415 lines, `StripeProvider.tsx` 10, `DiscountCodeInput.tsx` 9, `PaymentForm.tsx` 8,
`ShippingOptions.tsx` 6, `ProgressBar.tsx` 6, `OrderConfirmationModal.tsx` 6,
`ShippingForm.tsx` 5, `OrderSummary.tsx` 5, `app/checkout/success/page.tsx` 4,
`OrderItemCard.tsx` 3, `app/checkout/page.tsx` 2.

`StripeProvider.tsx`'s `.Input` rules set a sixteen-pixel font size and a forty-four-pixel
minimum height with comments explaining that they prevent iOS zoom and meet touch-target
guidance. Those are not colour and must survive untouched.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server component → client bundle | `getThemeTokens()` is computed server-side and handed across the boundary through React context. |
| storefront page → Stripe Elements iframe | Appearance values are passed to a third-party frame that renders payment inputs. |
| payment outcome → shopper | Success and failure states are read by colour before they are read as text. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-10-01 | Spoofing | payment outcome state colours | high | mitigate | Success and danger are asserted to be distinct tokens in `CheckoutClient.tsx`, and the human check enters a bad card number to confirm the invalid state reads as an error. A declined payment that looks like a success is the worst outcome this sweep could produce. |
| T-05-10-02 | Tampering | Stripe Elements `appearance` passed into a third-party iframe | medium | mitigate | Every appearance value comes from the typed `ThemeTokens` constant, never from user input or a URL parameter, so no caller-controlled CSS can be injected into the payment frame. The existing caller-override spread is preserved but is itself fed from typed component props. |
| T-05-10-03 | Information Disclosure | theme tokens crossing into the client bundle | low | accept | The tokens are colour, radius, and font-stack strings. Plan 05-03 asserted the module reads no environment variable and imports nothing server-only, so nothing secret can ride along. |
| T-05-10-04 | Denial of Service | mobile input zoom regression | medium | mitigate | The sixteen-pixel input font size and forty-four-pixel minimum height are asserted present after the rewrite, and the human check exercises the mobile form directly. A dropped font size makes iOS zoom on every field. |
| T-05-10-05 | Tampering | Clerk appearance edited out of chunk order | low | mitigate | Task 1 asserts the Clerk `appearance` prop is byte-identical; its rewrite belongs to plan 05-11. |
| T-05-10-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan installs nothing; the only phase install happened in 05-02 behind the blocking human legitimacy checkpoint. |
