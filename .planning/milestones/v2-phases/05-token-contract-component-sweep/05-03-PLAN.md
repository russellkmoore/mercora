`tailwind.config.ts` today (32 lines) exports a `Config` whose only `theme.extend` key is
`colors`. It already defines the helper this plan extends:

  const runtimeColor = (variable: string) => `rgb(from var(${variable}) r g b / <alpha-value>)`;

Keep that helper byte-identical, keep the `content` array, keep
`plugins: [require("@tailwindcss/typography")]`.

`app/globals.css` line 1 is `@import 'tailwindcss';` and line 2 is
`@config '../tailwind.config.ts';`. A plain CSS `@import` must precede every non-import
at-rule, so the theme import belongs on the line immediately after line 1, ahead of `@config`.

`app/layout.tsx` currently: `<html lang="en" suppressHydrationWarning>` has no `data-theme`
attribute; `<body>` carries `className={`${geistSans.variable} ${geistMono.variable}
antialiased flex flex-col min-h-screen`}` plus a `style` prop that sets `backgroundColor`,
`color`, and five `--store-` custom properties from `config.theme`. `config` comes from
`getStoreConfig()` and is still needed for `StoreConfigProvider`.

`lib/store-config.ts` `StoreConfig["theme"]` is
`{ mode: "dark" | "light"; primary: string; surface: string; surfaceElevated: string;
foreground: string; mutedForeground: string; logoPath: string }`. The defaults object sits at
lines 114-122 and the env-override block at lines 419-424. `app/layout.tsx` is the only reader
of the colour fields anywhere in the tree — this was confirmed by a whole-repo grep, closing
RESEARCH.md Open Question 2.

Tailwind v4.3.3 defines its own `--radius-sm`, `--radius-md`, `--radius-lg`, `--radius-xl`
and `--font-sans` in `node_modules/tailwindcss/theme.css`. This is why every contract property
carries the `--store-` prefix (D-07) — bare names would collide with the framework's own layer.

`tests/unit/tailwind-config.test.ts` currently asserts three keys including
`colors.background`, an alias this plan deletes. It must be updated in the same task, or the
suite breaks.

      border makes focus rings marginally more visible.

      on the page background.

      enumerates `border-inverse` as covering the drawers' dark border classes, and D-10
      separately routes transactional email dividers to that same token. Those two locked
      decisions meet on one value, and one value cannot be both a dark drawer edge and a light
