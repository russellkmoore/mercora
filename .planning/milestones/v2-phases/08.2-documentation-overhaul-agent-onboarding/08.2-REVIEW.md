## Critical Issues

### CR-01: The locked-ADR guard doesn't verify which entries carry `locked: true`

**File:** `scripts/docs-lint.mjs:184-204` (`checkLockedAdrGuard`)
**Issue:** D-10 and the manifest's own comment ("All four ADRs locked... never merged, renamed or
moved") establish that `checkLockedAdrGuard` exists specifically to catch an ADR being silently
unlocked. The implementation checks two things independently: (1) each of the four `LOCKED_ADRS`
paths appears somewhere in the manifest as a `path:` line, and (2) the whole file contains exactly
four lines matching `locked: true`. It never associates a specific `locked: true` line with a
specific ADR's `path:` entry.

I proved this is exploitable: I removed `locked: true` from `docs/subscriptions.md`'s manifest entry
and added it to `docs/theming.md`'s entry instead (a non-ADR SPEC doc), leaving all four ADR `path:`
lines in place. `mise exec -- node scripts/docs-lint.mjs` still printed `[docs-lint] 0 violations`
and exited 0. I reverted with `git checkout -- gsd-ingest-manifest.yaml` and reran the gate clean to
confirm no residual state. A future edit that moves or drops the lock marker on a real ADR — while
compensating the count elsewhere, even accidentally — passes the gate silently, defeating the one
check whose entire job is to prevent exactly that.
**Fix:** Bind the lock check to each specific path instead of a global count, e.g. parse each ADR's
YAML block and assert `locked: true` appears within it:
```javascript
function checkLockedAdrGuard() {
  const violations = [];
  const manifestLines = readLines(MANIFEST_PATH);
  for (const p of LOCKED_ADRS) {
    if (!existsSync(path.join(REPO_ROOT, p))) {
      violations.push(violation("locked-adr-guard", p, 0, "locked ADR missing from the working tree"));
      continue;
    }
    const pathIdx = manifestLines.findIndex((l) => l.includes(`path: ${p}`));
    if (pathIdx === -1) {
      violations.push(violation("locked-adr-guard", MANIFEST_PATH, 0, `locked ADR not listed in manifest: ${p}`));
      continue;
    }
    // The entry's fields live on the lines between this path: and the next path:/blank separator.
    const nextPathIdx = manifestLines.findIndex((l, i) => i > pathIdx && /^\s*-\s*path:/.test(l));
    const entryLines = manifestLines.slice(pathIdx, nextPathIdx === -1 ? undefined : nextPathIdx);
    if (!entryLines.some((l) => l.includes("locked: true"))) {
      violations.push(violation("locked-adr-guard", MANIFEST_PATH, pathIdx + 1, `${p}'s manifest entry is missing locked: true`));
    }
  }
  return violations;
}
```
This also lets you drop the fragile global "exactly 4" count, which was only a weak proxy for the
real invariant.

## Warnings

### WR-01: `checkHeaderConvention` never enforces the Status line, so the gate can't catch the exact regression the phase's own verification already found once

**File:** `scripts/docs-lint.mjs:253-263` (`checkHeaderConvention`)
**Issue:** The check only asserts line 1 matches `/^# /`. It does not look for a `**Status:**` line
anywhere in the file, even though the phase's style contract (D-05, `08.2-CONTEXT.md`) and the
roadmap's own success criterion require "a consistent header: title, one-line purpose, status."
`08.2-VERIFICATION.md` already caught four docs missing a Status line that this check let through
silently; the follow-up commit (`ce218ac`) added Status lines to those four files by hand but never
touched `docs-lint.mjs`. I confirmed the gate is still blind to this: I stripped the `**Status:**`
line from `docs/theming.md` and reran `mise exec -- node scripts/docs-lint.mjs` — it still printed
`0 violations`. Reverted with `git checkout -- docs/theming.md` (confirmed via `git diff` before and
`git status --short` after). Any future doc edit that drops its Status line will pass this gate
without anyone noticing, exactly as happened once already in this phase.
**Fix:**
```javascript
function checkHeaderConvention() {
  const violations = [];
  const STATUS_RE = /^\*\*Status:\*\*/;
  for (const rel of docsTopLevelMarkdownFiles()) {
    const lines = readLines(rel);
    const first = lines[0] || "";
    if (!/^# /.test(first)) {
      violations.push(violation("header-convention", rel, 1, "first line is not a level-one heading"));
    }
    if (!lines.slice(0, 15).some((l) => STATUS_RE.test(l.trim()))) {
      violations.push(violation("header-convention", rel, 1, "missing a **Status:** line near the top"));
    }
  }
  return violations;
}
```
(Cap the search window — e.g. first 15 lines — so a `**Status:**`-shaped string deep in prose doesn't
count; adjust the window to whatever the longest real purpose paragraph in the set requires.)

### WR-02: `docs/CLAUDE.md` contains a stale, factually wrong comment about CI wiring

**File:** `docs/CLAUDE.md:123`
**Issue:** The project-structure tree comment reads:
```
│     ├── scan-hardcoded-colors.mjs  # Token-contract scanner (local gate, not CI-wired)
```
This is false. `.github/workflows/ci.yml:42-43` runs `npm run scan:tokens` (which is
`scripts/scan-hardcoded-colors.mjs`) on every push and pull request — it has been CI-wired since
commit `12d478a` ("feat(08.1-03): wire hardcoded-colour scan into CI (D-03)"), well before this
phase started. D-06's claim-check was scoped to commands/paths/env-vars resolving, not to whether a
parenthetical claim about a file's CI status is still true, so this pre-existing stale comment
survived the phase's otherwise-thorough verification pass. An assistant reading `docs/CLAUDE.md` (the
file whose whole purpose is giving an AI accurate structural context) would wrongly conclude this
scanner isn't enforced anywhere and could, for example, decide to skip fixing a violation "since it's
not gating anything."
**Fix:** Delete the stale parenthetical, or update it to match reality:
```
│     ├── scan-hardcoded-colors.mjs  # Token-contract scanner, wired into CI (npm run scan:tokens)
```

## Info

### IN-01: `checkReferencesResolve`'s path pattern can't see one-level-deep doc paths

**File:** `scripts/docs-lint.mjs:93` (`DOCS_PATH_RE`)
**Issue:** `/docs\/[A-Za-z0-9_.-]+\.md/g` matches only a single path segment after `docs/` — it
cannot match a reference like `docs/archive/foo.md` because the character class excludes `/`. There
are no subdirectory `.md` files under `docs/` today (only `docs/images/presets/*.png`, which this
check doesn't target anyway), so this is currently inert, but D-11's discretion note ("whether
`docs/archive/` ... is used for retired historical docs") explicitly considered an archive
subdirectory as a live option. If a future doc set adopts `docs/archive/`, this check silently stops
verifying references into it.
**Fix:** Widen the character class to allow nested paths: `/docs\/[A-Za-z0-9_./-]+\.md/g` (add `/` to
the allowed set), and confirm it still excludes trailing punctuation correctly.
