## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Presets & the light-theme acid test
- **D-01:** Three presets ship: `volt-dark` (existing, remains the manifest default), `luxe` (light: warm ivory, champagne gold accent, serif display face) and `midnight` (dark: indigo-black, second dark theme proving the mechanism is not volt-dark recoloured). Both new presets are authored from Russell's `docs/voltique-theme-direction.md` specs (sections 1 and 2), converted onto the 23-token contract. The other four themes in that document (Clinical, Retro, Atelier, Market) are deferred.
- **D-02:** Non-Geist display fonts load in the root layout via `next/font` with `preload: false` (Cormorant Garamond for Luxe), exposed as a CSS variable the theme file references in `--store-font-display`. A theme file never contains `@import` or `@font-face`; the validator rejects them. Browsers fetch a face only when text uses it, so volt-dark pages pay nothing extra.
- **D-03:** The 23-token contract is frozen one-way (Phase 5 D-01). The direction doc's extra properties (`shadow`, `border-width`, `image-aspect`, `accent-2`, `font-mono`) are NOT added. Presets express themselves through the 23 tokens only; the rest is dropped or approximated, and the dropped properties are recorded as a backlog note for a later milestone.
- **D-04:** Scrims stay black-alpha (`bg-black/50` style backdrops) and shadows stay Tailwind defaults — both are polarity-neutral. THEME-04's light-preset QA inspects shadows and overlays under `luxe` and fixes only what actually reads wrong, case by case, with each fix recorded. No blanket surface-relative overlay class is introduced.

#### Theme file format & build validator (THEME-01)
- **D-05:** Each theme file opens with a header comment block carrying metadata, e.g. `/* @theme label: Luxe | industry: fashion, jewelry, watches | synopsis: A small luxury house … */`. The scanner parses it into the manifest as `{ name, label, meta: { industry?, synopsis? }, tokens }`. `label` is required; `industry` and `synopsis` are optional and feed the admin cards (Russell's request, todo `theme-metadata-industry-synopsis-admin.md`). One file is the single source of truth per theme.
- **D-06:** The validator is strict on all four checks: every one of the 23 `--store-*` tokens present; no unknown `--store-*` token; no rule other than the file's own single `[data-theme="<name>"]` block (no `@import`, `@font-face`, `:root`, or second selector); `<name>` equals the filename stem. Any failure exits non-zero with a `file:line` message and fails `build:worker` and `predev` (both wired explicitly; a `prebuild` script name never fires on the deploy path).
- **D-07:** Colour tokens must be 6-digit hex (`#rrggbb`). Emails and Stripe read raw manifest values and `oklch()` has poor mail-client support. The direction doc's oklch values are converted to hex when a preset is authored; the conversion is noted in the theme header.
- **D-08:** `lib/themes/manifest.generated.ts` and `themes/index.generated.css` are committed to git, regenerated by `scripts/build-themes.mjs` on `predev` and `build:worker`, and a CI freshness check (`build-themes.mjs --check`) fails when the committed output is stale. `app/globals.css` imports the barrel instead of `volt-dark.css` directly.

#### Active theme resolution (THEME-02)
- **D-09:** The admin's choice is stored as `admin_settings` row `appearance.theme` in a new category `appearance` (Phase 7's layout switches join it), written through the existing `POST /api/admin/settings` pattern.
- **D-10:** `getActiveTheme()` lives in `lib/themes/active-theme.ts` and resolves D1 `appearance.theme` → `NEXT_PUBLIC_THEME_DEFAULT` → manifest default (`volt-dark`). It is called once in the root layout, blocking, never Suspense-wrapped, never isolate-cached. `NEXT_PUBLIC_THEME_DEFAULT` is declared as a `wrangler.jsonc` var and documented as needing a Workers Build variable (project rule for `NEXT_PUBLIC_*`).
- **D-11:** `getThemeTokens(name?)` becomes a synchronous manifest lookup (default: manifest default theme). The root layout calls it with the active name and keeps pushing the result through `StoreConfigProvider`; Stripe, Clerk, emails and `global-error.tsx` callers do not change (Phase 5 D-09). The Phase 5 parity test is updated to assert the manifest matches every theme file.
- **D-12:** An unknown stored theme name falls back to the env/manifest default and emits `theme.unknown_selection` (severity `warning`, sampleRate 1) registered in `TELEMETRY_EVENTS` (`lib/observability/telemetry.ts`) and in the tail Worker's `commerce.telemetry.v1` parity list (`workers/observability-tail/src/core.ts`), with a test asserting both lists agree. **Research note: see Pitfall 4 — a literal reading of this decision conflicts with an existing passing test; recommended resolution documented there.**

#### Admin Appearance section (THEME-03)
- **D-13:** A new page at `app/admin/settings/appearance/page.tsx`, linked from the settings hub like the existing sub-pages. Phase 7 adds its three layout switches to this page.
- **D-14:** Each theme card shows: five colour chips (primary, surface, surface-elevated, foreground, surface-inverse), a small inline mock (a button on a card) rendered from manifest values, the label, the industry line and synopsis from the header metadata, and an "Active" badge on the current theme.
- **D-15:** Selecting a card then pressing an explicit Save button persists the choice (matches the settings page's save model); a toast confirms; the storefront reflects it on the next request with no redeploy.
- **D-16:** The admin keeps its hardcoded palette and stays scan-excluded. Card previews use inline `style` values from the manifest; this is the one legitimate place raw colour values appear in admin UI and needs no scanner exception because admin paths are already excluded.

## Summary

This phase has no new external unknowns — every mechanism it needs (a parse-only PostCSS validator, an async D1 read inside a Server Component, `next/font/google` non-preloaded loading, the existing `admin_settings` save pattern) already has a working precedent somewhere in this exact codebase. The work is almost entirely a **wiring and sequencing problem**: get a validator into two script entry points that don't currently call it (`predev`, `build:worker`), make one previously-synchronous root layout function asynchronous without breaking its Suspense/force-dynamic contract, and extend one existing contract test to loop over N theme files instead of one.

Two things verified during this research materially change how the plan should read versus a literal reading of `06-CONTEXT.md`: **`app/layout.tsx`'s `RootLayout` is not currently an `async function`**, and `getActiveTheme()`'s D1 read (via `getSettings()`/`getDbAsync()`) is unavoidably a `Promise` — so the layout must become `async function RootLayout` and `await getActiveTheme()` before rendering `<html data-theme>`. This is routine in this codebase (`app/product/[slug]/page.tsx` is already an async Server Component) but is a structural change to a file nine other things depend on, not just a token swap. Second, and more load-bearing: **D-12's telemetry parity instruction, read literally, contradicts the existing test it must extend.** `workers/observability-tail/src/core.ts`'s `TAIL_CRITICAL_EVENTS` list and its own `parseEnvelope()` function both hard-require `severity === 'critical'`; `theme.unknown_selection` is specified at `severity: 'warning'`. Adding it to `TAIL_CRITICAL_EVENTS` would fail the existing test `expect(TELEMETRY_EVENTS[event].severity).toBe('critical')` for every member of that list. See Pitfall 4 for the verified evidence and the recommended resolution (register in `TELEMETRY_EVENTS` only; do not touch `TAIL_CRITICAL_EVENTS`).

**Primary recommendation:** Build `scripts/build-themes.mjs` as a `postcss.parse()`-based AST validator + codegen (zero new dependencies — `postcss@8.5.26` is already a devDependency), wire it explicitly into both `predev` and `build:worker` (never a `prebuild` script name — confirmed absent from `package.json` and confirmed to never fire on the real deploy path), commit its two generated outputs (`themes/index.generated.css`, `lib/themes/manifest.generated.ts`) to git per D-08, and give it a `--check` mode for CI. Make `getActiveTheme()` an async function in `lib/themes/active-theme.ts` that resolves D1 → `NEXT_PUBLIC_THEME_DEFAULT` → manifest default, called once with `await` at the top of an now-`async function RootLayout`, never behind Suspense.

### Pattern 1: Parse-only PostCSS validator, four checks

**What:** Walk each `themes/*.css` file's AST and assert structural properties, not just presence of substrings.
**When to use:** Any build-time gate that must reject malformed *structure* (a second selector, a nested at-rule), where a text/regex scan would be unreliable.
**Example (skeleton, not literal production code):**
```js
// Source: local verification this session (node -e with postcss.parse()),
// pattern matches this repo's existing scripts/*.mjs convention.
import postcss from "postcss";
import { readFileSync, readdirSync } from "node:fs";
import path from "node:path";

const REQUIRED_TOKENS = [/* the 23 --store-* names, camelCase→kebab already
                             enumerated in 05-TOKEN-MAP.md §1 — copy verbatim,
                             do not re-derive */];

function validateThemeFile(filePath) {
  const stem = path.basename(filePath, ".css");
  const source = readFileSync(filePath, "utf8");
  const root = postcss.parse(source, { from: filePath });
  const errors = [];

  const rules = [];
  root.walkRules((rule) => rules.push(rule));
  root.walkAtRules((at) => {
    errors.push(`${filePath}:${at.source.start.line}: disallowed at-rule @${at.name}`);
  });

  if (rules.length !== 1 || rules[0].selector !== `[data-theme="${stem}"]`) {
    errors.push(`${filePath}: must contain exactly one rule, [data-theme="${stem}"]`);
  }

  const declared = new Set();
  rules[0]?.walkDecls((decl) => {
    if (!decl.prop.startsWith("--store-")) {
      errors.push(`${filePath}:${decl.source.start.line}: non-token declaration ${decl.prop}`);
      return;
    }
    declared.add(decl.prop);
  });

  for (const token of REQUIRED_TOKENS) {
    if (!declared.has(token)) errors.push(`${filePath}: missing required token ${token}`);
  }
  for (const token of declared) {
    if (!REQUIRED_TOKENS.includes(token)) errors.push(`${filePath}: unknown token ${token}`);
  }

  return errors;
}
```
Collect errors across **all** files before deciding first-failure-vs-all-errors reporting (Claude's Discretion per CONTEXT.md) — `postcss.parse()` itself throws `CssSyntaxError` synchronously on unparseable CSS, so wrap each file's parse in its own try/catch to keep one broken file from hiding errors in the others.

### Anti-Patterns to Avoid

- **A module-level / `React.cache()`-memoized D1 read for the active theme:** Cloudflare Workers isolates are reused unpredictably across requests; a cached value will serve a stale theme after an admin save and violates D-10's explicit "never isolate-cached." `getDbAsync()`'s own `React.cache()` wrapper is fine — that memoizes only *within* a single request/render, not across requests [VERIFIED: `lib/db.ts:72`, `cache(async () => { const { env } = await getCloudflareContext({ async: true }); ... })`, comment confirms "request-level caching"].
- **Wrapping `getActiveTheme()` in `<Suspense>`:** would let `<html>` render before `data-theme` is known, causing a flash of the wrong theme — the entire point of resolving it blocking, above the fold, mirrors exactly how `getStoreConfig()` already works today.
- **A `prebuild` npm script name:** confirmed absent from `package.json` and confirmed the deploy path (`deploy` → `build:worker` → `opennextjs-cloudflare build`) never triggers npm's implicit `pre*` convention for a script not literally named to match. Wire the validator by literally editing the `predev` and `build:worker` script strings [VERIFIED: `package.json` scripts block, read this session — current `"build:worker": "node scripts/build-with-public-env.mjs ./node_modules/.bin/opennextjs-cloudflare build"`, current `"predev": "node scripts/db-local-ensure.mjs"`, no `prebuild` key exists].

|---------|-------------|-------------|-----|
| CSS structural validation | A regex/string-scanning validator | `postcss.parse()` AST walk | Regex cannot reliably detect "a second top-level rule exists" vs. "a nested at-rule" vs. "a token name inside a comment"; the AST gives rule/at-rule/decl boundaries for free and free `CssSyntaxError` handling on malformed input |
| oklch → hex color conversion | An ad hoc/approximate formula | The UI-SPEC's already-computed values | `06-UI-SPEC.md` §Preset Token Contracts already lists every hex value with its oklch source and the conversion method (Björn Ottosson's OKLab/OKLCH → linear-sRGB → sRGB), including two explicit accessibility-driven deviations from the doc's literal values (Luxe `ring`, Midnight `on-primary`) with measured contrast ratios. Re-deriving these risks silently reintroducing the WCAG failures the UI-SPEC already caught and fixed |
| Theme registry / discovery | A hand-maintained list of theme names (in a wrangler var, a config array, etc.) | Directory scan of `themes/*.css` at build time | Explicitly decided at the milestone level (`REQUIREMENTS.md` Out of Scope: "Theme registry as wrangler var or hand-maintained list — Decided: build-time generated from `themes/*.css` only") |
| Font loading for the Luxe display face | `@import`/`@font-face` inside a theme CSS file | `next/font/google` in the root layout, exposed as a CSS var | D-02 explicitly forbids `@import`/`@font-face` inside any `themes/*.css` file, and the validator (Pattern 1) rejects it structurally, not just by convention |

**Key insight:** Every "don't hand-roll" item in this phase already has its answer pre-computed by an earlier document in the phase's own chain (CONTEXT.md's locked decisions, the UI-SPEC's color table). The research risk here is not "what's the right library" — it's "did the plan actually consume the values that were already derived, instead of re-deriving them and drifting."

## Common Pitfalls

### Pitfall 1: `prebuild` never fires on the real deploy path
**What goes wrong:** A script literally named `scripts/build-themes.mjs` gets wired as an npm `prebuild` hook, which silently never runs because the deploy path calls `build:worker`, not `build`.
**Why it happens:** npm's `pre*`/`post*` convention only fires for the *exact* script name being invoked (`npm run build` → runs `prebuild` then `build`); `npm run build:worker` has no corresponding `prebuild:worker` convention and does not chain through `prebuild`.
**How to avoid:** Edit the literal `predev` and `build:worker` script strings in `package.json` to call `node scripts/build-themes.mjs` before the existing command, e.g. `"build:worker": "node scripts/build-themes.mjs && node scripts/build-with-public-env.mjs ./node_modules/.bin/opennextjs-cloudflare build"`.
**Warning signs / verification:** THEME-01's own acceptance test is exactly this — deliberately break a theme file (e.g. delete a required token from `themes/luxe.css`) and run `npm run build:worker`; it must fail non-zero with a `file:line` message, not silently succeed. Run `npm run predev` similarly.

### Pitfall 2: D1 read latency / caching temptation
**What goes wrong:** A well-meaning "optimization" caches `getActiveTheme()`'s result at module scope or via a non-request-scoped cache, then serves a stale theme after an admin save because the isolate that served the cached read is reused for a later request.
**Why it happens:** Cloudflare Workers isolates persist across requests unpredictably; a module-level `let cachedTheme` looks like a normal Node.js pattern but behaves differently at the edge.
**How to avoid:** Accept the per-request D1 read as designed (explicitly decided at the milestone level, see Don't Hand-Roll table). `getDbAsync()`'s `React.cache()` wrapper is safe because it is *request*-scoped, not module-scoped — confirmed by reading its implementation this session.
**Warning signs:** If a future admin theme switch doesn't take effect until a deploy or a manual cache-bust, something reintroduced isolate-level caching.

### Pitfall 3: Wrapping the theme read in Suspense reintroduces FOUC
**What goes wrong:** `data-theme` must be present in the initial server-rendered HTML for the CSS `[data-theme="X"]` block to apply before first paint. If `getActiveTheme()` is wrapped in `<Suspense>` (as `<Header>` and `<PromotionalBanner>` already are, for unrelated reasons), `<html>` renders without `data-theme` and the browser paints with no matching CSS block — a flash of unstyled/wrong-themed content.
**Why it happens:** Suspense boundaries are the idiomatic App Router pattern for slow data, and it's easy to pattern-match "this reads from D1, therefore Suspense" from the two Suspense boundaries already in the same file.
**How to avoid:** Keep `getActiveTheme()` blocking, called directly in the (now-async) `RootLayout` function body, exactly where `getStoreConfig()`/`getThemeTokens()` already sit — never inside a `<Suspense>` child.
**Warning signs:** Any visible flash of the default/wrong theme on page load, especially noticeable when the light `luxe` preset is active (dark→light flash is far more visible than dark→dark).

### Pitfall 4: `theme.unknown_selection` cannot literally join `TAIL_CRITICAL_EVENTS`
**What goes wrong:** D-12 says the event must be "registered in `TELEMETRY_EVENTS` ... and in the tail Worker's `commerce.telemetry.v1` parity list (`workers/observability-tail/src/core.ts`), with a test asserting both lists agree." A literal reading suggests adding `'theme.unknown_selection'` to `TAIL_CRITICAL_EVENTS`. This breaks an **existing, already-passing test**.
**Why it happens / the verified evidence:**
- `workers/observability-tail/src/core.ts:9-35` defines `TAIL_CRITICAL_EVENTS` as an array; its own name and every existing member (`payment.inventory_check_failed`, `webhook.claim_failed`, etc.) are `severity: 'critical'` events in `TELEMETRY_EVENTS` [VERIFIED: `lib/observability/telemetry.ts:25-76`, read this session].
- `tests/unit/workers/observability-tail-core.test.ts:63-67` (existing, passing test) asserts: `for (const event of TAIL_CRITICAL_EVENTS) { expect(TELEMETRY_EVENTS[event].severity).toBe('critical'); }` [VERIFIED: quoted verbatim, read this session].
- `workers/observability-tail/src/core.ts:181` — `parseEnvelope()`'s own guard clause: `if (value.marker !== TAIL_TELEMETRY_MARKER || value.severity !== 'critical' || ...) return null;` [VERIFIED: quoted verbatim, read this session] — the tail Worker structurally discards every non-critical envelope regardless of what's in `TAIL_CRITICAL_EVENTS`.
- D-12 specifies `theme.unknown_selection` at `severity: 'warning'`. Warning-severity events already exist in `TELEMETRY_EVENTS` today (`payment.pricing_rejected`, `ai.response_guard_replaced`, both `warning`) and **neither appears in `TAIL_CRITICAL_EVENTS`** — this is the existing, working precedent for how a non-critical event is "registered" in this taxonomy [VERIFIED: `lib/observability/telemetry.ts:26,28`, cross-checked against `workers/observability-tail/src/core.ts:9-35`, neither event present].

**How to avoid:** Register `theme.unknown_selection` in `TELEMETRY_EVENTS` only (`lib/observability/telemetry.ts`). Do **not** add it to `TAIL_CRITICAL_EVENTS`. The "test asserting both lists agree" should be read as: extend/reuse the existing synchronization pattern (severity-consistency for whatever *is* in `TAIL_CRITICAL_EVENTS`) rather than forcing a warning-severity event into a critical-only list. A reasonable literal way to satisfy the spirit of D-12 with a real, passing test: add an assertion that `TELEMETRY_EVENTS['theme.unknown_selection']` exists with `severity: 'warning'` and `sampleRate: 1`, alongside the existing marker-string parity check (`TAIL_TELEMETRY_MARKER === TELEMETRY_MARKER`, already asserted at line 64) — this is a real cross-file assertion about the shared `commerce.telemetry.v1` contract without requiring the tail Worker to alert on it.
**Warning signs:** If a plan task literally instructs "add `theme.unknown_selection` to `TAIL_CRITICAL_EVENTS`," the existing test at `tests/unit/workers/observability-tail-core.test.ts:63-67` will fail (`TELEMETRY_EVENTS['theme.unknown_selection'].severity` is `'warning'`, not `'critical'`) — this is a build-time gate, not a silent runtime miss, so it will surface immediately, but it's worth pre-empting in the plan so it isn't discovered mid-execution.

### Pitfall 5: The light-preset scrim finding is real and already located
**What goes wrong:** `bg-surface/NN` scrims in `dialog.tsx:106` (`bg-surface/80`), `alert-dialog.tsx:39` (`bg-surface/50`), `sheet.tsx:128` (`bg-surface/50`), and `app/category/[slug]/page.tsx:133` (`bg-surface/40`) [VERIFIED: all four read this session, exact lines and opacity values confirmed] render as a black-alpha scrim under `volt-dark` (`surface: #000000`) but as a light ivory-tinted scrim under `luxe` (`surface: #f8f5ef`) — visually failing to recede the backdrop behind a modal/sheet.
**Why it happens:** These classes are token-driven (not literal `bg-black`), so they pass the token scanner cleanly and look "correctly swept" from Phase 5's perspective — but a token-driven scrim inherits the *theme's* polarity, and a scrim's whole job is to be polarity-*independent*.
**How to avoid:** This is deliberately left unresolved by D-04 for the phase's own QA pass, case-by-case. Two verified constraints on the fix: (1) a literal `bg-black/NN` class will be caught by the token scanner (`black`/`white` are both in `COLOR_FAMILIES` at `scripts/scan-hardcoded-colors.mjs:75` [VERIFIED: read this session]) and needs either the existing `gsd:scan-ignore-start`/`-end` sentinel (a generic mechanism, not admin-specific — confirmed by reading the scanner's sentinel-handling code, which matches the literal string anywhere in scanned files, not just inside the admin CSS block) or a small explicit design decision; (2) no new token may be added (23-token contract frozen one-way per Phase 5 D-01).
**Warning signs:** Screenshot the `luxe` preset with a dialog/sheet/drawer open and the category hero — if the backdrop reads as a light haze rather than visually receding the page behind the modal, the QA pass needs to act.

### Pitfall 6: `getActiveTheme()`'s fallback chain conflates two different "unknown" cases
**What goes wrong:** D-12 says "an unknown stored theme name falls back ... and emits `theme.unknown_selection`." There are at least three distinct paths through the fallback chain: (a) no `appearance.theme` row exists at all (first-ever load, before any admin save), (b) a row exists but its value doesn't match any theme in the manifest (e.g., an admin selected a theme later removed from `themes/`), (c) `NEXT_PUBLIC_THEME_DEFAULT` itself is set to a typo'd/invalid name. D-12's literal wording ("an unknown *stored* theme name") most naturally covers only case (b).
**Why it happens:** Case (a) is not really "unknown," it's "absent" — telemetry-ing every first page-load before an admin ever visits Appearance would be noisy and semantically wrong (sampleRate 1 makes this worse, not better).
**How to avoid:** Only emit `theme.unknown_selection` when a stored value is *present but doesn't match a manifest theme name* (case b). Treat an absent row (case a) as the normal, expected default path — no telemetry. Case (c), an invalid env default, is arguably also worth a signal but is not explicitly in scope per D-12's wording; flag as a planner decision rather than silently deciding it either way.
**Warning signs:** If telemetry volume for `theme.unknown_selection` is nonzero on a fresh/unconfigured environment, case (a) and case (b) were conflated.

### Pitfall 7: `NEXT_PUBLIC_THEME_DEFAULT` build-variable guidance may be broader than necessary
**What goes wrong:** D-10 states `NEXT_PUBLIC_THEME_DEFAULT` "is declared as a `wrangler.jsonc` var and documented as needing a Workers Build variable (project rule for `NEXT_PUBLIC_*`)." The general project rule (this project's own memory: client-rendered code needs the value inlined at build time via a dashboard Build variable, because Cloudflare Workers Builds does not inject `wrangler.jsonc` vars into the build step by default) exists specifically because some `NEXT_PUBLIC_*` values are read inside client-bundled code.
**Why it happens:** `NEXT_PUBLIC_THEME_DEFAULT` is read only inside `getActiveTheme()`, a server-only module (never imported by a client component) — its only consumer is the root layout's server-side resolution chain. Per the same project memory, this project's `build:worker` script (`scripts/build-with-public-env.mjs`) already injects **every** `NEXT_PUBLIC_*` var from `wrangler.jsonc` into the build environment automatically — this was the actual Aug 2026 fix that made a per-var dashboard Build variable unnecessary for vars reached through `build:worker` [CITED: project memory `cloudflare-next-public-build-vars.md`, dated 30 days old at time of read — flagged stale by its own system reminder, verify against current dashboard state before treating as settled].
**How to avoid:** Add `NEXT_PUBLIC_THEME_DEFAULT` to `wrangler.jsonc`'s `vars` block (required regardless, for SSR/runtime access — confirmed pattern: every existing `NEXT_PUBLIC_*` var in `lib/store-config.ts`'s `resolveStoreConfig()` reads from `process.env`, populated at runtime by the `nodejs_compat_populate_process_env` compatibility flag). A dashboard Build variable is likely redundant given the `build:worker` auto-injection fix, but since this is a deploy-environment claim outside what can be verified from the repo alone, treat D-10's instruction as the safer default and follow it, noting the redundancy as a possible simplification rather than reversing the locked decision unilaterally.
**Warning signs:** None expected if D-10 is followed as written; this note exists to prevent over-interpreting the general project rule as requiring extra manual dashboard configuration beyond what the current `build:worker` pipeline already provides.

### `getActiveTheme()` skeleton

```ts
// lib/themes/active-theme.ts
import { getSettings } from "@/lib/utils/settings";
import { THEME_MANIFEST, DEFAULT_THEME_NAME } from "@/lib/themes/manifest.generated";
import { emitTelemetry } from "@/lib/observability/telemetry"; // exact export name TBD — verify at implementation time

export async function getActiveTheme(): Promise<string> {
  const manifestNames = new Set(THEME_MANIFEST.map((t) => t.name));
  const stored = (await getSettings("appearance"))["appearance.theme"] as string | undefined;

  if (stored === undefined) return resolveEnvOrDefault(manifestNames);
  if (manifestNames.has(stored)) return stored;

  // Present but not a known theme -> genuinely "unknown selection" (Pitfall 6, case b)
  // emitTelemetry('theme.unknown_selection', { stored }); // exact call shape per existing telemetry API
  return resolveEnvOrDefault(manifestNames);
}

function resolveEnvOrDefault(manifestNames: Set<string>): string {
  const envDefault = process.env.NEXT_PUBLIC_THEME_DEFAULT;
  if (envDefault && manifestNames.has(envDefault)) return envDefault;
  return DEFAULT_THEME_NAME;
}
```
This is illustrative, not literal production code — the exact `emitTelemetry`-equivalent call shape must be read from `lib/observability/telemetry.ts`'s actual exported logging function at implementation time (this research only confirmed the `TELEMETRY_EVENTS` registration shape, not the call-site API for triggering an event).
