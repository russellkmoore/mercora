<objective>
Build the theme mechanism's spine end to end: a theme CSS file is validated and compiled by a
prebuild script into a generated CSS barrel and a generated typed manifest, and both far ends of the
stack — the browser's CSS cascade and the non-cascade typed bridge — read from that generated
output instead of hand-maintained duplicates.

Purpose: THEME-01. This is the phase's tracer. If the spine is wrong, every later plan (resolution,
presets, admin UI) is built on a dead end. Proving it against the one theme that already exists
costs one commit; discovering it after three presets ship costs a rewrite.

Output: `scripts/build-themes.mjs`, `themes/index.generated.css`, `lib/themes/manifest.generated.ts`,
a rewritten `getThemeTokens` body, the barrel import in `app/globals.css`, the `predev` /
`build:worker` / CI wiring, and fixture-driven validator tests.
</objective>

<assumption_delta_decision>
The assumption-delta detector fired on this phase: the roadmap said "a second theme" (singular),
CONTEXT.md D-01 chose "admins choose among shipped presets" (plural).

**Decision: promote.** The theme `name` — the manifest key, which is exactly the theme file's
filename stem — is the primary identity for everything theme-related: the theme attribute value on
the html element, the `appearance.theme` setting value, the argument to `getThemeTokens(name)`, and
the admin card key. `volt-dark` is demoted to one manifest entry that happens to carry the default
role via `DEFAULT_THEME_NAME`. No code path in this phase may special-case that string beyond the
one exported constant.

The invariant this creates, which Task 3 tests: for every manifest entry, `getThemeTokens(name)`
returns exactly the 23 tokens parsed from that theme's own file. Plan 06-02 adds the second half —
`getActiveTheme()` with `appearance.theme` set to a name resolves to that name.
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo -> build output | Theme CSS files are source, but the generator turns them into global CSS and into a data module that ships to the browser. A malformed or hostile theme file crosses into production output here. |
| build output -> browser | `lib/themes/manifest.generated.ts` is imported by `lib/themes/tokens.ts`, which is pulled into the client bundle through StoreConfigProvider. Anything the codegen emits is publicly readable. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Tampering | `themes/*.css` -> `themes/index.generated.css` | medium | mitigate | Task 1 rule 3: the validator rejects any at-rule and any rule beyond the file's own single attribute-selector block, so a theme file cannot pull in an external stylesheet or font resource. Proven by the extra-rule fixture in Task 3. |
| T-06-02 | Tampering | `scripts/build-themes.mjs` file and path handling | medium | mitigate | The script uses only `node:fs` and `node:path` with no child-process spawn and no shell interpolation; theme names are constrained to lowercase alphanumerics and hyphens before being used in any path or emitted string; output paths are two fixed constants, never derived from file content. |
| T-06-03 | Information Disclosure | `lib/themes/manifest.generated.ts` shipping to the browser | low | mitigate | The codegen emits only name, label, industry, synopsis and the 23 token values.
