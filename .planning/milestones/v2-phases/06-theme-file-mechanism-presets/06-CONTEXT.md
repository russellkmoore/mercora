# Phase 6: Theme File Mechanism & Presets - Context

**Gathered:** 2026-09-04
**Status:** Ready for planning
**Mode:** Smart discuss (autonomous) — four grey areas proposed in batch tables, all accepted by Russell

<domain>
## Phase Boundary

A theme is a self-contained CSS file under `themes/` that can be added or swapped without touching component code. A prebuild scanner validates every theme file, generates the CSS import barrel and a typed manifest, and fails the real deploy build on an invalid file. `getActiveTheme()` resolves the active theme server-side per request (D1 → env → manifest default) and stamps `data-theme` on `<html>`. Admins pick among shipped presets from swatch-preview cards in a new Appearance section. Two presets beyond volt-dark ship, one light, and the light one is the sweep's acid test.

In scope: THEME-01, THEME-02, THEME-03, THEME-04. Out of scope: layout switches (Phase 7), `docs/theming.md` and the presets × layouts QA matrix (Phase 8), any change to the frozen 23-token contract, theming the admin.

</domain>

<decisions>
## Implementation Decisions

### Presets & the light-theme acid test
- **D-01:** Three presets ship: `volt-dark` (existing, remains the manifest default), `luxe` (light: warm ivory, champagne gold accent, serif display face) and `midnight` (dark: indigo-black, second dark theme proving the mechanism is not volt-dark recoloured). Both new presets are authored from Russell's `docs/voltique-theme-direction.md` specs (sections 1 and 2), converted onto the 23-token contract. The other four themes in that document (Clinical, Retro, Atelier, Market) are deferred.
- **D-02:** Non-Geist display fonts load in the root layout via `next/font` with `preload: false` (Cormorant Garamond for Luxe), exposed as a CSS variable the theme file references in `--store-font-display`. A theme file never contains `@import` or `@font-face`; the validator rejects them. Browsers fetch a face only when text uses it, so volt-dark pages pay nothing extra.
- **D-03:** The 23-token contract is frozen one-way (Phase 5 D-01). The direction doc's extra properties (`shadow`, `border-width`, `image-aspect`, `accent-2`, `font-mono`) are NOT added. Presets express themselves through the 23 tokens only; the rest is dropped or approximated, and the dropped properties are recorded as a backlog note for a later milestone.
- **D-04:** Scrims stay black-alpha (`bg-black/50` style backdrops) and shadows stay Tailwind defaults — both are polarity-neutral. THEME-04's light-preset QA inspects shadows and overlays under `luxe` and fixes only what actually reads wrong, case by case, with each fix recorded. No blanket surface-relative overlay class is introduced.

### Theme file format & build validator (THEME-01)
- **D-05:** Each theme file opens with a header comment block carrying metadata, e.g. `/* @theme label: Luxe | industry: fashion, jewelry, watches | synopsis: A small luxury house … */`. The scanner parses it into the manifest as `{ name, label, meta: { industry?, synopsis? }, tokens }`. `label` is required; `industry` and `synopsis` are optional and feed the admin cards (Russell's request, todo `theme-metadata-industry-synopsis-admin.md`). One file is the single source of truth per theme.
- **D-06:** The validator is strict on all four checks: every one of the 23 `--store-*` tokens present; no unknown `--store-*` token; no rule other than the file's own single `[data-theme="<name>"]` block (no `@import`, `@font-face`, `:root`, or second selector); `<name>` equals the filename stem. Any failure exits non-zero with a `file:line` message and fails `build:worker` and `predev` (both wired explicitly; a `prebuild` script name never fires on the deploy path).
- **D-07:** Colour tokens must be 6-digit hex (`#rrggbb`). Emails and Stripe read raw manifest values and `oklch()` has poor mail-client support. The direction doc's oklch values are converted to hex when a preset is authored; the conversion is noted in the theme header.
- **D-08:** `lib/themes/manifest.generated.ts` and `themes/index.generated.css` are committed to git, regenerated by `scripts/build-themes.mjs` on `predev` and `build:worker`, and a CI freshness check (`build-themes.mjs --check`) fails when the committed output is stale. `app/globals.css` imports the barrel instead of `volt-dark.css` directly.

### Active theme resolution (THEME-02)
- **D-09:** The admin's choice is stored as `admin_settings` row `appearance.theme` in a new category `appearance` (Phase 7's layout switches join it), written through the existing `POST /api/admin/settings` pattern.
- **D-10:** `getActiveTheme()` lives in `lib/themes/active-theme.ts` and resolves D1 `appearance.theme` → `NEXT_PUBLIC_THEME_DEFAULT` → manifest default (`volt-dark`). It is called once in the root layout, blocking, never Suspense-wrapped, never isolate-cached. `NEXT_PUBLIC_THEME_DEFAULT` is declared as a `wrangler.jsonc` var and documented as needing a Workers Build variable (project rule for `NEXT_PUBLIC_*`).
- **D-11:** `getThemeTokens(name?)` becomes a synchronous manifest lookup (default: manifest default theme). The root layout calls it with the active name and keeps pushing the result through `StoreConfigProvider`; Stripe, Clerk, emails and `global-error.tsx` callers do not change (Phase 5 D-09). The Phase 5 parity test is updated to assert the manifest matches every theme file.
- **D-12:** An unknown stored theme name falls back to the env/manifest default and emits `theme.unknown_selection` (severity `warning`, sampleRate 1) registered in `TELEMETRY_EVENTS` (`lib/observability/telemetry.ts`) and in the tail Worker's `commerce.telemetry.v1` parity list (`workers/observability-tail/src/core.ts`), with a test asserting both lists agree.

### Admin Appearance section (THEME-03)
- **D-13:** A new page at `app/admin/settings/appearance/page.tsx`, linked from the settings hub like the existing sub-pages. Phase 7 adds its three layout switches to this page.
- **D-14:** Each theme card shows: five colour chips (primary, surface, surface-elevated, foreground, surface-inverse), a small inline mock (a button on a card) rendered from manifest values, the label, the industry line and synopsis from the header metadata, and an "Active" badge on the current theme.
- **D-15:** Selecting a card then pressing an explicit Save button persists the choice (matches the settings page's save model); a toast confirms; the storefront reflects it on the next request with no redeploy.
- **D-16:** The admin keeps its hardcoded palette and stays scan-excluded. Card previews use inline `style` values from the manifest; this is the one legitimate place raw colour values appear in admin UI and needs no scanner exception because admin paths are already excluded.

### Claude's Discretion
- Exact hex conversions of the oklch specs, chip ordering, card layout details, the shape of the CI freshness check, and how the validator reports multiple errors (all at once vs first failure).
- Whether `getActiveTheme()` shares the existing `getSettings('appearance')` helper or does a single-key read.

## Existing Code Insights

### Reusable Assets
- `themes/volt-dark.css` — the reference theme file (23 tokens, single `[data-theme]` block, header comment already present).
- `lib/themes/tokens.ts` — `ThemeTokens` type and `getThemeTokens()`; Phase 6 replaces only the body (D-11). `tests/unit/lib/themes/token-contract.test.ts` parses the CSS and asserts parity.
- `lib/utils/settings.ts` `getSettings(category)` and `app/api/admin/settings/route.ts` (POST `{ updates: [{ key, value, category }] }`) — the D1 settings pattern to reuse for `appearance.theme`.
- `lib/db/schema/settings.ts` `admin_settings` (key, value JSON, category, data_type) — no migration needed for a new key/category.
- `lib/store/StoreConfigProvider.tsx` — already carries `themeTokens` to client consumers (Phase 5 05-10); `toPublicStoreConfig()` narrows the client payload.
- `scripts/build-with-public-env.mjs`, `scripts/db-local-ensure.mjs`, `scripts/scan-hardcoded-colors.mjs` — plain-`.mjs`, zero-dependency script convention to follow for `scripts/build-themes.mjs`. `postcss` 8.5 is a devDependency usable as a parse-only AST reader.
- `lib/observability/telemetry.ts` `TELEMETRY_EVENTS` map and `workers/observability-tail/src/core.ts` — the two `commerce.telemetry.v1` parity files (locked v1 rule).
- `components/ui/card.tsx`, `components/admin/RecommendationSettingsCard.tsx`, `app/admin/settings/page.tsx` — admin card and settings sub-page patterns.

### Established Patterns
- `app/layout.tsx` is `force-dynamic`, stamps `data-theme="volt-dark"` on `<html>` (line ~140) and already calls `getThemeTokens()` and `getStoreConfig()` server-side; `app/globals.css` line 2 imports `themes/volt-dark.css` ahead of `@config`.
- `tailwind.config.ts` maps all 23 tokens through `runtimeColor("--store-*")`; no change needed for new themes.
- Fonts: `next/font/google` Geist + Geist Mono in the root layout exposed as `--font-geist-sans` / `--font-geist-mono`.
- `NEXT_PUBLIC_*` values are read through `resolveStoreConfig(env)` helpers, never module-scope `process.env`; client-visible build vars need a Workers Build variable (memory: `cloudflare-next-public-build-vars`).
- Real deploy path is `build:worker` (`scripts/build-with-public-env.mjs` → `opennextjs-cloudflare build`), called by `deploy`; `predev` runs `scripts/db-local-ensure.mjs`.

### Integration Points
- `app/globals.css` `@import` → generated barrel `themes/index.generated.css`.
- `app/layout.tsx` → `getActiveTheme()` → `data-theme={name}` and `getThemeTokens(name)`.
- `package.json` scripts: `predev` and `build:worker` gain `node scripts/build-themes.mjs`; a CI step gains `--check`.
- `app/admin/settings/page.tsx` hub → link to `/admin/settings/appearance`.
- `TELEMETRY_EVENTS` + tail parity list → `theme.unknown_selection`.

<specifics>
## Specific Ideas

- Russell's six pre-packaged theme specs live in `docs/voltique-theme-direction.md` (committed with Phase 5's transition). Each names a target industry and synopsis; he wants those visible in the admin next to the swatch cards (D-05, D-14). The doc's token names (`surface`, `ink`, `accent`, `font-display`, …) differ from the frozen contract; the planner records the rename map once (doc name → `--store-*` token) and reuses it for both presets.
- Luxe direction: ivory paper, single champagne-gold accent, serif headlines, hairline dividers, square-ish corners (radius 0 in the doc; approximate with the four radius tokens). Midnight direction: indigo-black surfaces, geometric sans, larger radius, glassy elevated cards.
- Phase 5 carry-overs relevant here: `border-inverse` serves both drawer edges and email dividers (if the darker email divider reads badly under any preset, split it in a later phase rather than hardcode); prose blocks run on Typography plugin defaults, so prose accent colour should be wired off the CSS variables in this phase if cheap, otherwise noted for Phase 8.
- Phase 5's screenshot harness (`npm run screenshot:routes`) and scan gate (`npm run scan:tokens`) are the verification tools; capture each shipped preset across the seven-route grid.

</specifics>
