<objective>
Wire both frozen type tokens into the storefront and accept the visible change (D-10).

`--store-font-sans` and `--store-font-display` are fully wired through the token contract, the
Tailwind config and all seven theme files — and neither reaches a single rendered element. Nothing
applies the sans class, and `app/globals.css` pins the document element to a literal system font
stack, so every storefront page renders in the operating system's UI font regardless of which preset
is active. That is why the display faces plan 06.1-02 loaded — Orbitron, Fraunces, Nunito, and
Cormorant Garamond before them — would never appear on a heading.

D-10 settles it: wire both tokens site-wide and accept that the storefront's type changes. Body copy
gets the sans token; the 23 inventoried page-title and CMS section headings get the display class.
Under `volt-dark` this shifts text from the system stack to Geist. That shift is intentional, is
recorded as snap `S-TYPE-01` with before-and-after captures across the route grid, and is explicitly
not a regression — a non-zero diff does not trigger a revert here. D-10 supersedes the zero-visual-
change condition CONTEXT §Specifics and the UI-SPEC carried.

Purpose: make a preset's chosen typography something a visitor actually sees, and prove it — per
preset, on a live page — rather than asserting it from a correct token value.

Output: both tokens rendering, the snap registered with evidence, a per-preset display-face proof
table, and the Phase 6 carry-over closed.
</objective>

### Where each type token has to land, and why

| Token | Element it is declared on | Why not elsewhere |
|---|---|---|
| `--store-font-sans` | the body element | The token's value starts with `var(--font-geist-sans)`. `next/font` declares that variable through a generated class, and the root layout puts that class on the body element. Referencing it from the document element resolves to an undefined custom property, which makes the whole declaration invalid at computed-value time — font-family falls back to the browser default, i.e. the storefront turns serif. |
| `--store-font-display` | each of the 23 heading elements | Custom properties inherit, so a heading nested inside the body sees both the theme block's tokens (declared on the document element by the `[data-theme]` selector) and the layout's font variables (declared on the body element). Both resolve at that depth. |
