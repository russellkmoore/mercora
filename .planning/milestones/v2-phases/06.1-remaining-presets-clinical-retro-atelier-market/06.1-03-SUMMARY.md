## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `app/layout.tsx`'s next/font variable classes were only on `<body>`, leaving the theme's font tokens permanently unresolved**
- **Found during:** Task 2, while verifying the live computed style (not just the source-level grep the plan's own acceptance criteria specified)
- **Issue:** `[data-theme="volt-dark"]` declares `--store-font-sans`/`--store-font-display`, both of which nest a reference to a `next/font` CSS variable (e.g. `--font-geist-sans`). That variable was declared only via a class on `<body>`. Custom properties resolve nested `var()` references at the element that declares the outer property, not the element that later consumes it — so `[data-theme]` (on `<html>`) tried to resolve `--font-geist-sans` where it didn't exist, and the resulting invalid value is what inherited down to `<body>`, regardless of `<body>`'s own `font-family: var(--store-font-sans)` declaration being exactly where the plan's `<action>` said it should be. Verified live: before the fix, computed `font-family` on `html`/`body`/`h1` under `volt-dark` fell all the way back to Tailwind's own default sans stack, not Geist.
- **Fix:** Applied the same six `next/font` variable classes to `<html>`'s `className`, in addition to keeping them on `<body>`. Confirmed the mechanism with a standalone minimal HTML repro (outside this app, not committed) before touching the real code, and confirmed the fix live afterward for both `volt-dark` (Geist) and `luxe` (Cormorant Garamond on the heading, Geist on body).

- **Verification:** live computed-style reads via Playwright against a real `npm run dev` server, before and after; full gate suite green
