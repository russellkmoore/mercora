### WR-01: `failOrderEffect`'s backoff exponent can go negative for a mis-supplied `attempt_count`

**Files modified:** `lib/services/order-effects.ts`, `tests/integration/lib/services/order-effects.test.ts`
**Commit:** 363dc0f
**Applied fix:** Clamped the retry-backoff exponent in `failOrderEffect` to a sane `[0, 10]` range instead of the review's minimal `Math.max(0, ...)` suggestion, extending it to also guard against non-finite input (`NaN`/`Infinity`): a non-finite `attempt_count` now falls back to attempt 1 before the exponent is computed, so a corrupted or hand-constructed `ClaimedOrderEffect` can never produce a fractional, negative, `NaN`, or `Infinity` delay. Added a new integration test (`clamps the backoff exponent for an out-of-range attempt_count (defense-in-depth)`) covering `attempt_count` values of `0`, `-5`, and `NaN`, each asserting the resulting `next_attempt_at` matches the five-minute base delay. The hostile values are passed only via the in-memory `ClaimedOrderEffect` object (never written to the `order_effects` row), since the table's own `CHECK (attempt_count >= 0)` constraint would reject a negative/NaN persisted value — confirmed this constraint exists by hitting it directly during test development. All 14 tests in the file pass, including the 13 pre-existing ones (drain theme logic untouched).
