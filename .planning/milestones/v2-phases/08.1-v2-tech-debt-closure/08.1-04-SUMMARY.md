# Phase 08.1 Plan 04: Cron-drain order-confirmation and merchant-notification emails follow the theme active at staging time Summary

**A new expand-only `order_effects.payload` column carries the admin's active theme from the request that stages a paid order's email effects to the scheduled recovery sweep that may drain them with no request context, closing the one email path Plan 02 could not reach.**

## Accomplishments

- `migrations/0023_add_order_effects_payload.sql` adds one nullable `TEXT` column to `order_effects` with no default and no backfill — verified expand-only against the repo's own six contraction patterns, applied cleanly against the local D1 database, and the harness's exact-migration-list assertion extended to match.
- `emailThemeForStagedPayload()` in `lib/email/theme.ts` is the one place a stored `order_effects.payload` string may influence a rendered email's colours. It parses defensively (unparseable JSON, non-object JSON, a missing or non-string `themeName` field, and an absent payload entirely all silently fall back to the manifest default) and emits `theme.unknown_selection` exactly once, with no part of the stored string in the event, for the one genuinely anomalous case: a present, non-empty name that is not a manifest key.
- `stagePaidOrderEffects` resolves `getActiveTheme()` exactly once, only when the caller doesn't already supply a `themeName` — the sole call site in `lib/services/order-effects.ts` allowed to touch the active-theme resolver, since this function is only ever reached from a request context, never from the scheduled drain. `preparePaidOrderEffectStatements` serializes `{ themeName }` into the new `payload` column for the two email effect types only (`confirmation_email`, `merchant_notification`); the other four effect types bind `NULL`. The `ON CONFLICT DO NOTHING` clause means a re-stage never rewrites an already-staged row's payload.
- `CLAIM_SQL`'s `RETURNING` list and the `ClaimedOrderEffect` interface both carry `payload`; `executeEffect`'s `confirmation_email` and `merchant_notification` branches compute `emailThemeForStagedPayload(effect.payload)` and pass the result as a third argument into `sendOrderConfirmation`/`sendMerchantOrderNotification`, which forward it into the existing `tokens` override seam Plan 02 opened on the underlying senders.
- `lib/subscriptions/invoice-service.ts`'s two `preparePaidOrderEffectStatements` call sites (both inside async, request-scoped functions reached only from the Stripe webhook route) resolve the active theme themselves and pass it through as `themeName`, rather than adding a second theme-resolution path inside `order-effects.ts`.
- Integration coverage proves the theme survives staging to drain for a non-default theme, a `null` payload (the exact shape of a row staged before this migration) still renders the manifest default and completes successfully, an unknown stored theme name also degrades to the default without failing the drain, and re-staging never overwrites an already-staged row's theme.
- `lib/observability/scheduled.ts` and `worker.ts` are byte-identical to before this plan — verified by a `git diff --name-only` gate in Task 2's own `<verify>` command and reconfirmed against every commit in this plan's range.

## Decisions Made

- `emailThemeForStagedPayload()` performs its own `THEME_MANIFEST` membership check rather than relying solely on `getThemeTokens()`'s built-in unknown-name fallback, because it must distinguish "no payload at all" (the normal state for every row staged before this migration — no telemetry) from "a payload naming a theme the manifest doesn't recognize" (a genuine anomaly — telemetry required). `getThemeTokens()` alone cannot make that distinction; both cases look identical to it.
- `stagePaidOrderEffects` is the only call site in `lib/services/order-effects.ts` permitted to call `getActiveTheme()`, enforced by the plan's own occurrence-count verification gate (exactly 2: one import, one call). `invoice-service.ts`'s two call sites resolve the theme independently since they are already inside async, request-scoped functions — no second resolution path was added inside `order-effects.ts` itself.
- The staging INSERT's `payload` column is populated only for `confirmation_email` and `merchant_notification`; the other four effect types (`inventory`, `coupon`, `gift_card`, `subscription`) always bind `NULL`, matching the plan's must-haves precisely.
