# Phase 08.1 Plan 01: Theme tracer — active theme reaches the crash page via a public route Summary

**A shared request-scoped appearance read now backs both `getActiveTheme()` and `getLayoutSettings()`, and `app/global-error.tsx` repaints from the admin-selected theme after mount via a new public `GET /api/theme` route — proven end-to-end by tests and a live dev-server probe.**

## Performance

- **Duration:** 55 min
- **Tasks:** 3 completed
- **Files modified:** 9 (5 created, 4 modified) plus this SUMMARY and the VALIDATION status update

## Accomplishments

- `lib/themes/appearance-read.ts` gives `getActiveTheme()` and `getLayoutSettings()` a single request-scoped read of the `appearance` D1 category, wrapped in React's `cache()` — the one named, explained exception to the project's no-cross-request-cache guard.
- `app/api/theme/route.ts` is a public, unauthenticated, `force-dynamic` route returning exactly `{ name, tokens }` with `Cache-Control: no-store` — never a settings row, D1 record, or env value.
- `lib/themes/theme-response.ts`'s `parseThemeResponse()` resolves a response body's theme *name* through the caller's own bundled manifest, so a tampered or malformed body can never inject an arbitrary style value into the crash page (T-08.1-02).
- `app/global-error.tsx` now paints the manifest default first (unchanged first-paint behavior, zero flash-of-unstyled-content risk), then fetches `/api/theme` on mount and repaints with the real active theme; every failure path (network, non-2xx, malformed JSON, unrecognised theme) is swallowed silently.
- A live dev-server probe confirmed the whole chain works against a running server, not just mocks.

## Decisions Made

- **PROMOTE (assumption delta):** the active theme name is the one identity the crash page and the theme route care about; the manifest default is purely a fallback, never a competing identity. This resolved cleanly with no ambiguity in the route or parser design.
- `readAppearanceSettings()` and `APPEARANCE_SETTINGS_CATEGORY` were placed in the new `lib/themes/appearance-read.ts` (one of the two options CONTEXT.md left to discretion) rather than inlined into `active-theme.ts`, specifically to let `lib/layout/settings.ts` import the reader directly without adding a dependency edge onto `active-theme.ts` — `active-theme.ts` now depends on `appearance-read.ts`, not the reverse, avoiding any circular-import risk while `active-theme.ts` still re-exports the constant so no external import path changed.
- The dev-server probe used the existing development-only `x-dev-admin` bypass header (already used by the 06-04 probe method) rather than a real Clerk session — appropriate for a local-only verification step, never usable outside `NODE_ENV=development`.

## Live Dev-Server Probe (Task 3 evidence)

5. **After restore:** `GET /api/theme` → `name: "volt-dark"`, `tokens.primary: "#f97316"` — back to the starting body, byte-identical to step 1.
