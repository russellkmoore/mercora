This is plan 07's own visual QA coverage record, following the label/table format
`08-QA-MATRIX.md` established. Captured images live under the git-ignored `.screenshots/`
directory and are never committed — the order-status route depicts order contents (a

Scope: the `order-status` route only, captured under all seven shipped presets
(`volt-dark`, `luxe`, `midnight`, `clinical`, `retro`, `atelier`, `market`) at the single

order-status route renders none of the three layout-switch variants, so crossing it with
combinations B and C would add rows with no new information.

## Capture command

Every one of the seven runs uses this exact invocation, with all four flags:

```bash
mise exec -- npm run screenshot:routes -- \
  --label phase-08.1-a-<theme> \
  --manifest .planning/phases/08.1-v2-tech-debt-closure/08.1-SCREENSHOTS.md \
  --allow-missing \
  --include-content \
  --order-id "dev-order-001?token=<minted token>"
```

The `--manifest` flag is passed explicitly on every run, pointed at this file — the
harness's default manifest path points at
`.planning/phases/05-token-contract-component-sweep/05-SCREENSHOTS.md`, an earlier phase's
committed file, and relying on the default has already caused one real incident.

The fixture order id is the fixed, documented `dev-order-001` (`data/d1/seed-dev.sql`,
plan 07 Task 1). The bearer token is a signed, expiring, HMAC-SHA256 credential minted
once per capture session via `createOrderStatusToken(orderId)` and held only in a shell
variable — it is never written into this file, into `.env.local`'s committed state (the
file itself is git-ignored and confirmed untracked), or into any other record.

## Theme-switch method

A local `npm run dev` server runs against the existing local D1 fixture. Theme and all
three combination-A layout values are written in one request to `POST
/api/admin/settings`, using the documented `x-dev-admin` development-bypass header (its
value is read from `lib/auth/admin-middleware.ts` at run time — not written down here —
and the bypass is gated to the development environment only). Before every capture: the
appearance category is read back from the settings endpoint and all four written values
are confirmed, and the storefront root is fetched and its rendered `data-theme` attribute
is confirmed to match. Only after both confirmations does the harness run.

## Environment

The guest-link variables were appended to `.env.local` in one command that never read or
echoed the file (`>>`, generated with `openssl rand -hex 32`); `.env.local` is git-ignored
and `git status --porcelain` confirmed no diff. The token gate was confirmed working
(`/order-status/dev-order-001?token=<minted>` returned 200, not 404) before any capture
began.
