# Phase 8.1: v2 Tech-Debt Closure - Research

**Researched:** 2026-09-05
**Domain:** Next.js App Router / OpenNext-Cloudflare server-context plumbing, CI gates, test-fixture hygiene, D1 seed fixtures
**Confidence:** HIGH (every claim below is either read-this-session code, a runtime probe executed this session, or explicitly flagged `[ASSUMED]`)

## Summary

This phase closes nine narrowly-scoped tech-debt items (D-01..D-09) against a codebase that is
already fully built — there is no new library, no new architecture, only wiring existing pieces
together correctly. The highest-risk item is D-01: three of the six call chains for
theme-aware emails (`sendOrderConfirmation`/`sendMerchantOrderNotification`, invoked from
`lib/services/order-effects.ts`) can run from a **Cloudflare `scheduled()` cron handler that never
establishes OpenNext's request-scoped `AsyncLocalStorage` context** — calling `getActiveTheme()`
(which calls `getDbAsync()`) from that path will throw internally and silently fall back to the
default theme, not the admin-selected one, defeating D-01's stated goal for that one path. This is
verified this session by reading the actual generated `.open-next/worker.js`/`cloudflare/init.js`,
not inferred. Every other call site (webhook Route Handlers, admin Route Handlers) has full D1
context and is a straightforward parameter-threading change.

The second real finding is D-05: `resolveProductImageSrc` is **not** a drop-in replacement for
`getMediaUrl` — it inserts a leading `/` on a bare relative path and defaults to a different
placeholder filename (`.svg` vs `.jpg`). The existing parity-test fixture
(`getMediaUrl("products/x.jpg")` asserted to equal `"products/x.jpg"` verbatim, no leading slash)
would break under a literal swap. The `placeholder` argument covers the filename difference; the
leading-slash difference does not have a parameter escape hatch and must be resolved explicitly
(see Pitfall 2).

D-09's guest order-status page requires a **cryptographically signed, stateless bearer token**
(`?token=`) bound to the exact order id — it is not stored in D1, is not present by seeding a row,
requires `ORDER_STATUS_SECRET`/`ORDER_STATUS_GUEST_LINKS_ENABLED=true` configured locally (currently
unset — `.env.example` ships the flag `false`), and must be minted at capture time via
`createOrderStatusToken(orderId)`, not baked into `seed-dev.sql`.

D-03, D-04 (partially), D-06, D-07, D-08 are low-risk, mechanical changes with exact line-level
targets already identified by prior code reviews (06-REVIEW.md, 07-REVIEW.md, 08-REVIEW.md) — those
reviews double as a ready-made fix list; this research adds only the verification needed to plan
tasks around them safely.

**Primary recommendation:** Sequence the plan so D-01's cron-path risk is explicitly decided (see
Pitfall 1) before writing tasks for the six email builders, and treat D-05's leading-slash finding as
a blocking design question (see Pitfall 2), not a mechanical swap. Everything else is safe to plan
directly from the tables below.

### Pattern 1: Threading `ThemeTokens` into a pure builder (D-01)

**What:** Change each builder's HTML/text-generating function to accept `tokens: ThemeTokens` as a
parameter instead of calling `getThemeTokens()` internally; the call site resolves the theme.

**When to use:** Every one of the six builder files.

**Example (verified against actual current source, `lib/payments/refund-email.ts`):**
```typescript
// BEFORE — lib/payments/refund-email.ts:18-24 (read this session)
export async function sendRefundSettledEmail(
  input: RefundSettledEmailInput
): Promise<EmailResult> {
  if (!input.customerEmail) return { success: true };
  const store = getStoreConfig();
  const tokens = getThemeTokens();          // <- always default theme
  ...
}

// AFTER (shape only — planner decides exact helper name per "Claude's Discretion")
export async function sendRefundSettledEmail(
  input: RefundSettledEmailInput
): Promise<EmailResult> {
  if (!input.customerEmail) return { success: true };
  const store = getStoreConfig();
  const tokens = getThemeTokens(await getActiveTheme());   // call site now has D1 access
  ...
}
```
The call site for `sendRefundSettledEmail` is `app/api/webhooks/stripe/handlers/refund-handlers.ts`
[VERIFIED: grep this session, `refund-handlers.ts:349,386`] — a Route Handler with full ALS context,
so this is safe there. The same pattern applies to `sendSubscriptionLifecycleEmail`
(`subscription-handlers.ts:209`) and `sendReviewStatusNotification`/`sendReviewReminderEmail`
(called from `lib/models/reviews.ts`, itself invoked only from
`app/api/admin/reviews/reminders/route.ts` and admin review-moderation routes — all Route
Handlers). See Pitfall 1 for the one call chain (`drainOrderEffects` via cron) where this pattern
does **not** safely resolve the real active theme.


### Anti-Patterns to Avoid

- **Module-scope or `unstable_cache` memoization of the active theme:** already explicitly rejected
  by the milestone (06-RESEARCH.md, D-10) — Cloudflare isolate reuse would serve a stale theme after
  an admin save. `React.cache()` is the only sanctioned mechanism, and only because it is
  per-render-pass, not per-isolate (verified by runtime probe, see Pitfall 4).
- **Assuming `getCloudflareContext()` works anywhere `env` is reachable:** it does not — it reads an
  `AsyncLocalStorage` store that only the OpenNext-generated fetch handler populates. See Pitfall 1.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Order-status guest auth | A new token/session scheme for the local fixture | `createOrderStatusToken(orderId)` (already exists) | It is already a reviewed, tested, constant-time-compared HMAC scheme; inventing a second one for "just local testing" risks divergence and is unnecessary — the real function works locally once the two env vars are set |

explicit override parameter and have the cron caller pass `env.DB` down; if D-01 needs cron-path
correctness, that is the precedent to follow, not a new mechanism.

## Common Pitfalls

### Pitfall 1: `getActiveTheme()` throws (and silently degrades) when reached from the cron `scheduled()` handler

**What goes wrong:** CONTEXT.md's D-01 states the active theme should be resolved "in the server
context that already has D1 (webhook handlers, admin routes, **cron**)" — but the cron path does
**not** have working D1 access via `getDbAsync()`/`getActiveTheme()`.

**Why it happens (verified this session, not inferred):**
- `worker.ts`'s `scheduled()` export calls `handleScheduled(controller, env, ctx)` directly
  [VERIFIED: `worker.ts:22-28`, read this session].
- `handleScheduled` calls `drainOrderEffects({ database: env.DB, ... })`
  [VERIFIED: `lib/observability/scheduled.ts:34`, read this session] — note it passes `env.DB`
  explicitly as a raw `D1Database`, not via `getDbAsync()`.
- `drainOrderEffects` → `executeEffect` → for `effect_type: 'confirmation_email'` /
  `'merchant_notification'`, calls `sendOrderConfirmation`/`sendMerchantOrderNotification`
  [VERIFIED: `lib/services/order-effects.ts:283,290`, read this session] which import from
  `lib/services/order-confirmation.ts`, whose `resolveOrderLineImages()` **unconditionally** calls
  `getDbAsync()` [VERIFIED: `lib/services/order-confirmation.ts:35-46`, read this session] with no
  override parameter — unlike its sibling functions in the same codebase
  (`runPaidOrderInventoryEffect(order, { database, now })`,
  `fulfillPaidGiftCards(order, { environment })`) which explicitly accept and prefer a passed-in
  environment over calling `getCloudflareContext()`.
- `getDbAsync()` is `React.cache(async () => { const { env } = await getCloudflareContext({ async:
  true }); ... })` [VERIFIED: `lib/db.ts:72-75`].
- `getCloudflareContext({ async: true })` reads `cloudflareContextALS.getStore()` — an
  `AsyncLocalStorage` instance that is populated **only** by
  `runWithCloudflareRequestContext(request, env, ctx, handler)`
  [VERIFIED: `.open-next/worker.js` / `.open-next/cloudflare/init.js`, read this session — exact
  quote: `const cloudflareContextALS = new AsyncLocalStorage(); ... export async function
  runWithCloudflareRequestContext(request, env, ctx, handler) { init(request, env); return
  cloudflareContextALS.run({ env, ctx, cf: request.cf }, handler); }`]. This function is called only
  from the generated `fetch()` handler [VERIFIED: `.open-next/worker.js:17`,
  `return runWithCloudflareRequestContext(request, env, ctx, async () => {`]. `worker.ts`'s
  `scheduled()` export never calls it.
- Therefore, inside the cron path, `getCloudflareContext({ async: true })` finds no ALS store, is
  not in the Node.js dev-server runtime, and throws (per its own source:
  `throw new Error(initOpenNextCloudflareForDevErrorMsg)`).
- `resolveOrderLineImages()`'s own `try { ... } catch { return new Map(); }` (pre-existing, not
  introduced by this phase) swallows that throw silently — meaning this is **already** a latent gap
  in shipped code (cron-triggered confirmation emails already lose product images silently). If
  `getActiveTheme()` is added to this same call chain, its own internal `try { ... } catch { return
  resolveEnvOrManifestDefault(...); }` [VERIFIED: `lib/themes/active-theme.ts:56-61`] will likewise
  swallow the throw and silently return the **default** theme, not the admin-selected one, for any
  email sent via the cron recovery-queue retry path (as opposed to the synchronous, request-scoped
  retry that fires immediately after checkout via
  `app/api/webhooks/stripe/route.ts`/`app/api/orders/route.ts`/`app/api/payment-intent/route.ts`,
  which **do** have working D1 access — confirmed these three files all import `getDbAsync` directly
  [VERIFIED: `lib/services/order-finalization.ts:1`, whose only callers are those three route
  files]).

**Scope of the gap:** only the every-5-minutes recovery sweep (`handleScheduled`'s
`'*/5 * * * *'` branch, unqualified `drainOrderEffects` with no `orderId`) is affected — this only
fires for an order-confirmation or merchant-notification effect that failed on its first,
synchronous, request-scoped attempt and is being retried. The common path (send at checkout
completion) is unaffected.

**How to avoid / recommendation for the planner:** this is a genuine product decision CONTEXT.md
did not anticipate, not a bug to silently code around. Two honest options, either is defensible:
1. **Accept the gap, document it.** The cron retry path already degrades gracefully (never throws,
   never breaks the retry), it just uses the default theme for that one retry path. Low severity,
   consistent with the existing "never throws" contract. Recommended default given the low
   frequency and the fact the correct-path is unaffected — but flag as a known limitation in the
   phase's own doc update, the same way the milestone tracked "emails always use default theme" as
   accepted debt before this phase existed.
2. **Thread `env.DB` through.** Give `getActiveTheme()`/`getSettings()` (or a new theme-resolution
   helper) an optional D1Database/drizzle-instance override, mirroring
   `runPaidOrderInventoryEffect`'s pattern, and have `handleScheduled` pass `env.DB` down through
   `drainOrderEffects` → `executeEffect` → the send functions. This is a real, larger refactor
   touching `OrderEffectRuntime`'s shape and every function in the chain — likely out of proportion
   for this phase's stated "code-closable tech debt" scope, but should be surfaced to Russell as an
   explicit choice rather than silently picking option 1.

**Warning signs:** a test asserting `getActiveTheme()` resolves the *stored* theme when invoked with
a mocked cron-style `database` parameter and no ALS context would fail if option 1 is silently
assumed to "just work" the way CONTEXT.md's D-01 wording implies.

### Pitfall 2: `resolveProductImageSrc` is not byte-identical to `getMediaUrl` for a bare relative path

**What goes wrong:** D-05 requires "byte-identical" output for the `left` gallery's existing
fixtures. The two functions diverge in two ways confirmed against actual test assertions.

**Why it happens:**
- `getMediaUrl("products/x.jpg")` is asserted to return `"products/x.jpg"` verbatim (no leading
  slash) [VERIFIED: `tests/unit/components/layout/product/product-gallery-variants.test.ts:38`,
  read this session].
- `resolveProductImageSrc(primaryImage, media, placeholder)`'s own logic is: `if
  (/^https?:\/\//i.test(url) || url.startsWith('/')) return url; return \`/${url}\`;`
  [VERIFIED: `lib/utils/product-image.ts:105-106`, read this session] — a bare relative path
  without a leading slash gets one **inserted**. `resolveProductImageSrc("products/x.jpg")` would
  return `"/products/x.jpg"`, not `"products/x.jpg"` — breaking the byte-identical fixture
  assertion above if that exact call pattern is substituted verbatim.
- Separately, the default placeholder differs: `getMediaUrl`'s fallback is `"/placeholder.jpg"`
  [VERIFIED: same test file, line 33-34] vs. `resolveProductImageSrc`'s default third parameter
  `'/placeholder.svg'` [VERIFIED: `lib/utils/product-image.ts:101`]. This part **is** fixable — pass
  `'/placeholder.jpg'` explicitly as the third argument at both gallery call sites.
- A further signature mismatch: `getMediaUrl(media: any)` is called with a single, **already
  resolved plain string** at both gallery call sites (`getMediaUrl(selectedImage)`,
  `getMediaUrl(imageUrl)` where both come from `allImages: string[]`)
  [VERIFIED: `components/layout/product/ProductGalleryLeft.tsx:43,63`,
  `ProductGalleryTop.tsx:42,62`, read this session]. `allImages` itself is built by
  `ProductDisplay.tsx`'s own inline `useMemo`, which extracts `item.url || item.file?.url` itself
  and does **not** call either `getMediaUrl` or `resolveProductImageSrc`
  [VERIFIED: `app/product/[slug]/ProductDisplay.tsx:141-159`, read this session]. So in production,
  `getMediaUrl`'s only live branches (given the call pattern) are the falsy-input placeholder branch
  and the string-passthrough branch — the object-shape-handling code in `getMediaUrl` is
  unreachable dead code under the real call pattern, while `resolveProductImageSrc(primaryImage,
  media)` expects the *raw*, unresolved two-value shape (`primary_image` object + `media` array),
  not a single pre-resolved string. Swapping the call means passing the single string as
  `primaryImage` with no `media` argument, which still resolves correctly via
  `urlFromImageRecord`'s string branch — it is the leading-slash behavior above that is the actual
  blocker, not this shape difference.

**How to avoid:** before writing the D-05 task, check whether the actual parity-test fixture data
(`tests/unit/components/layout/product/product-gallery-variants.test.ts` and any category/home
fixtures reused for the product gallery) contains any bare relative path lacking both `http(s)://`
and a leading `/`. If yes — which is confirmed true for at least the `"products/x.jpg"` /
`"products/y.jpg"` fixtures in the existing test file — a literal drop-in swap changes output and
violates the "byte-identical" requirement as literally stated. Recommended resolution: either (a)

### Pitfall 3: The order-status guest token is not a seedable value

**What goes wrong:** A plan that just inserts an `orders` row and expects `/order-status/<id>` to
render will 404, because the page requires a `?token=` query parameter verified via
cryptographic HMAC, and 404s before the first database read if it is absent
[VERIFIED: `app/order-status/[id]/page.tsx:46-56`, read this session — `if (!token) notFound();`
appears before `verifyOrderStatusToken`, which itself appears before `getOrderById`].

**Why it happens:** `lib/order-status/token.ts` implements a stateless, expiring, HMAC-SHA256-signed
bearer token (`base64url(payload).base64url(HMAC)`) [VERIFIED: `lib/order-status/token.ts:1-18,
126-152`, read this session]. It requires two env vars neither of which is currently set locally:
`ORDER_STATUS_GUEST_LINKS_ENABLED` (must be `"true"`, not merely present) and `ORDER_STATUS_SECRET`
(must be ≥32 characters and not equal to the placeholder string). `.env.example` documents both with
the generation command `openssl rand -hex 32` and ships `ORDER_STATUS_GUEST_LINKS_ENABLED=false`
[VERIFIED: `.env.example:11-14`, read this session]. No `.dev.vars` file exists in the repo
[checked this session — `ls .dev.vars*` found nothing], and `.dev.vars*` is gitignored
[VERIFIED: `.gitignore:44`], so a local-only secret can be added safely without ever being committed.
`.env.local` exists but its contents could not be read this session (permission denied — treat as
containing live secrets; do not assume its contents).

**How to avoid:**
1. The seed fixture only needs a valid `orders` row (see Standard Stack / schema below) — no token
   column exists on that table, and none should be added.
2. Locally, set `ORDER_STATUS_GUEST_LINKS_ENABLED=true` and a real
   `ORDER_STATUS_SECRET` (32+ chars) in `.env.local` (Next.js env, read via `process.env` in both
   `next dev` and the deployed Worker per `nodejs_compat_populate_process_env`) — this is a
   local-machine action, not something the plan's code changes can automate, since `.env.local`
   content is out of scope for a Write/Edit tool call to a file whose contents are unknown and which
   may already hold real secrets. Flag this as a `checkpoint:human-verify`-style manual step in the
   plan (or a `.env.example`-adjacent doc note), not a task the executor silently completes.
3. At screenshot-capture time, mint the token by importing `createOrderStatusToken(orderId)`
   (or writing a tiny throwaway Node script that inlines the same HMAC logic against the same env
   vars) and pass the full `<orderId>?token=<token>` string as `--order-id`'s value —
   `screenphot-routes.mjs` string-concatenates `--order-id`'s value directly into
   `` `/order-status/${orderId}` `` before wrapping it in `new URL(...)`
   [VERIFIED: `scripts/screenshot-routes.mjs:124-125`, read this session], so a value containing
   `?token=...` flows through correctly with no script changes required, since `new URL()` will
   parse the query string out of the interpolated path.
4. Default token TTL is 7 days (`DEFAULT_ORDER_STATUS_TTL_SECONDS`); minting fresh at capture time
   avoids any staleness concern.

### Pitfall 4: `React.cache()` provides zero memoization outside an active render — verified by a live runtime probe, not assumed

**What goes wrong:** A plan might assume `React.cache()`-wrapping `readAppearanceSettings()` will
break the existing `active-theme.test.ts` assertion that two independent `await getActiveTheme()`
calls each trigger their own `getSettings()` call (no cross-call memoization)
[VERIFIED: `tests/unit/lib/themes/active-theme.test.ts:167-178`, read this session — asserts
`expect(mocks.getSettings).toHaveBeenCalledTimes(2)` after two sequential `getActiveTheme()` calls
with different mocked results].

**Why it does not actually break:** this session ran a direct probe of the project's installed
`react` package:
```
node -e "
const { cache } = require('react');
let calls = 0;
const fn = cache((x) => { calls++; return { x, calls }; });
console.log(JSON.stringify(fn(1)));
console.log(JSON.stringify(fn(1)));
console.log(JSON.stringify(fn(2)));
console.log('total calls', calls);
"
```
Output:
```
{"x":1,"calls":1}
{"x":1,"calls":2}
{"x":2,"calls":3}
total calls 3
```
`fn(1)` called twice back-to-back produced two separate executions (`calls` incremented both
times), not a cached hit — `React.cache()` outside of an active React render/request dispatcher is a
pure passthrough with **no** memoization [VERIFIED: live `node` probe against this project's
`react` dependency, executed this session]. Vitest unit tests run entirely outside any React render
pass, so `readAppearanceSettings()` wrapped in `React.cache()` will behave identically to an
unwrapped function under test — the existing test suites for `active-theme.test.ts` and
`layout/settings.test.ts` (which both mock `@/lib/utils/settings`'s `getSettings` directly and
assert exact call counts) should continue to pass unmodified.

**Corollary — where the caching *does* engage:** `getDbAsync()` is already `React.cache()`-wrapped
and already used from Route Handlers project-wide with no reported staleness issues (06-RESEARCH.md,
07-RESEARCH.md both concluded this is safe), which by direct analogy means Next.js's render/Route
Handler execution does install a working cache-dispatcher scope for real requests — the caching is
real in production, absent (safely, as a no-op) in unit tests. This is the same mechanism `getDbAsync` already relies on; D-04 introduces no new risk class.

**Warning signs:** if a future test asserts `readAppearanceSettings()` IS memoized within a single
test (e.g. two calls inside one `it()` block expecting only one underlying `getSettings` call),
that assertion would fail in the test environment even though the real request-scoped behavior is
correct — do not write such a test; the module's own comment should say why (mirroring `getDbAsync`'s docstring).

### Pitfall 5: Existing token-assertion email tests call builders with no `tokens` argument today

**What goes wrong:** `tests/unit/lib/utils/order-status-email-tokens.test.ts` currently calls
`generateOrderStatusUpdateHTML({ ...base, status })` with no tokens argument and separately calls

**How to avoid:** treat "update every existing test call site for the six builders" as an explicit,
