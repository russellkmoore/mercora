**Every request-scoped transactional email path (order confirmation, status update, shipping, refund, subscription lifecycle, review notifications) now resolves the admin-selected theme once at send time instead of always rendering the manifest default — proven by a test that stubs luxe and asserts its colours reach the HTML while the default's do not.**

## Accomplishments

- `lib/email/theme.ts` gives the email layer one send-time theme resolver, `resolveEmailTheme()` — awaits `getActiveTheme()` and returns that name's manifest tokens, inheriting the "never throws" contract transitively from the resolvers it composes.
- `lib/email/footer.ts`'s `postalFooterHtml`/`unsubscribeFooterHtml` take a required tokens parameter instead of resolving their own theme; the module no longer imports the token lookup (or its type) at all.
- `lib/utils/email.ts`'s two pure generators (`generateOrderConfirmationHTML`, `generateOrderStatusUpdateHTML`) take `tokens: ThemeTokens` as a parameter; all three async senders (`sendOrderConfirmationEmail`, `sendOrderStatusUpdateEmail`, `sendNewOrderMerchantNotification`) resolve the theme once via `resolveEmailTheme()`, with the two order senders accepting an optional `options.tokens` override for Plan 04's cron-drain seam.
- `lib/fulfillment/shipping-email.ts`, `lib/payments/refund-email.ts`, `lib/subscriptions/lifecycle-email.ts`, and `lib/utils/review-notifications.ts` follow the same pattern — the pure builder takes tokens, the async sender resolves it. `sendReviewReminderEmail` gained theme resolution it had never had.
- A stored non-default theme (luxe) is proven to reach the rendered email HTML through the async sender end to end, the adjacency case (stored-default vs. nothing-stored) is byte-identical, both footer helpers are proven against two different presets, and every manifest preset's token set is proven to carry all 23 keys.
- No call site outside the six builder files changed — the webhook handlers, admin order routes, and `lib/models/reviews.ts` are untouched (verified by a git-diff scope gate in the task's own `<verify>`).

## Decisions Made

- `lib/email/footer.ts`'s `tokens` parameter is typed as a minimal local `FooterTokens` (`{ mutedOnInverse: string }`) rather than the plan's literal `ThemeTokens` wording, because the plan's own `<verify>` command for this task greps the whole file for the string `themes/tokens` and fails on any import from that module — including a type-only one. Every real caller passes a full `ThemeTokens` object, which satisfies this narrower structural type, so no caller needed a change.
- The two order senders' `options.tokens` override (already specified by the plan for Plan 04's benefit) required no additional design — `options.tokens ?? await resolveEmailTheme()` mirrors the codebase's existing explicit-override precedent named in the plan (`runPaidOrderInventoryEffect(order, { database, now })`).

**1. [Rule 3 - Blocking] `lib/email/footer.ts`'s tokens parameter uses a local structural type instead of importing `ThemeTokens`**
- **Found during:** Task 2, while verifying the task's own automated `<verify>` command
- **Issue:** The plan's action text says to give the footer helpers a `tokens: ThemeTokens` parameter, but the same task's `<verify>` command asserts `! grep -q 'themes/tokens' lib/email/footer.ts` — a plain string match that a type-only `import type { ThemeTokens } from "@/lib/themes/tokens"` would also trigger, since the module specifier itself contains that substring.
