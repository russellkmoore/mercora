# Phase 8.1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase has exactly **two UI surfaces**, both governed by D-01/D-02 (08.1-CONTEXT.md): make an existing rendered surface follow the admin-selected theme instead of the hardcoded default. **No new components, no new layouts, no new copy.** Every other surface in the app (admin, storefront, drawers, Stripe, Clerk) is unchanged — see Phase 6/6.1/7 UI-SPECs for those contracts, which this document does not restate or supersede.

1. **`app/global-error.tsx`** — a client component rendered *without* the root layout (no `globals.css`, no theme-cascade `[data-theme]` attribute reaches it). Today it calls `getThemeTokens()` with no argument (always `volt-dark`). D-02 adds a two-paint sequence: manifest default first, then the active theme's tokens once `GET /api/theme` resolves on mount.
2. **Transactional emails** (six builders in D-01) — already token-driven per Phase 5 D-10/D-13, but every call site passes no theme name, so `getThemeTokens()` silently defaults to `volt-dark` regardless of the admin's selection. D-01 makes the call sites theme-aware; the *token-to-role mapping itself does not change*.

Neither surface introduces a new visual element, a new copy string, or a new interaction. This spec's job is to pin down the **two-state sequence** (global-error) and the **per-preset contrast floor** (both surfaces) so the executor doesn't have to eyeball seven themes to know if text is still readable.

## Color

Both surfaces already use the frozen 23-token contract (Phase 5 D-01/D-09/D-10/D-13) for every color decision. D-01/D-02 change *which theme's values* populate those tokens at render/send time — the role-to-token mapping is unchanged and is restated here only for completeness, not as new decisions.

### `global-error.tsx` token-to-role mapping (unchanged, Phase 5 D-13)

| Role | Token | Usage |
|------|-------|-------|
| Dominant (60%) | `surfaceElevated` | `<body>` background |
| Foreground text | `foreground` | Body text color (`<body>` default, inherited by `<h1>`), "Go home" link text |
| Muted text | `mutedForeground` | Paragraph under the heading |
| Accent (10%, CTA) | `primary` background / `onPrimary` text | "Try again" button — the only accent use on this page |
| Secondary boundary | `border` | "Go home" link's 1px outline (decorative, non-text) |

Accent reserved for: the "Try again" button only. The "Go home" link is a bordered outline in `foreground`/`border`, not accent-colored — this is the existing pattern and D-02 does not change it.

### Email token-to-role mapping (unchanged, Phase 5 D-10, confirmed by 08.1 D-01)

| Role | Token | Usage |
|------|-------|-------|
| Page background | `surfaceInverse` | Outer email body background |
| Card background | `surfaceInverseElevated` | Content card/panel background |
| Body text | `onInverse` | Primary email copy |

### Per-preset contrast floor — all 7 presets, both surfaces

D-02 explicitly requires the crash page (and by the same logic, D-01's emails, which share the `primary`/`onPrimary` pair) to hold contrast under **every** preset, not just `volt-dark`. Computed with the WCAG 2 relative-luminance formula directly from `lib/themes/manifest.generated.ts` values (not eyeballed):

| Preset | `foreground` on `surfaceElevated` | `mutedForeground` on `surfaceElevated` | `onPrimary` on `primary` (button, both surfaces) | `onInverse` on `surfaceInverse` (email body) | `mutedOnInverse` on `surfaceInverse` (email footer) |
|--------|:--:|:--:|:--:|:--:|:--:|
| atelier | 15.87:1 | 5.81:1 | 4.64:1 | 17.72:1 | 5.48:1 |
| clinical | 13.63:1 | 4.54:1 | 4.61:1 | 19.90:1 | 5.48:1 |
| luxe | 18.20:1 | 6.35:1 | 7.53:1 | 18.29:1 | 5.47:1 |
| market | 15.86:1 | 5.91:1 | 4.63:1 | 18.78:1 | 5.49:1 |
| midnight | 15.15:1 | 5.74:1 | 6.60:1 | 17.62:1 | 4.52:1 |
| retro | 13.40:1 | 6.67:1 | 8.98:1 | 16.10:1 | 4.44:1 |
| volt-dark (default/manifest first-paint) | 17.93:1 | 7.11:1 | 7.49:1 | 20.62:1 | 4.75:1 |

**All 35 cells clear WCAG AA (4.5:1 normal text)** — the tightest is `onPrimary`/`primary` at 4.61–4.64:1 (atelier, clinical, market), still a pass with no margin to spare. This is a **contract, not just an observation**: if a future preset is added to the manifest whose `onPrimary`/`primary` pair falls under 4.5:1, that preset fails this page and the emails identically (same token pair, same rule) — the Phase 6 preset-author process should re-run this check, not just the admin-page contrast check.

**Flagged assumption (autonomous run, not blocking):** the "Go home" link's `border`-color outline measures 1.19–1.73:1 against `surfaceElevated` across all 7 presets — well under the 3:1 non-text-UI-component threshold. This matches the sitewide `border` token's established role as a deliberately faint hairline divider (Phase 6's own Midnight rationale: "~1.4:1... to match the doc's own faint gradient border" direction), so it is **not a regression introduced by this phase** — the link's affordance is carried by its `foreground`-colored text (13.4–18.2:1, always legible) and its clickable padding, not the border. Recorded here so the D-09 screenshot capture (all 7 themes) doesn't mistake it for a new defect.

## UI Considerations

Probe authored directly from the CONTEXT scope notes over 3 elements: E1 = `global-error.tsx` page (static-content + interactive-control, two-element action row), E2 = `GET /api/theme` (data surface consumed by E1), E3 = the six email builders (static-content, per-send). Autonomous run — AskUserQuestion not invoked; judgement calls below are flagged as assumptions, not silent decisions.

Applicable state considerations resolved: 9 covered, 1 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| loading | E1 page | ✅ covered | First paint uses `getThemeTokens()` with no argument (manifest default, `volt-dark`) — identical to today's behavior, zero flash-of-unstyled-content risk since there is no async gate before first paint (D-02: "renders with the manifest default first") |
| loading→populated transition | E1 page | ✅ covered | On mount, `fetch('/api/theme')` resolves and the component re-renders with the returned theme's tokens. Colors only change — no element moves, resizes, or reflows (same fixed padding/gap values throughout), so this is **not a layout shift**, only a color swap. If the active theme equals the manifest default (`volt-dark` is itself the active theme), the re-render is a no-op repaint, not visually detectable |
| error | E1 page (fetch failure) | ✅ covered | `/api/theme` unreachable, non-200, or malformed JSON → the component simply never calls its state-setter for the fetched tokens and stays on the manifest default. No error banner, no retry-the-fetch UI — the page's own "Try again" button already exists for the *actual* crash the user is looking at; a themeing failure must never block or clutter the crash-recovery UI (D-02 intent) |
| error | E2 `/api/theme` | ✅ covered | Route always returns 200 with `{ name, tokens }` for whatever `getActiveTheme()` resolves to; `getActiveTheme()`'s own fallback-to-default behavior (established Phase 6) means the route itself cannot represent a "themed but broken" state — worst case it returns the default theme's data, which is indistinguishable from E1's own first-paint default |
| empty | E2 `/api/theme` | ✅ covered | Cannot return an empty body — `getThemeTokens()` throws if `THEME_MANIFEST` is empty (a build-time guarantee per `lib/themes/tokens.ts`), so the route either returns valid theme data or the whole Worker fails to build; there is no "manifest resolved but is empty" runtime state to design for |
| long-text | E1 page (crash body/heading) | ✅ covered | Fixed, non-interpolated copy (see Copywriting Contract) — no user data or variable-length string ever renders on this page, so no wrap/clamp/truncate decision applies |
| long-text | E1 page (error digest) | 🧪 backstop | { statement: "If a future change surfaces `error.digest` in the rendered markup, it must wrap (not overflow) inside the fixed-width `main` container, matching the existing `maxWidth: 28rem` paragraph treatment", verification: backstop } — not applicable today (current markup never renders `digest`, confirmed by reading the file: the `error` prop's `digest` field is accepted in the type but never interpolated into JSX); flagged only because the CONTEXT scope note explicitly calls out "long-text = error digest wraps" as a consideration to cover |
| overflow | E1 page (button row) | ✅ covered | `display: flex, gap: 0.75rem` with no fixed width — two buttons wrap naturally on narrow viewports via normal flex behavior (unchanged; not modified by this phase) |
| zero-one-many | E2 `/api/theme` | ✅ covered | Not applicable by shape — the route returns exactly one theme (the active one), never a collection; no zero/one/many state exists |
| partial | E3 emails | ✅ covered | Not applicable by shape — `getThemeTokens(name)` is a synchronous manifest lookup that always returns the full 23-token object or throws (never a partial token set); a builder either has a complete theme or the call itself fails loudly upstream |
| resolution-source ambiguity | E3 emails (D-01) | ✅ covered | All six builders resolve the theme once, server-side, in the caller that already has D1 access (webhook handlers, admin routes, cron) — never inside the pure builder functions themselves. If `getActiveTheme()` itself fails (D1 unreachable), that failure surfaces through the *existing* error handling of whichever webhook/route/cron job triggered the send (unchanged plumbing) — this phase does not add a new failure mode, it removes the current silent-default one |
