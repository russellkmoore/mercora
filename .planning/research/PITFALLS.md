# Pitfalls Research

**Domain:** Retrofitting a CSS design-token contract + runtime theme switching + layout variants onto a live Next.js App Router commerce storefront (Voltique, on Cloudflare Workers via OpenNext, Tailwind v4, D1)
**Researched:** 2026-09-02
**Confidence:** HIGH (codebase-verified findings) / MEDIUM (general Next.js + Tailwind v4 + Cloudflare platform behavior)

## Codebase facts that shape every pitfall below

Verified directly in the repo, not assumed:

- `app/layout.tsx` stamps theme CSS variables inline on `<body>` from `getStoreConfig().theme`, which is **synchronous today** (`lib/store-config.ts:482`, no `async`). The milestone's `getActiveTheme()` adds a D1 read here — this is a new blocking I/O call in the single most-requested code path in the app.
- The root layout already declares `export const dynamic = "force-dynamic"` and `suppressHydrationWarning` on `<html>`, `<body>`, and `<main>`. The app does not use ISR or static rendering anywhere in the storefront — every request already re-renders server-side. This removes the classic "stale cached theme from ISR" failure mode, but does nothing for D1 latency or cold-start cost.
- `tailwind.config.ts` already maps every `store.*` color through a custom `runtimeColor()` helper: `rgb(from var(--store-primary) r g b / <alpha-value>)`. This is CSS Relative Color Syntax, not Tailwind's old `rgba(var(--x), <alpha-value>)` triplet trick — it works with hex, rgb, or any valid CSS color stored in the variable. Two hardcoded exceptions survive outside that helper: `border: "#2a2a2a"` and `ring: "#333333"` are literal hex, not tokens.
- 85 files under `app/` and `components/` still contain hardcoded dark-palette classes (`neutral-800`, `neutral-900`, `text-white`, `bg-black`, `gray-300`, `gray-800`). `components/checkout` alone has 6, `components/cart` has 2, `app/checkout` has 2 — all inside the milestone owner's explicitly named regression-sensitive surfaces.
- `app/layout.tsx:170` hardcodes `bg-(--store-primary)/80 text-black` on the promotional banner — an assumption that `primary` is always light enough for black text to read. There is no `on-primary` token today; the milestone's token contract adds one specifically because of cases like this.
- `components/checkout/OrderConfirmationModal.tsx` hardcodes `bg-white` on a modal in an otherwise all-dark component tree — currently reads as an intentional light card floating on dark chrome. Under a light theme it becomes a white card on a white-ish page: same class, invisible contrast.
- Several shadcn/ui-style components (`components/ui/dialog.tsx`, `sheet.tsx`, `dropdown-menu.tsx`, `alert-dialog.tsx`) reference `bg-background`, `text-popover-foreground`, `bg-popover` classes. `--popover` is not defined anywhere in `app/globals.css` or `tailwind.config.ts` — these classes currently resolve to nothing. They will look like "already tokenized" code during the sweep but are dead CSS, not wired to the theme system at all.
- `package.json` has no `prebuild` script today, and the two bundlers diverge: `dev` runs `next dev --turbopack`, `build` runs `next build --webpack`. Neither is the actual deploy entrypoint — `deploy` and `deploy:ci` call `build:worker`, which runs `node scripts/build-with-public-env.mjs ./node_modules/.bin/opennextjs-cloudflare build`, a **differently-named script**. A `predev` hook already exists and works (`scripts/db-local-ensure.mjs`).

## Critical Pitfalls

### Pitfall 1: A script named `prebuild` never runs before the real deploy build

**What goes wrong:**
The theme-scan script is added as `"prebuild": "node scripts/build-themes.mjs"`, tested locally with `npm run build`, confirmed working, and shipped. It never runs in CI or on deploy, because the actual pipeline calls `build:worker`, not `build`. Invalid or stale theme files reach production; the manifest is whatever was last generated by a developer's local `npm run build`.

**Why it happens:**
npm's automatic pre/post script convention only matches by exact script name — `prebuild` fires before `build`, not before `build:worker`. This repo's deploy path is `deploy` → `build:worker` → `build-with-public-env.mjs` → `opennextjs-cloudflare build`. `npm run build` (plain) is a dead end that nothing in the deploy chain calls. This is easy to miss because `npm run build` succeeds and looks like the right verification step.

**How to avoid:**
Do not rely on the `pre`-prefix convention. Call `scripts/build-themes.mjs` explicitly as the first step inside `build:worker` (and inside `predev`, next to the existing `db-local-ensure.mjs` call, for local dev). Verify by temporarily breaking a theme file and running `npm run deploy:ci` (or `build:worker` alone) — the build should fail, not just `npm run build`.

**Warning signs:**
Theme validation errors never appear in CI logs; `npm run build` is used as the acceptance test for the phase instead of `build:worker`/`deploy:ci`.

**Phase to address:**
Phase B (theme file mechanism) — wire the script into `build:worker` and `predev` directly, not via a `pre*` npm hook name.

### Pitfall 2: The D1 theme read becomes a synchronous tax on every request, or gets accidentally cached

**What goes wrong:**
`getActiveTheme()` reads `admin_settings` from D1 on every request in the root layout, which runs for every page in the app (there is no per-route opt-out — layout is shared). Two opposite failure modes both happen in practice: (a) latency — a D1 round trip is added to the server response for every single request, including ones that don't touch commerce logic at all, and it's on the request's critical rendering path since it's not wrapped in Suspense (it can't be, without causing a flash — see Pitfall 3); (b) an over-eager fix for (a) introduces caching (KV, in-memory, `unstable_cache`, a module-level variable) that then serves a stale theme after an admin switches it in the Appearance UI, contradicting the milestone's stated goal that "switching between shipped themes is instant via D1."

**Why it happens:**
`export const dynamic = "force-dynamic"` already means every request is a fresh render — there's no ISR safety net doing this for free, and no existing pattern in the codebase for a fast admin-settings read (the existing `admin_settings` reads for the promotional banner already pay this same cost, so precedent exists, but adding a second D1 read to the same hot path compounds it). On Cloudflare Workers specifically, a module-scope cache variable is **not safe** across requests the way it would be on a long-lived Node server — isolates are reused unpredictably and can be evicted at any time, so an in-memory cache gives inconsistent staleness rather than a real fix.

**How to avoid:**
Accept the per-request D1 read as designed (this is the milestone's own explicit decision — "revisit only if traces show it"). If latency becomes a real, measured problem, the correct lever is D1 itself (a narrow, indexed lookup on a single-row key, not a broader settings scan) or Cloudflare's edge cache with a short, explicit TTL plus deliberate purge-on-write from the admin Appearance save action — not an ad hoc in-isolate cache. Do not reach for `unstable_cache` or a module-level variable as a quick fix.

**Warning signs:**
An admin changes the theme and the storefront doesn't update on the next request; a module-level `let cachedTheme` or similar appears anywhere near `getActiveTheme()`.

**Phase to address:**
Phase B (theme file mechanism) — this is exactly what `getActiveTheme()` is being built to do; the trap is "optimizing" it later without re-reading the milestone's own decision log.

### Pitfall 3: Wrapping the theme read in Suspense reintroduces the flash the server-stamped approach was chosen to avoid

**What goes wrong:**
A developer, worried about Pitfall 2's latency, moves the D1 `getActiveTheme()` call into a Suspense boundary or a streamed child component "to not block the shell." Next.js on Cloudflare (via OpenNext) then streams an initial HTML shell with a default or missing `data-theme` attribute, followed later by the real value — a visible flash from the fallback theme to the real one, exactly the FOUC problem a server-stamped `data-theme` was supposed to eliminate. This is worse than a client-side flash in some ways because it looks "fixed" in every manual test on a fast connection and only shows up under real network/edge latency.

**Why it happens:**
Suspense-and-stream is the generically "correct" Next.js performance pattern, so it's a natural reflex — but it's wrong here specifically because `data-theme` has to be present on the initial HTML for CSS to apply the right theme block before first paint. Anything the browser paints before the Suspense boundary resolves paints in the wrong (or no) theme.

**How to avoid:**
Keep the `getActiveTheme()` D1 read blocking, in the root layout, above any Suspense boundary, exactly where `getStoreConfig()` is called today. The milestone already treats `force-dynamic` + a blocking layout read as the intended trade (latency for correctness). Do not introduce partial prerendering, `loading.tsx` at the root, or a client-side `useEffect` fallback for theme.

**Warning signs:**
A brief flash of the default/fallback theme visible on slow connections or in Chrome DevTools network throttling; `data-theme` missing from the server-rendered HTML `<html>` tag in "View Source."

**Phase to address:**
Phase B (theme file mechanism) — encode this as an explicit constraint in the plan, not just an implementation detail, since the temptation to "fix" latency with streaming will recur.

### Pitfall 4: The sweep declares victory on component files and misses hardcodes in Tailwind's own config, third-party UI primitives, and inline styles

**What goes wrong:**
A grep-and-replace sweep targets `app/**` and `components/**` for `neutral-*`/`gray-*`/`text-white` classes and stops there. It misses: (a) the two literal hex values already sitting in `tailwind.config.ts` (`border: "#2a2a2a"`, `ring: "#333333"`) — these aren't `className` strings, so a `className`-focused grep or codemod skips them entirely; (b) shadcn/ui-style primitives that reference undefined tokens like `bg-popover` (Pitfall 6) which look tokenized but aren't real; (c) inline `style={{ }}` props and CSS-in-JS-like patterns (the same pattern used in `layout.tsx` today) that don't show up in a `className` search; (d) SVG `fill`/`stroke` attributes and inline `<style>` blocks that hardcode colors outside Tailwind entirely.

**Why it happens:**
"Sweep the components" mentally scopes to `.tsx` files with obvious `className="bg-neutral-800"` strings, because that's 90%+ of what a first pass finds (85 files is already a lot of surface area). The remaining 10% is scattered across config, inline styles, and third-party-pattern components that look pre-solved.

**How to avoid:**
Grep for raw color values across the whole tree, not just component class-name strings: hex codes (`#[0-9a-fA-F]{3,8}`), `rgb(`/`rgba(`/`hsl(` literals, and Tailwind's non-token palette names (`neutral-`, `gray-`, `slate-`, `zinc-`, `stone-`, `black`, `white`) across `.ts`, `.tsx`, and `.css` — not just `.tsx` with `className`. Explicitly check `tailwind.config.ts` itself as a sweep target, not just its consumers. For shadcn/ui primitives, verify every referenced CSS variable (`--popover`, `--card`, etc.) actually resolves to something in the new token contract before assuming the component is theme-safe — several currently don't (Pitfall 6).

**Warning signs:**
`grep -rn "#[0-9a-fA-F]\{3,8\}"` or `grep -rn "neutral-\|gray-\|bg-black\|text-white"` across `app/ components/ tailwind.config.ts` still returns hits after the sweep is marked complete.

**Phase to address:**
Phase A (token contract & sweep) — treat the grep above as the actual completion check, not "no obvious hardcodes left in the components I touched."

### Pitfall 5: The light preset ships with dark-theme shadows, overlays, and glass/blur effects, and looks broken even though every color token resolved correctly

**What goes wrong:**
Every color in a component correctly resolves through a token, the sweep is "complete" by the grep in Pitfall 4, and the light theme still looks wrong: modals and dropdowns use `shadow-lg`/`shadow-xl` tuned for a dark backdrop (barely visible on light surfaces, or visible as a muddy gray halo); `backdrop-blur` + semi-transparent dark overlays (used for menus, image lightboxes, loading states) render as a dark smear over light content instead of a subtle scrim; focus rings and borders calibrated against `neutral-900` backgrounds (the hardcoded `ring: "#333333"` in `tailwind.config.ts`, for one) disappear or clash against a light surface. None of this is a "hardcoded color" in the grep sense — it's *tuned intensity and elevation values* that assumed one lighting direction.

**Why it happens:**
Design tokens solve "which color," not "how much shadow/opacity is legible against this background." Elevation and overlay treatments are almost always designed once, against the original dark UI, and never revisited because they don't contain an obviously wrong hex value — they contain a correct-looking `black/50` or `shadow-2xl` that happens to assume a dark canvas.

**How to avoid:**
Treat shadow/overlay intensity as part of the token contract's job, not outside it — either a `shadow` token that each theme tunes (e.g., dark theme uses light-colored glow shadows, light theme uses conventional dark drop-shadows), or a documented convention (e.g., shadows always use `color-mix`/relative-color syntax against `--store-foreground` rather than a literal `black`, so they auto-invert with theme mode). At minimum, treat every `shadow-`, `backdrop-blur`, `/50`, `/80` overlay class as a sweep target requiring visual verification under the light preset, not just a token-resolution check.

**Warning signs:**
Modals, dropdowns, and the promotional banner render with no visible elevation, a muddy border, or an inverted-looking scrim specifically under the light theme, while every individual color token is provably correct.

**Phase to address:**
Phase B (once a light preset exists to test against) — call this out explicitly as part of "the light theme is the acid test," beyond just missed `text-white`.

### Pitfall 6: Undefined shadcn/ui token classes (`bg-popover`, `text-popover-foreground`) are mistaken for already-tokenized code during the sweep

**What goes wrong:**
`components/ui/dialog.tsx`, `sheet.tsx`, `dropdown-menu.tsx`, and `alert-dialog.tsx` already use semantic-looking class names (`bg-background`, `bg-popover`, `text-popover-foreground`) that read as "this component is already on the token system, skip it." In fact `--popover` is undefined anywhere in this codebase today — the class currently generates no color at all. These are exactly the interactive surfaces (dropdowns, the order confirmation dialog, cart/menu sheets) named as regression-risk in this milestone, and they'll silently render unstyled/transparent under the new token CSS unless someone notices the variable was never real.

**Why it happens:**
`bg-popover`/`bg-card`/`text-muted-foreground` are shadcn/ui's own default naming convention, distinct from and coincidentally similar to this project's own `store.muted-foreground` token. A sweep done by pattern-matching "does this look tokenized" rather than "does this CSS variable actually exist and resolve" will pass these over.

**How to avoid:**
During the sweep, grep `tailwind.config.ts` and the generated theme CSS for every `--color-*`/`--store-*` variable actually defined, then cross-check every `bg-`/`text-`/`border-` class used across `components/ui/*` against that list. Anything referencing an undefined variable (currently: `popover`, likely `card` and others in the shadcn set) needs either a real token added to the contract or an explicit remap to an existing `store.*` token — not a pass because the name looks right.

**Warning signs:**
Dropdown menus, dialogs, or sheets render with a transparent or default-browser background in the new theme system even though "no hardcoded classes" were found by a naive grep.

**Phase to address:**
Phase A (token contract & sweep) — verify token *existence*, not just token-shaped naming, as an explicit sweep step.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|-----------------|------------------|
| Leaving `border`/`ring` as literal hex in `tailwind.config.ts` instead of tokens | Saves touching the Tailwind config during the sweep | Two colors invisible to theme switching forever; light theme borders/focus rings stay dark-theme values | Never — these are two lines, fix them in Phase A |
| Adding a module-level cache in front of `getActiveTheme()` to cut D1 latency | Immediate perceived speedup | Stale theme after admin save; inconsistent behavior across Worker isolates on Cloudflare | Only with an explicit, measured latency problem and a real invalidation strategy (edge cache + purge-on-write), never as a first move |
| Skipping visual verification of shadow/overlay components under the light preset because "colors all resolved" | Faster sweep completion | Light theme ships with dark-tuned elevation that reads as broken chrome, discovered post-launch | Never for the 2-3 shipped presets; acceptable only for a theme nobody will actually select yet |
| Reusing `bg-popover`/shadcn default class names without verifying the variable exists | Component "looks" already tokenized, skip it | Silent transparent/unstyled UI on dropdowns and dialogs | Never |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|-----------------|-------------------|
| D1 (`admin_settings`) read in root layout | Wrapping the read in Suspense/streaming to "improve" performance, reintroducing theme flash | Keep it blocking, above any Suspense boundary, exactly like the existing synchronous `getStoreConfig()` call it replaces |
| OpenNext Cloudflare build (`opennextjs-cloudflare build`) | Assuming `npm run build`/`prebuild` covers the real deploy path | Wire the theme-scan script explicitly into `build:worker` (and `predev`), since `deploy`/`deploy:ci` never call plain `build` |
| Turbopack (`next dev`) vs Webpack (`next build`) | Assuming the generated theme manifest hot-reloads in dev the same way it's validated in build | Treat the generated `lib/themes/manifest.generated.ts` as a real file the script must rewrite on every relevant change; there is no watch mode today — running `next dev` after editing a `themes/*.css` file will not regenerate the manifest without re-running the script or restarting |
| Cloudflare Workers isolate reuse | Storing "the active theme" in a module-scope variable as an implicit cache | Isolates are reused unpredictably; any state that must reflect the current admin setting has to come from D1 (or an explicitly-purged edge cache) on each request, not isolate memory |
| Telemetry taxonomy (`commerce.telemetry.v1`) | Adding the "unknown theme name" event to only one of the two taxonomy parity files | Update both taxonomy files together — this is a locked v1 rule, and CI likely checks parity |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|-----------------|
| Per-request D1 read for theme resolution added on top of the existing per-request `admin_settings` read for the promotional banner | Slightly elevated TTFB across every storefront page, not just checkout | Consider combining both `admin_settings` reads (banner + theme) into a single batched D1 query if/when this is measured as a real cost | Noticeable once traffic or D1 latency variance grows; the milestone explicitly defers this ("revisit only if traces show it") |
| CSS Relative Color Syntax (`rgb(from var(...) r g b / <alpha-value>)`) evaluated on every themed utility | Negligible CPU cost, but depends on browser support | None needed for target browsers (Safari 16.4+, Chrome 119+, Firefox 128+ all support it, well-established by 2026) | Only relevant if a required legacy browser predates 2023-2024 support windows — verify against actual analytics before treating as an issue |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Trusting an unvalidated `store.active_theme` value from D1 as a `data-theme` attribute or a CSS import path | A corrupted/malicious D1 row could reference a theme name that doesn't exist in the generated manifest, breaking rendering or (in a worse design) enabling path-like injection into a file lookup | `getActiveTheme()` must validate the D1 value against the generated manifest's known theme names before using it anywhere, falling back to the env default per the milestone's own resolution order — never interpolate the raw D1 value into a file path or class name without a manifest lookup first |
| Treating the theme-scan prebuild step as purely a DX convenience | An invalid or malicious `themes/*.css` file (e.g., committed by mistake, or during a future contribution workflow) reaches production because the validating script silently no-ops instead of failing the build | The milestone already requires the build to fail hard on an invalid theme file — verify this actually happens in the real deploy path (`build:worker`), not just `npm run build` (see Pitfall 1) |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|-------------|-------------------|
| Theme flash between a default/fallback theme and the real D1-resolved theme | Visible flicker on page load, especially on slower connections or cold Worker starts | Blocking, server-side resolution above any Suspense boundary (Pitfall 3); no client-side theme swap ever |
| Light theme shipping with dark-theme shadow/overlay treatments | Modals and menus look "broken" or low-contrast even though colors are technically correct | Explicit visual QA pass per preset, not just a token-resolution check (Pitfall 5) |
| Admin picks a theme in the Appearance UI and the storefront doesn't reflect it immediately | Admin assumes the save failed or the feature is broken | No caching layer between the admin save and the next storefront request reading D1 fresh (Pitfall 2) |
| `text-black` hardcoded on the promotional banner assuming `primary` is always light | A future preset with a dark primary color makes the banner text unreadable | Use the token contract's `on-primary` token instead of a hardcoded text color wherever text sits directly on a `primary`-colored surface |

## "Looks Done But Isn't" Checklist

- [ ] **Tailwind config itself:** `border`/`ring` (and any other config-level literal color) is tokenized, not just component `className` strings — verify by reading `tailwind.config.ts`, not by grepping `.tsx` files.
- [ ] **shadcn/ui-pattern components:** every `bg-`/`text-`/`border-` class referencing a CSS variable (`popover`, `card`, `muted-foreground`, etc.) actually resolves to a defined token — verify by cross-referencing against the generated theme CSS, not by name-pattern alone.
- [ ] **Shadow/overlay components:** every `shadow-`, `backdrop-blur`, `/50`-`/90` overlay class has been visually checked under the light preset specifically, not just confirmed to compile.
- [ ] **`data-theme` on initial HTML:** "View Source" (not just DevTools computed styles) on a cold request shows the correct `data-theme` attribute already present — confirms no streaming/Suspense boundary is delaying it.
- [ ] **The real deploy build, not `npm run build`:** the theme-scan validation actually fires in `build:worker`/`deploy:ci`, verified by intentionally breaking a theme file and running the real deploy script, not the bare `next build`.
- [ ] **Checkout, cart, and header specifically:** these were named as regression-sensitive; confirm they were included in the sweep grep (not skipped as "too risky to touch this pass") and re-tested end-to-end after retokenizing, not just visually spot-checked.

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|----------------|------------------|
| `prebuild` script never runs on real deploys | LOW | Move the invocation into `build:worker` and `predev` directly; redeploy; confirm with a deliberately broken theme file that the build now fails |
| Module-level cache serving stale theme after admin save | LOW | Remove the cache; if latency was the driver, replace with an edge cache keyed off the setting with explicit purge-on-write from the admin save action |
| Light theme shipped with dark-tuned shadows/overlays | MEDIUM | Audit `shadow-`/`backdrop-blur`/opacity-overlay usages theme-by-theme; introduce a shadow token or relative-color-based shadow convention; re-run screenshot diffs per route |
| Undefined `bg-popover`-style classes discovered post-sweep | LOW–MEDIUM | Add the missing token(s) to the contract and generated CSS, or remap the component to existing `store.*` tokens; re-test the specific dropdown/dialog/sheet components |
| Missed hardcode found in checkout/cart/header after the sweep is marked done | MEDIUM (regression-sensitive surface) | Fix the specific class, re-run the before/after screenshot diff for that route only, and re-run the checkout/cart e2e or manual UAT pass given the owner's regression sensitivity |

## Screenshot-Diff Mitigation Practice

The milestone already commits to "before/after screenshots per route... at each PR." To make that catch real regressions rather than become a rubber stamp:

- **Capture per theme, not just per route.** A screenshot diff taken only under `volt-dark` (the default) will never show a light-theme contrast failure. Once a light preset exists (Phase B), the same route list needs to be diffed under both/all shipped presets, not just the one active during Phase A's sweep.
- **Capture interactive states, not just resting pages.** The riskiest surfaces (checkout, cart, dropdowns, the order confirmation modal) are risky specifically in their open/expanded/hover/focus states — a resting-page screenshot of `/checkout` won't show a broken dropdown or an invisible-on-light-theme modal.
- **Diff against the pre-sweep baseline, not against the previous PR's screenshot.** Sequential PR-to-PR diffing lets a regression introduced in PR 3 and "confirmed" as the new baseline in PR 4 hide permanently. Keep the original pre-Phase-A screenshots as the durable baseline for the sweep's duration.
- **Treat a zero-diff result on checkout/cart with suspicion, not relief.** If the sweep is genuinely retokenizing 6+ files in `components/checkout` and 2 in `components/cart`, a screenshot tool that reports no visual difference likely means the capture didn't include the states that changed (e.g., a hover/focus/expanded state), not that the change was safe.
