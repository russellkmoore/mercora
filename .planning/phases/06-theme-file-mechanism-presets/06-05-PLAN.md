<objective>
Run THEME-04's acid test. Capture every shipped preset across the storefront's route grid, then look
hard at the light one: a token-driven scrim inherits its theme's polarity, and a scrim's whole job is
to be polarity-independent, so the light preset is where a dark-tuned leftover from Phase 5's sweep
would show. Fix what actually reads wrong, case by case, write down every judgement including the
ones that end in "leave it", and close the phase with evidence for each of its four success criteria.

Purpose: THEME-04's second half, and the phase's evidence record.

Output: `06-SCREENSHOTS.md` carrying the per-preset captures, the QA findings table, the registered
changes, and the phase-close roll-up; plus whatever narrow overlay fixes the QA pass actually
justifies.
</objective>

<flagged_assumption>
THEME-04's QA scope was left unresolved by the source artifacts: CONTEXT.md D-04 defers the decision
to "the phase's own QA pass, case by case", the UI-SPEC records the scrim finding as a flagged
finding explicitly not resolved on the planner's behalf, and the edge probe classified THEME-04 as
unclassified.

The planner therefore authors the pass criteria rather than inheriting them, and records that as an
assumption rather than a decision:

**Assumed pass criteria.** Under the light preset, a modal, an alert dialog, a sheet and the category
hero each visually recede the content behind them, and no surface reads as an unintended light haze
where a scrim is expected. The four sites the UI-SPEC already located are the floor, not the ceiling:
the executor may inspect more surfaces and must not inspect fewer.

**Assumed disposition rule.** Where the light scrim still separates the modal from the page
acceptably, record "accepted as-is" with the reason. Where it does not, fix that one site. Prefer a
fix that keeps the value token-driven; if a literal dark value is genuinely required, use the token
scanner's existing sentinel mechanism with a written reason, which is a general facility rather than
an admin-specific one. Do not add a token and do not introduce a shared overlay class — D-03 and
D-04 both forbid those, and either would turn a four-site judgement call into a contract change.

If the executor disagrees with these criteria, it should record the disagreement and its own criteria
in the SUMMARY rather than silently narrowing the pass.
</flagged_assumption>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local D1 -> capture runs | The capture runs write the stored theme setting repeatedly against a local database and must leave it in a known state. |
| screenshot output -> repository | Captured pages may contain seeded catalog, order or account data. |
| overlay fix -> swept storefront | A fix in a shared primitive changes every surface that primitive renders, not just the one that read wrong. |
