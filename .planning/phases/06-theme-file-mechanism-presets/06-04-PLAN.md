it changeable by a human without touching D1 by hand.

link, and source-contract tests.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> settings API | The Appearance page's save is an authenticated cross-origin-capable write to a generic settings endpoint that accepts any key and value. |
| manifest -> admin markup | Theme labels, industry lines and synopses originate in theme file comments and are rendered into the admin page; token hex values are rendered into inline style attributes. |
| admin selection -> storefront render | The saved value becomes the theme every visitor's page is rendered with. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-13 | Elevation of Privilege | the appearance theme write path | high | mitigate | The save calls the existing settings endpoint, whose POST handler already runs the admin permission check and returns 403 on failure. No new route is created and no new authorization code is written, so there is no second guard to get wrong. Task 2's acceptance criteria forbid adding an endpoint. |
| T-06-14 | Tampering | a theme name outside the manifest posted to the settings endpoint | medium | mitigate | The grid only renders manifest entries and re-checks membership before posting. The authoritative control is the read-time membership check in plan 06-02, so even a direct hand-crafted POST cannot change what the storefront renders — it can only store a value that resolves back to the default and emits the unknown-selection event. |
| T-06-15 | Cross-Site Scripting (Tampering) | theme label, industry and synopsis rendered in admin | low | mitigate | The strings render as React text children, which escapes them; the raw-HTML sink is asserted absent by both Task 1's criteria and Task 3's test. Colour values reach only inline style attributes and were validated as 6-digit hex at build time by plan 06-01, so they cannot carry a style-attribute escape. |
| T-06-16 | Repudiation | a theme change with no record of who made it | low | accept | The existing settings endpoint's audit behaviour is unchanged by this plan, and a theme selection is a reversible cosmetic setting with no financial or data-access consequence. Adding a bespoke audit trail for one cosmetic key is out of scope for this milestone; the endpoint's own admin guard already establishes that only an admin could have made the change. |
| T-06-SC | Tampering | npm / pip / cargo installs | low | accept | No package-manager install task exists in this plan; every UI primitive used is already vendored under components/ui. `06-RESEARCH.md` section "Package Legitimacy Audit" records zero packages added this phase, and `06-UI-SPEC.md` section "Registry Safety" records no third-party registry in use. |
</threat_model>
