# Phase 6.1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This phase has no new UI surface.** `ThemePresetGrid` (Phase 6, THEME-03) is manifest-driven — it
already renders however many theme cards the generated manifest contains, so the four new presets
(`clinical`, `retro`, `atelier`, `market`) appear automatically once their `themes/*.css` files
validate. This document is therefore almost entirely **four token-value contracts** (one per
preset) plus the light-preset QA checklist for the three light ones. Sections that describe the
unchanged admin page reproduce 06-UI-SPEC.md's values for checker completeness and are marked
**(unchanged)**; do not re-derive them.

Reuses 06-UI-SPEC.md's structure verbatim per the CONTEXT's explicit instruction: the rename map,
the per-token table format demonstrated by `luxe`/`midnight`, the contrast-check method, the
font-loading pattern, and the light-preset QA finding format.

## Preset Token Contracts (THEME-05) — the core of this phase

All four presets express themselves **only** through the frozen 23-token contract
(`05-TOKEN-MAP.md §1`). Per D-03, the direction doc's extra properties (`shadow`, `border-width`,
`image-aspect`, `accent-2` where not folded into `info`, `font-mono`, `letter-spacing`) are **not**
implemented. No component markup and no decorative CSS (perspective grids, gradient borders, hard
offset shadows, backdrop-blur glass headers, masonry layouts) is added — out of scope for this
milestone's tokens-only architecture.

All oklch → hex conversions below were computed programmatically (Björn Ottosson's OKLab/OKLCH →
linear-sRGB → sRGB formulas), not eyeballed, and cross-checked against `luxe.css`/`midnight.css`'s
already-shipped values to confirm the conversion formula matches exactly (both reproduced byte-for-byte).

### Rename map (reused verbatim from 06-UI-SPEC.md §Preset Token Contracts)

Same disposition rules apply to all four new presets: `surface`→`surface` direct; `surface-raised`→
`surface-elevated` direct; `surface-sunken`→ no main-set slot (repurposed as `border` when the doc
gives no explicit border color, dropped when the doc does or when `border` is independently derived
for a dark theme — see each preset's table for which applies); `ink`→`foreground`; `ink-muted`→
`muted-foreground`; `accent`→`primary`; `accent-ink`→`on-primary` (subject to the same
contrast-correction discipline Phase 6 established for Luxe's `ring` and Midnight's `on-primary`);
`accent-2`→`info` **only where the doc uses it for a status/badge role**, else dropped and `info`
is independently derived (this phase's four presets split both ways — see below); `success`/
`warning` direct; `danger`, `border`, `ring` required by the contract but absent from the doc,
derived per preset; `radius` (single doc value) → four radius tokens, scaled per preset (not a
uniform rule — each preset's scaling is justified in its own table); `font-display` per the Fonts
section; `font-sans` stays Geist for all four, per CONTEXT D-05 overriding the doc's Market
"font-body Nunito" line — Nunito is used for Market's `font-display` only, not `font-sans`.

**Contrast-check method (reused from Phase 6):** for each preset, `primary`/`on-primary`,
`foreground`/`surface`, `ring`/`surface`, and `muted-foreground`/`surface` were computed with the
standard WCAG relative-luminance contrast formula. `on-primary` is treated as **text on a solid
button background** (AA text threshold 4.5:1); `ring` is treated as a **non-text UI component**
(WCAG 3:1 threshold). Every deviation from the doc's literal oklch value is recorded explicitly in
the affected preset's table, following the exact "flagged deviation" phrasing `luxe.css` and
`midnight.css` already use.

### Font Loading (D-05)

Three new `next/font/google` display faces, added to `app/layout.tsx` alongside the existing
Geist/Geist Mono/Cormorant Garamond block — same `preload: false` discipline (a page that never
renders text in a given `font-display` face pays nothing extra; the browser fetches it only when a
`[data-theme]` block that references the variable actually renders text):

```tsx
// app/layout.tsx — add alongside the existing font imports
import { Orbitron, Fraunces, Nunito } from "next/font/google";

const orbitron = Orbitron({
  variable: "--font-orbitron",
  subsets: ["latin"],
  weight: ["600", "700"],
  display: "swap",
  preload: false, // D-02: never preload a non-default display face
});

const fraunces = Fraunces({
  variable: "--font-fraunces",
  subsets: ["latin"],
  weight: ["500"],
  display: "swap",
  preload: false,
});

const nunito = Nunito({
  variable: "--font-nunito",
  subsets: ["latin"],
  weight: ["700"],
  display: "swap",
  preload: false,
});

// add orbitron.variable, fraunces.variable, nunito.variable to the existing
// body className list, alongside geistSans.variable / geistMono.variable /
// cormorantGaramond.variable — each CSS var is then always defined, but the
// browser only fetches the font file when a page actually renders text with
// font-display under the matching [data-theme]
```

No `@import`/`@font-face` may appear inside any `themes/*.css` file (D-02, enforced by the D-06
validator) — all three faces are loaded exactly once, in the root layout, for every theme, exactly
as `luxe`'s Cormorant Garamond already is.

**Before using any of these three imports**, verify Orbitron, Fraunces, and Nunito exist in the
installed `next/font/google`'s font-data manifest and export the weight arrays listed above
(CONTEXT states all three, plus Righteous and Fredoka, are already confirmed present — this is a
final belt-and-suspenders check at implementation time, not a re-litigation of that confirmation).
If any weight is unavailable, fall back to the nearest available static weight and record the
substitution in the theme file's header comment, following the same discipline `luxe.css` and
`midnight.css` already use for their own conversion notes.
