## Summary

Reviewed the four new theme files, the `next/font` wiring in `app/layout.tsx`/`app/globals.css`, the 23 `font-display` heading edits across 22 files, the regenerated theme manifest/barrel, and the `select.tsx` highlighted-row fix.

The theme files themselves are solid: exactly 23 tokens each, all 6-digit hex, single `[data-theme]` selector, no stray `@import`/`@font-face`, and the documented contrast corrections check out against independent WCAG calculation (clinical primary/on-primary 4.61:1, atelier 4.64:1, market 4.63:1 — all match the header comments). `mise exec -- node scripts/build-themes.mjs --check` passes, confirming the generated manifest and barrel are fresh. The `html`/`body` `next/font` variable-class duplication in `app/layout.tsx` is correct and necessary — traced through CSS custom-property inheritance semantics, confirming the claimed bug (T-06.1-13) and its fix. The literal `system-ui` stack removal from `html` in `globals.css` is a genuine, needed fix (it previously outranked Tailwind's own token-driven preflight rule in the same cascade layer, hard-coding every theme to a system font at the document-element level).

One real defect was found: the site-wide `font-display` wiring, applied to headings that also carry `font-semibold`/`font-bold`/`font-extrabold`, exposes a weight gap in the pre-existing (untouched) `cormorantGaramond` font config that this phase did not update, even though it updated the three sibling display faces for exactly this reason. A second defect: the `select.tsx` highlighted-row fix is undone at one of its own call sites already in scope for this review.

## Critical Issues

### CR-01: `font-display` wiring exposes a missing-weight regression on the Luxe theme, unlike the three faces this phase actually tuned

**File:** `app/layout.tsx:98-104` (cormorantGaramond config, unchanged by this phase) interacting with all 23 heading edits, e.g. `app/page.tsx:56`, `app/product/[slug]/ProductDisplay.tsx:185`, `app/blog/[slug]/page.tsx:70`, `components/pages/*.tsx`

**Issue:** This phase adds the `font-display` Tailwind class to ~23 headings site-wide (theme-agnostic JSX — the same className list renders for every active theme). For the three *new* display faces this phase adds, the weight arrays were deliberately widened to cover every `font-*` weight utility used alongside `font-display`:
- `orbitron`: `["600","700","800"]`
- `fraunces`: `["500","600","700","800"]`
- `nunito`: `["600","700","800"]`

These comments (lines 110-113, 127-129, 143-145) explicitly say the arrays were extended "so the storefront's font-extrabold/font-bold/font-semibold headings render at a loaded weight instead of a synthesized one" — because `font-synthesis: none` (in `app/globals.css`) means the browser is forbidden from faking bold when the requested weight isn't loaded.

`cormorantGaramond` (Luxe theme's `--store-font-display`, per `lib/themes/manifest.generated.ts:133`) was **not** touched by this phase and still loads only `weight: ["400", "500"]` (line 101). But Google's Cormorant Garamond family actually supports weights up to 700 (verified via `node_modules/next/dist/compiled/@next/font/dist/google/font-data.json`: `weights: ["300","400","500","600","700","variable"]`). The union of Tailwind weight classes actually paired with `font-display` in this diff is `{600, 700, 800}` (font-semibold / font-bold / font-extrabold), none of which is in cormorantGaramond's loaded set.

Before this phase, headings never explicitly requested the display face (no `font-display` class existed), so Luxe's headings just inherited Geist from `body`. This phase's site-wide wiring newly switches Luxe's headings onto Cormorant Garamond — and with `font-synthesis: none` already in place, every one of those ~23 headings will silently render at weight 500 (the heaviest loaded) instead of the requested 700/800 when the Luxe theme is active, a visible weight-thinning regression across nearly every page.

**Fix:** Widen `cormorantGaramond`'s weight array to match the other three faces' pattern:
```ts
const cormorantGaramond = Cormorant_Garamond({
  variable: "--font-cormorant-garamond",
  subsets: ["latin"],
  weight: ["400", "500", "600", "700"], // extended to cover font-semibold/bold/extrabold headings now paired with font-display
  display: "swap",
  preload: false,
});
```
(Google's Cormorant Garamond tops out at 700, so `font-extrabold` requests will still resolve to 700 rather than a true 800 — that's an acceptable, non-synthesized nearest-match, unlike the current 500 ceiling.)

## Warnings

### WR-01: `select.tsx`'s highlighted-row fix is overridden back to the invisible state at a call site already in this review's scope

**File:** `app/product/[slug]/ProductDisplay.tsx:273`
**Issue:** `components/ui/select.tsx`'s `SelectItem` was just fixed (per its own inline comment, "06.1-04 Task 2 fix") because `focus:bg-surface-elevated` was byte-identical to the popover's own `bg-surface-elevated`, making the highlighted row invisible on every theme. The fix changed the base component's default to `focus:bg-primary/10`.

However, `ProductDisplay.tsx`'s product-variant `SelectItem` passes its own `className="text-foreground hover:bg-surface-elevated focus:bg-surface-elevated"` (line 273). `cn()` (`lib/utils.ts`) uses `twMerge`, which resolves conflicting Tailwind utilities by keeping the *last* one in the merged string — and `className` is passed after the base classes in every component in `select.tsx` (`cn(baseClasses, className)`). So this call site's own `focus:bg-surface-elevated` wins over the base component's new `focus:bg-primary/10`, reintroducing the exact invisible-highlight bug this phase's own commit describes fixing, specifically on the product page's variant selector — a shopper cannot see which variant option is focused/hovered when selecting a product option.

**Fix:** Remove the redundant/conflicting override at the call site (the base component's default already handles this correctly):
```tsx
<SelectItem
  key={variant.id}
  value={variant.id}
  className="text-foreground"
>
```
(The `hover:bg-surface-elevated` on the same line is also dead — it matches the trigger's own base background at line 262, so it's a visual no-op even before considering the conflict; drop it too, or replace with a token-driven hover consistent with the base fix if a distinct hover state is wanted.)

### WR-02: No automated test for the `next/font` variable-class / body-font-family wiring this phase fixes

**File:** `app/layout.tsx`, `app/globals.css`
**Issue:** The comments in both files describe a real, previously-shipped regression (T-06.1-13: storefront silently drops to the browser's default serif) with a fairly subtle root cause (CSS custom-property scope resolution order between `<html>` and `<body>`). There is no test in `tests/` that pins `font-family` resolving correctly on `body`, or that the `next/font` variable classes are present on `<html>`. `tests/unit/scripts/build-themes.test.ts` and `tests/unit/lib/themes/active-theme.test.ts` cover theme *token* validation and active-theme resolution, not this font-wiring interaction. Given this exact defect already shipped once, a regression on this specific wiring (e.g., someone "simplifying" the html className back to just `data-theme` and `lang`) would go undetected until a user or a future review notices theme-specific serif fallback again.
**Fix:** Add a lightweight test — e.g. a snapshot/regex assertion over the rendered `<html>`/`<body>` className output of `RootLayout`, or a jsdom-rendered assertion that all six `next/font` variable class tokens are present on both elements — so a future edit that drops the html-level classes fails CI instead of shipping silently.

### WR-03: Duplicate `.font-sans` utility declaration in `app/globals.css` is dead code (pre-existing, but worth flagging since it sits right next to this phase's new `body` rule)

**File:** `app/globals.css:12-15`
**Issue:** `tailwind.config.ts` maps `fontFamily.sans` to `"var(--store-font-sans)"`, so Tailwind v4 auto-generates its own `.font-sans { font-family: var(--store-font-sans) }` utility in the `utilities` cascade layer. The project's own `.font-sans` rule at lines 12-15 is declared inside `@layer base`, and in Tailwind v4's layer ordering (`theme, base, components, utilities`), `utilities` always wins over `base` regardless of source order or specificity. Confirmed in the built CSS output (`.next/static/css/*.css`): two separate `.font-sans` rules exist, and the `base`-layer one (with `font-display: swap`, itself not a valid property outside `@font-face`) can never take effect. This predates this phase's diff (only the new `body` rule and the `html` literal removal were touched here), but it sits inside the same file/block this phase edited and is worth cleaning up while in the area.
**Fix:** Remove the dead `.font-sans` rule from `@layer base` (Tailwind's own generated utility already does the job), or rename it to something that isn't shadowed if a distinct base-layer default is actually wanted.

## Info

### IN-01: `select.tsx` focus-highlight tint is visually subtle on some themes

**File:** `components/ui/select.tsx:119`
**Issue:** Computed `primary` @ 10% opacity over each theme's `surface-elevated` gives an RGB-distance of roughly 20-36 (out of a 441 max) across the seven shipped themes — visible but modest, smallest on `luxe` (~20). Not incorrect, and text contrast stays high (>11:1) in every case, but a designer reviewing pixel-level polish may want a slightly stronger tint (e.g., `/15` or `/20`) for consistency with `CategoryDisplay`'s referenced `hover:bg-primary/20` precedent, which this fix's own comment cites as the model but uses half the opacity.
**Fix:** Consider bumping to `focus:bg-primary/15` or `/20` if a design pass confirms the current value reads as too subtle on light-warm themes (atelier, luxe).
