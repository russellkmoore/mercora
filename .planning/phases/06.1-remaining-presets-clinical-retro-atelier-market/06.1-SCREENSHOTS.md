## Plan 06.1-03: Type wiring — both frozen tokens reach rendered elements (D-10)

**Decision this section proves:** CONTEXT D-10 wires `--store-font-sans` onto the body element
and `--store-font-display` onto the storefront's 23 page-title/CMS-section headings, site-wide,
and accepts the resulting visible change under `volt-dark` as the intentional snap `S-TYPE-01`
rather than a revert trigger. **This supersedes the zero-visual-change condition CONTEXT
§Specifics and 06.1-UI-SPEC.md's `## UI Considerations` table carried** — that condition was
correct when written (no component applied `font-display` yet) and is now explicitly overridden
by D-10, not silently ignored.

### Static facts (confirmed before any edit)

- Zero elements in `app/` or `components/` apply the `font-sans` Tailwind utility today
  (`grep -rlE 'className="[^"]*\bfont-sans\b' app components | wc -l` → `0`).
- `app/globals.css`'s base layer defines a `.font-sans` rule (`font-family:
  var(--store-font-sans)`) that nothing currently consumes, and pins the document element
  (`html`) to a literal `system-ui, -apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif`
  stack.
- `app/layout.tsx` puts the `next/font` variable classes (`--font-geist-sans`,
  `--font-geist-mono`, `--font-cormorant-garamond`, `--font-orbitron`, `--font-fraunces`,
  `--font-nunito`) on the `<body>` element's `className`, not on `<html>`.
- `themes/volt-dark.css`'s two font tokens are byte-identical:
  `--store-font-sans` = `--store-font-display` =
  `var(--font-geist-sans), system-ui, -apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif`.

Together these are why neither frozen type token currently reaches a rendered element (the sans
utility is defined but unused; the document element's literal stack always wins for text that
inherits no other font-family), and why the sans token has to land on `<body>` rather than one
level up on `<html>` — a `<html>`-level declaration would reference `--font-geist-sans`, which is
undefined there, making the whole declaration invalid at computed-value time (T-06.1-13).

### The layout.tsx deviation this task's proof depended on

Getting the "after" column above required one fix beyond the plan's own `<action>` text, made
during Task 2 and folded into its commit as a Rule 1 auto-fix (not repeated as a separate task
here): `app/layout.tsx`'s six `next/font` variable classes were applied only to `<body>`, but
`[data-theme="volt-dark"]` (which declares `--store-font-sans`/`--store-font-display`) matches
`<html>`. A custom property whose value nests a `var()` reference is resolved — and, if that
nested reference is undefined, invalidated — at the element that **declares** the property, not
the element that later **consumes** it in an actual CSS property. Confirmed with a standalone
minimal HTML repro outside this app before applying the fix: declaring the CSS variable at an
ancestor where the nested reference is out of scope leaves it permanently invalid for every
descendant, even ones where the nested reference *is* in scope. The fix applies the same six
`next/font` variable classes to `<html>` as well as `<body>`; this only widens where those CSS
custom properties are in scope; it changes no font-loading behavior and no visible layout. Every
reading in this record was taken **after** that fix, and the "before" column stays a true
before — it was captured in Task 1, before Task 2's edits existed at all.
