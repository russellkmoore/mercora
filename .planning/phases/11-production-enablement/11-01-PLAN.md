<objective>
Prove the whole gift-card key-ring pipeline locally, end to end, before any production
action: generate a development ring with the exact non-echoing shell pipeline that plan
11-04 will run against Cloudflare, prove git can never see it, and prove both frozen
parsers accept that shape and reject an under-length key.

Purpose: the production `wrangler secret put` steps are costly to undo once a card is
issued under a key. A malformed ring fails closed on every five-minute cron tick. This
plan makes the shape mistake cheap and local instead of expensive and live.
Output: an extended parser-invariant test and an untracked `.dev.vars` that makes
`npm run dev` able to exercise the gift-card paths.
</objective>

  <behavior>
    Five new cases, all fixtures constructed in memory. No fixture is read from `.dev.vars`, from
    `.env.local`, or from any environment variable.

    - Accepts an HMAC key shaped like `openssl rand -base64 32` output: 44 ASCII characters, which
      is 44 UTF-8 bytes, comfortably over the 32-byte floor. Build it with `btoa("0".repeat(32))`.
    - Rejects an HMAC key one byte under the floor: a 31-character ASCII string. Expect
      `toThrow("Gift-card runtime configuration is unavailable")`.
    - Accepts a delivery key of `"base64:" + btoa("0".repeat(32))` — canonical standard base64 of
      exactly 32 bytes, one trailing `=`, which is the shape `openssl rand -base64 32` emits.
    - Rejects a delivery key of `"base64:" + btoa("0".repeat(31))` — still valid canonical base64
      and still 44 characters, but it decodes to 31 bytes. This is the boundary case one byte under
      AES-256, distinct from the 16-byte case already covered at lines 69-75.
    - Rejects a delivery key with no prefix: `btoa("0".repeat(32))` on its own. The regex requires
      the prefix, so a bare value fails even though it decodes to the right length.
  </behavior>
