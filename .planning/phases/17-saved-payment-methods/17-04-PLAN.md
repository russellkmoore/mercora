<interface_contract>
Plan 17-05's client component consumes exactly these shapes and nothing else:

- `GET /api/account/payment-methods` → 200 `{ paymentMethods: Array<{ id: string; brand: string; last4: string; expMonth: number; expYear: number }> }`, 401 `{ error: string }`, 503 `{ error: string }`
- `DELETE /api/account/payment-methods/[id]` → 200 `{ success: true }`, 401 / 403 / 404 / 503 `{ error: string }`

Export the row type from the collection route as
`export interface SavedPaymentMethod { id: string; brand: string; last4: string; expMonth: number; expYear: number }`
so plan 17-05 imports it rather than restating it.
</interface_contract>

  <read_first>

    - `.planning/phases/17-saved-payment-methods/17-RESEARCH.md` Pattern 5 and Pitfall 4 — `paymentMethods.detach(id)` takes only an id, so nothing scopes it to a customer unless the route checks first
  </read_first>
  <behavior>
    - No Clerk session: 401, and neither Stripe nor the binding lookup is called.
    - Signed in, cross-origin: 403, and neither Stripe nor the binding lookup is called.
    - Signed in, same origin, id missing or longer than 80 characters: 404, no Stripe call.
    - Signed in, same origin, caller has no binding: 404, and `detach` is never called.
    - Signed in, same origin, retrieved payment method's customer is a different Stripe customer: 404, and `detach` is never called.
    - Signed in, same origin, retrieved payment method's customer matches the caller's binding: `detach` called once with that id, response 200 `{ success: true }`.
    - Stripe `retrieve` or `detach` throws: 503 with a fixed message, and the caught error's own text is not in the body.
  </behavior>
  <action>
    Create `app/api/account/payment-methods/[id]/route.ts` exporting `DELETE(request: NextRequest, context: { params: Promise<{ id: string }> })`,
    copying the addresses item route's structure line for line: a module-level `denial()` returning
    404 `{ error: "Payment method not found" }`, then `await auth()` → 401, then
    `hasSameOrigin(request)` → 403 `{ error: "Origin validation failed" }`, then
    `const { id } = await context.params` and `if (!id || id.length > 80) return denial()`.

    Then the ownership check, which is the whole point of this route (D-09): resolve the caller's
    own `findStripeCustomerId(userId)`; if there is none, return `denial()`. Call
    `getStripeClient().paymentMethods.retrieve(id)` and compare the returned object's `customer`
    field to the caller's Stripe customer id — string-compare it, and treat a customer field that
    is an expanded object by reading its `id`. On any mismatch, return `denial()` — a 404, not a
    403, so the response cannot be used to confirm that some other shopper's payment method
    exists. This matches the non-leaking convention the gift-card balance route already uses.
    Only after the comparison passes, call `getStripeClient().paymentMethods.detach(id)` and
    return `{ success: true }`.

    Catch Stripe failures separately from the ownership decision and return 503
    `{ error: "The payment method could not be removed right now" }` with no caught-error text in
    the body.

    Create `tests/unit/app/api/account-payment-methods.test.ts` covering every behavior line above
    plus Task 1's GET cases, using the `vi.hoisted` mock-factory structure from
    `tests/unit/app/api/payment-intent-authority.test.ts` lines 1-40: mock
    `@clerk/nextjs/server`'s `auth`, mock `@/lib/payments/customer-binding`'s
    `findStripeCustomerId`, and mock `@/lib/stripe`'s `getStripeClient` to return a fake with

    case. Assert on status codes and parsed bodies, and assert `detach` was not called in every
    denial case — the negative assertion is the one that actually proves the mitigation.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `/api/account/payment-methods` | Any signed-in shopper can reach these routes and supply an arbitrary path id |
| route → Stripe API | `paymentMethods.detach` is unscoped: it will detach any id the server hands it |
| route → browser | The list response is the only place Stripe payment-method data reaches the page |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-17-17 | Elevation of Privilege | DELETE `[id]` route | critical | mitigate | `paymentMethods.retrieve(id)` then a string comparison of its customer against the caller's own `findStripeCustomerId(userId)` result, before any `detach` call; proven by a test asserting `detach` was never called on mismatch (D-09) |
| T-17-18 | Information Disclosure | DELETE denial responses | high | mitigate | Every denial path returns the same 404 body, so the response cannot distinguish "does not exist" from "belongs to someone else" (D-09) |
| T-17-19 | Spoofing | caller identity | critical | mitigate | The Stripe customer id is derived server-side from the Clerk `userId`; no request field can influence which customer is read or written |
| T-17-20 | Tampering | CSRF on DELETE | high | mitigate | `hasSameOrigin(request)` → 403, identical to the addresses item route precedent (D-08) |
| T-17-21 | Information Disclosure | list projection | high | mitigate | The response maps to exactly five fields; the raw Stripe object, its customer id, fingerprint and billing details never leave the server (D-08) |
| T-17-22 | Information Disclosure | Stripe error text in responses | medium | mitigate | Both routes return fixed 503 strings and never echo a caught Stripe error's message |
| T-17-23 | Denial of Service | unbounded path id | low | mitigate | `id.length > 80` is rejected before any Stripe call, copying the addresses route's bound |
| T-17-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is installed by this plan; all three Stripe packages are already installed and audited OK in 17-RESEARCH.md's Package Legitimacy Audit |
</threat_model>
