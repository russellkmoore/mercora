<objective>
Wire the honor guard into the two places that matter: the cron that measures and alarms, and the
capability resolution that decides whether stored value can still be spent.

This is the plan that makes D-04 real. Turning honoring off while a shopper still holds a balance
does not strand them: the runtime keeps honoring, the cron pages every five minutes, and the
configuration error for selling-without-honoring is untouched.

Purpose: the runtime half of GCF-02.
Output: a cron-side guard routine with an alarm, a request-side honor override that fails safe,
and tests for both — including the case where an invalid configuration must still throw.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Deploy-time flag → whether stored value can be spent | The highest-value decision in the phase |
| `admin_settings` row → capability resolution | A single row now influences money movement |
| Cron tick → D1 write | The only write path for that row |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-26 | Elevation of Privilege | the honor override in `resolveRuntimeCommerceCapabilities` | critical | mitigate | The override is bound to `!sell`, so it can only ever widen honoring in a state where selling is already off. A dedicated test asserts the sell-on/honor-off case still throws and that the guard is never consulted there |
| T-13-27 | Tampering | the guard record influencing tender | high | mitigate | The record is written only by `runGiftCardHonorGuard`, called only from the scheduled handler; it is admin-settings data reachable only through admin-authenticated paths. A forged record could only ever say "balances exist", which widens honoring, not spending rights — the record cannot authorise a redemption, only permit the capability to exist |
| T-13-28 | Denial of Service | stranded balances under honor=off | critical | mitigate | Missing, stale and unreadable all resolve to honoring, and the cron pages every tick while the condition holds |
| T-13-29 | Denial of Service | a guard failure stopping the recovery cron | high | mitigate | The guard call is wrapped in a `.catch` that degrades to the configured flags; the three drains still run and `waitUntil` still receives exactly one promise |
| T-13-30 | Information Disclosure | the telemetry emit | low | mitigate | Only closed-taxonomy dimensions and a reservation count are emitted — no card identity, no code material, no money total |
</threat_model>
