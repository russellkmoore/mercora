## Summary

This phase closes a batch of v2 tech-debt items: a shared request-scoped appearance
read, a public `/api/theme` route feeding `app/global-error.tsx`, theme-aware email
builders with a request-time-staged theme carried through the cron recovery drain,
an expand-only migration for that staged theme payload, CI token-scan wiring, a
consolidated product-image resolver, a required `productGallery` prop, a
duplicate-token validator check, and a guarded dev-only order fixture.

I traced every priority item called out in the phase context by hand:

- `GET /api/theme` returns exactly `{name, tokens}` from the manifest, sets
  `Cache-Control: no-store`, and is `force-dynamic` — verified against the route
  source and its test suite, which asserts the exact key set and headers.
- `parseThemeResponse` / `emailThemeForStagedPayload` both validate a candidate
  theme name against `THEME_MANIFEST` via `Array.some()`/`.find()` before calling
  `getThemeTokens()` — never an object-key index off an untrusted string, so
  neither is exploitable as a prototype-pollution vector.
- `readAppearanceSettings()` holds no top-level mutable binding and no
  `globalThis`/`unstable_cache` reference; `React.cache()` is request-scoped only
  (confirmed by the module's own docstring reasoning and independently enforced by
  `layout-switch-contract.test.ts`'s repo-wide grep guard, which treats this file
  as the one named, deliberate exception).
- `getActiveTheme()` and `getLayoutSettings()` both degrade a D1 read failure to
  `{}` (via `readAppearanceSettings()`'s internal try/catch) and both still return
  a manifest-valid value on absent/empty/invalid input — the branch-collapse in
  `active-theme.ts` is behavior-preserving (traced the collapsed conditional
  against the pre-refactor diff; same two outcomes, same one telemetry call).
- `app/global-error.tsx`'s mount effect swallows every fetch/parse failure with no
  state change and no thrown error; first paint never gates on the fetch.
- `emailThemeForStagedPayload` is a pure, synchronous function — `drainOrderEffects`
  never calls `getActiveTheme()`/`resolveEmailTheme()` on the recovery path, so the
  documented "cannot run in the scheduled handler" invariant holds structurally,
  not just by convention.
- The migration is a single nullable `ALTER TABLE ADD COLUMN`, matches the Drizzle
  schema change exactly, and `d1-harness.test.ts` pins it into the migration
  sequence.
- `data/d1/seed-dev.sql`'s new order fixture is `ON CONFLICT(id) DO NOTHING`,
  referenced by exactly one script (`scripts/db-local-ensure.mjs`), which invokes
  `wrangler d1 execute --local` — confirmed by reading that script directly, not
  just trusting the guard test's own assertions.
- Six email HTML generators/preparers (`generateOrderConfirmationHTML`,
  `generateOrderStatusUpdateHTML`, `prepareShippingEmail`, plus the inline builders
  in `refund-email.ts`, `lifecycle-email.ts`, `review-notifications.ts`) all take
  `tokens` as a parameter rather than resolving it themselves, and all HTML uses
  `escapeHtmlText()` on every interpolated user/store value I checked — escaping
  is unchanged from the pre-phase pattern in every builder.

No blocker-level defects found. One warning and three informational notes below —
none is a correctness or security gap; they are minor duplication/robustness notes
worth a look.

## Warnings

### WR-01: `failOrderEffect`'s backoff exponent can go negative for a mis-supplied `attempt_count`

**File:** `lib/services/order-effects.ts:373-377`
**Issue:** `Math.min(effect.attempt_count - 1, 10)` is used as the exponent for
`2 ** n`. In the normal path `attempt_count` is always ≥1 by the time a claimed
effect reaches `failOrderEffect` (the `CLAIM_SQL` UPDATE always increments it
before the row is claimable), so this is not reachable through the public API
today. But `failOrderEffect` is exported and takes a bare `ClaimedOrderEffect`
object — nothing in its own signature enforces `attempt_count >= 1` — so a future
caller (or a hand-constructed effect object in a test/tool) that passes
`attempt_count: 0` silently produces a fractional exponent (`2 ** -1 = 0.5`)
instead of failing loudly. This is defense-in-depth rather than an active bug.
**Fix:**
```ts
const exponent = Math.max(0, Math.min(effect.attempt_count - 1, 10));
const delayMs = Math.min(6 * 60 * 60 * 1000, 5 * 60 * 1000 * 2 ** exponent);
```

## Info

### IN-01: `resolveEmailTheme()` and `emailThemeForStagedPayload()` share an unenforced convention

**File:** `lib/email/theme.ts:34-36, 57-85`
**Issue:** Both functions independently call `getThemeTokens()` (no arg) as their
fallback and both encode the same "unknown theme name" telemetry contract
(`theme.unknown_selection` / `{ outcome: "invalid" }`) as `lib/themes/active-theme.ts`'s
`getActiveTheme()`. The three call sites currently agree, and the duplication is
small and well-commented (each one exists for a different trust boundary), but
nothing statically ties the three telemetry-event-name/field-shape triples
together — a future edit to one call site's event name would silently create a
telemetry inconsistency rather than a compile or test failure (no test currently
asserts all three use the identical event name/shape as a single source of truth).
**Fix:** Optional — extract a single `recordUnknownThemeSelection()` helper in
`lib/themes/manifest.generated.ts`'s consuming layer (or a small shared module) that
all three call, so the event name/shape can only be declared once.

### IN-02: `FooterTokens`'s structural subset type has no compile-time link to `ThemeTokens`

**File:** `lib/email/footer.ts:10`
**Issue:** `type FooterTokens = { mutedOnInverse: string }` is a deliberately minimal,
independently-declared type (per the file's own comment, to avoid importing
`lib/themes/tokens.ts`). This is safe today because every caller passes a full
`ThemeTokens` object, which is a structural superset. But there is no assertion
(e.g. `ThemeTokens extends FooterTokens ? true : never`) enforcing that
`ThemeTokens` will always carry a `mutedOnInverse` field of type `string` — if a
future theme-contract change ever renamed or restructured that field, the failure
would surface as a TypeScript error at each of the seven call sites rather than a
single, obvious location naming the actual contract.
**Fix:** Optional — add a one-line type-level assertion near the `FooterTokens`
declaration:
```ts
type _AssertFooterTokensSubset = ThemeTokens extends FooterTokens ? true : never;
```
(guarded behind a type-only import so it never reaches the bundle).

### IN-03: `admin/settings` route's new catch-and-log still swallows a genuine seed-insert failure into a 200 response

**File:** `app/api/admin/settings/route.ts:62-74`
**Issue:** This phase's change (adding `console.error` to the previously-empty
catch) correctly makes a real insert failure observable in logs instead of
silently, but the route still returns `200` with whatever rows currently exist —
including the case where the insert failed for a reason other than the benign
PK-conflict race the catch was written for (e.g. a genuine D1 write outage). The
route's own comment now acknowledges "anything reaching this arm is more likely a
genuine insert failure worth knowing about," but the response shape doesn't change
to reflect that — an operator only finds out via log-scraping, not via the API
response. This is a pre-existing behavior this phase's diff only made more
observable, not new; noting it because the added comment now explicitly documents
the accepted risk.
**Fix:** Out of scope for this phase (no action required) — flagging only so it
isn't mistaken for something the phase was meant to close.
