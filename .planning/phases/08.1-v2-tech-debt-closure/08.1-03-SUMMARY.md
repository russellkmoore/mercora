# Phase 08.1 Plan 03: CI scan step, loud parity baselines, logged seed fallback Summary

**The hardcoded-colour scan is now a named CI step (docs corrected to match), all three pre-extraction parity suites read their committed baseline through one loud-on-missing helper instead of self-writing it, and a settings seed-insert failure is logged with a stable prefix instead of vanishing into an empty catch block.**

## Accomplishments

- `.github/workflows/ci.yml` runs `npm run scan:tokens` as a step named "Scan for raw token usage", immediately after "Check theme manifest freshness" — the scan is automated, not a local convention.
- `docs/theming.md` §"The two gates and the screenshot harness" now states both gates run in CI; the two known-limits rows this plan closes (scan not wired into CI, parity tests self-writing baselines) are deleted from §"Known limits and backlog".
- `tests/unit/helpers/parity-snapshot.ts` exports `readParitySnapshot(relativePath, actual?)`: an existing file (including an empty one) is read unchanged; a missing file with no `UPDATE_SNAPSHOTS=1` opt-in throws naming the path and the flag and creates nothing; the opt-in with content supplied creates the parent directory and writes; the opt-in with no content still throws rather than recording an empty baseline.
- All three parity suites (`category-grid3-parity`, `home-hero-variants`, `product-gallery-variants`) now read their committed baseline through the helper; the category suite's own presence-check/write block and its `existsSync`/`mkdirSync`/`writeFileSync` imports are gone. No file under any `__snapshots__` directory was touched.
- `app/api/admin/settings/route.ts`'s seed-insert catch arm now binds its error and logs it once via `console.error('Seed insert failed (may be a benign concurrent race):', err)` — the exact fix the Phase 8 review (IN-02) prescribed. The scoped-defaults filter, re-select, response shape, and status codes are all unchanged.
- `tests/unit/app/api/admin-settings-empty-category.test.ts` no longer mocks the unused `isSuperAdminActor` (IN-01; this file only exercises `GET`) and gained a case proving a rejecting insert is logged exactly once and the handler still returns its normal successful response.

- The two retired `docs/theming.md` known-limits rows were deleted outright (not marked "done" in place) since that table's stated purpose is tracking open items only.
