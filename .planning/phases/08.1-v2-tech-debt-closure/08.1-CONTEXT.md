<decisions>
## Implementation Decisions

### Active theme everywhere (Russell's instruction)
- **D-01:** Transactional emails follow the admin-selected theme. The six builders (`lib/utils/email.ts`, `lib/fulfillment/shipping-email.ts`, `lib/payments/refund-email.ts`, `lib/subscriptions/lifecycle-email.ts`, `lib/utils/review-notifications.ts`, `lib/email/footer.ts`) stop calling `getThemeTokens()` with no argument. The active theme is resolved once at send time in the server context that already has D1 (webhook handlers, admin routes, cron) via `getActiveTheme()` and its tokens are passed into the builders (`tokens: ThemeTokens` parameter, or a small `resolveEmailTheme()` helper that returns `getThemeTokens(await getActiveTheme())`). Builders stay pure and synchronous; only the call sites become theme-aware. Existing escaping is untouched. Tests stub the active theme and assert a non-default token value appears in the HTML.
- **D-02:** `app/global-error.tsx` follows the admin-selected theme. It is a client component rendered without the root layout, so it cannot read D1: add a public, unauthenticated `GET /api/theme` route (`app/api/theme/route.ts`) that returns `{ name, tokens }` for the active theme from the manifest (no secrets; cache-control no-store). `global-error.tsx` renders with the manifest default first (no flash of unstyled), then `fetch('/api/theme')` on mount and applies the returned tokens. If the fetch fails, it stays on the default. Route gets a unit test; global-error gets a render test for both states.

### Gates and reads
- **D-03:** `npm run scan:tokens` is added to `.github/workflows/ci.yml` as its own step next to `build:themes:check`; `docs/theming.md` §gates and §known limits are updated to say the scan runs in CI (the "not in CI" sentence goes).
- **D-04:** `getActiveTheme()` and `getLayoutSettings()` share one request-scoped read of the `appearance` category: a `readAppearanceSettings()` helper wrapped in `React.cache` (request-scoped in RSC; not an isolate/module cache). Behaviour and existing tests of both resolvers are unchanged; the grep guards that forbid `unstable_cache`/`globalThis` stay and are extended to allow exactly this `React.cache` use with a comment explaining why it is request-scoped.

### Hygiene
- **D-05:** One image-URL resolver: `components/layout/product/gallery-media-url.ts` is retired in favour of `lib/utils/product-image.ts` (`resolveProductImageSrc`) for both gallery variants, with a render test proving the `left` gallery's output for the existing fixtures is byte-identical before/after (the pre-extraction parity snapshot is the oracle).
- **D-06:** Parity tests (`category-grid3-parity`, hero and gallery pre-extraction tests) fail loudly when the baseline snapshot file is missing instead of writing it; regenerating a baseline is an explicit `UPDATE_SNAPSHOTS=1` opt-in.
- **D-07:** The settings seed fallback `catch {}` in `app/api/admin/settings/route.ts` logs via the existing telemetry/`console.error` convention (check `lib/observability/telemetry.ts` for a suitable event; otherwise `console.error` with a stable prefix), never swallows silently. The unused `isSuperAdminActor` mock in `tests/unit/app/api/admin-settings-empty-category.test.ts` is removed.
- **D-08:** Review Info items closed: Phase 7 IN-01 (`productGallery` prop required, default removed since the only caller supplies it); Phase 6 info items (validator flags duplicate token declarations; `kebabToCamel` imported in the test rather than reimplemented; two near-identical branches in `active-theme.ts` collapsed) — each its own small commit with tests where behaviour changes.

### Order-status evidence
