Create the enumerations module first, exactly as the interfaces block above specifies. Three const
arrays, three derived union types, one defaults object. Nothing else belongs in this file — no
component imports, no server-only imports — because the admin client island in plan 07-04 imports it

**Flagged planner decision, recorded here per the assumption delta: promote the enum name to primary
identity.** Each switch's identity is its enum member name, and today's rendering is demoted to
whichever member happens to be listed in the defaults object. No page, component or test may
special-case the default beyond reading it from that object. The invariant this creates — for every
enum member the lookup map has a component, and the resolver given that stored value resolves to it
— is asserted in Task 3 for the category switch and repo-wide in plan 07-05.

Then create the resolver module. Import the appearance category constant from the theme resolver
rather than restating the literal, export the three setting keys as a named object, and write one
small internal helper that takes a stored value, that switch's enum array and that switch's default,
and returns a member of the enum. The helper must decide membership by testing the stored string
against the enum **array**, never by indexing an object with it — a stored value naming an object
prototype member would otherwise resolve through the prototype chain instead of falling back, which
is the tampering threat in this plan's register.

The helper's branches copy the theme resolver's shape exactly: an absent or explicitly null value
returns the default silently, an empty or whitespace-only string returns the default silently, a
string that trims to a member returns that member, a string that trims to anything else emits one
telemetry signal and returns the default, and a present non-string emits one telemetry signal and
returns the default. The signal carries only the allowed outcome enum field describing the value as
invalid — never any part of the stored value, which the sanitiser would drop anyway and which is the
disclosure this plan's register closes.

The exported resolver performs exactly one category-scoped settings read, inside a try/catch that
returns the three defaults on failure, and then runs the helper three times against that one record.

**Flagged planner decision on the double read (RESEARCH Pitfall 1 asks the plan to pick one
explicitly):** accept two reads per request. The root layout's theme resolution already reads this
category, and the shared settings helper is not request-memoised, so a page calling this resolver
issues a second small category-scoped query. That is the accepted per-request cost the project
already carries for theme resolution, and it keeps this module fully independent of the theme
resolver's internals and its frozen test suite. Do not add a shared memoised wrapper, do not
memoise anything at module scope, do not assign to a global, and do not reach for a framework-level
memoisation wrapper — a Workers isolate is reused across requests, so anything held outside the
request would serve a stale layout after an admin save.

Register the layout unknown-selection event in the telemetry events map at warning severity with
sample rate 1, in the object-literal shape the existing entries use, immediately below the theme
entry. Do not add it to the tail Worker's critical-event array: that array is structurally
critical-only, enforced by both the existing parity loop and the tail parser's own severity guard.
Add one sibling case to the existing tail parity test asserting the new event's registered severity
and sample rate and asserting the critical list does not contain it. Do not modify the existing
theme case.

Write the two test files. The enumerations test covers the last behavior row — distinctness, no
duplicates, defaults membership — and is where plan 07-05's repo-wide exhaustiveness test will later
find its per-enum precedent. The resolver test covers every other behavior row, mocking the settings
helper and the telemetry module the way the theme resolver's test does, and asserting both the
returned values and the exact telemetry call count so the "absent row emits nothing" rule is a real
assertion rather than an absence nobody checked.

Register the event before writing any resolver code that calls it: the record function's event
parameter is a literal-string union derived from the events map's keys, so the resolver will not
typecheck against an unregistered name. Phase 6 hit exactly this ordering and recorded it.
