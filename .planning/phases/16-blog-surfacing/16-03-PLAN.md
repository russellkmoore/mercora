<objective>
Put the latest articles on the home page, in a block an admin controls: heading, how many, on or off, and
which of two fixed positions relative to the featured-products grid.

Purpose: BLOG-02 and BLOG-03. The home page is where a shopper lands, and today it says nothing about the
blog at all.

Output: a new server component `components/home/BlogHighlights.tsx`, additive wiring in `app/page.tsx`, and
two test files — one for the component's rendering, one for the page's placement and gating behaviour
(D-15).

This plan carries the phase's only new visual surface and runs without a UI design contract on purpose: per
D-13, every visual decision here is already settled by existing token-correct components — the blog index's
card, the featured-products grid's responsive classes, and the home page's own section spacing. There is no
new design to make, only markup to copy accurately. If you find yourself inventing a look, stop and copy the
analog instead.
</objective>

Every colour, border and surface class must come from the 23-token contract. This is a storefront component
and `scan:tokens` walks it; a literal palette class fails the gate.

Render the heading and every excerpt as JSX text children. No raw-markup prop appears anywhere in this file —
the excerpt is derived from author-supplied article markup and is only safe because it arrives as stripped

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| D1 `blog_posts.html` -> home-page excerpt text | Author-supplied article markup reaches a public page that previously never touched it |
| D1 `admin_settings` -> home-page block heading and count | Admin free text and an integer drive a public render and a query limit |
| Server component tree -> client bundle | Whatever `app/page.tsx` passes into a component boundary is serialized for every visitor |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-16-21 | Tampering | Excerpt derived from `blog_posts.html` rendered on the home page | high | mitigate | `resolveBlogExcerpt` (16-01, T-16-02) returns tag-free plain text, and `BlogHighlights.tsx` renders it as a JSX text child. No raw-markup prop exists in the file, asserted by an occurrence count of 0. The "no body text past the cap appears in the markup" case pins that the full body never reaches the page |
| T-16-22 | Tampering | Admin-authored `blog_home_block_heading` rendered on the home page | low | mitigate | Rendered as a JSX text child, which React escapes; write access is admin-gated (16-04's T-16-31). Over-long or whitespace-only headings already fell back to the default in 16-01's resolver |
| T-16-23 | Denial of Service | The posts query's limit | medium | mitigate | The limit is the resolver's already-clamped 1..6 value, never the raw stored number; `getPublishedBlogPosts` independently caps at its own maximum. A tampered `content.blog_home_block_count` row cannot widen the query |
| T-16-24 | Information Disclosure | Article bodies entering the home page's payload | medium | mitigate | Bodies are fetched server-side for excerpt derivation only. `BlogHighlights` is a server component and renders only the derived excerpt, so no body string is serialized into the client payload. The build gate catches any accidental client boundary on this path |
| T-16-25 | Information Disclosure | Draft or future-dated articles appearing on the home page | high | mitigate | Only `getPublishedBlogPosts` is used, whose filter is locked to published status and a publish time at or before now; no new query path is introduced (D-03) |

No package-manager install occurs in this plan.
</threat_model>
