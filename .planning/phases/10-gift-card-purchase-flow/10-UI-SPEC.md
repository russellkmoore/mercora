# Phase 10 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase touches five existing storefront surfaces plus one new product-page block, all rendered
through the frozen 23-token contract (`docs/theming.md`) — no hex, no admin-style hardcoded palette
anywhere in this phase. Two of the five surfaces sit on the **inverse** token set per
`docs/theming.md` footnote 1 (the cart drawer, via `CartItemCard.tsx`); the rest sit on the **main**
token set. The one new shared component (`GiftCardRecipientBlock`, D-10) is used in both places and
must switch token sets via a `tone` prop rather than hardcoding either — see
`## Component Anatomy § Shared recipient block`.

`components.json` already exists — the shadcn init gate is satisfied; no new init needed this phase.
No new shadcn component is installed: `Input`, `Label`, `Textarea`, `Checkbox`, `Select`, `Button`,
and `Dialog` are already present and already fully token-driven (verified by reading each primitive
directly — see `## Component Inventory`).

## Typography

Typography is **overwhelmingly reused**, not newly introduced — every new field, heading, and error
string in this phase reuses the exact size/weight/line-height classes already established by
`ShippingForm.tsx`, `ProductDisplay.tsx`, and `CartItemCard.tsx`. Declared new elements (exactly 2
weights: regular 400, semibold 600):

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Section heading ("Recipient details", "Billing details") | 18px (`text-lg`) | semibold 600 (`font-semibold`, matches `ShippingForm`'s existing "Shipping Address" heading class, reused verbatim, and `ProductDisplay`'s tab labels) | 1.2 |
| Field value / body text | 14–16px (`text-sm`/`text-base`, matches `Input`'s own `text-base md:text-sm`) | regular 400 | 1.5 |
| Field error / helper text | 12px (`text-xs`, matches existing `ShippingForm` error text size) | regular 400 | 1.5 |
| Character counter | 12px (`text-xs`) | regular 400 | 1.5 |
| Recipient block "To:" line (cart/checkout/confirmation/account) | 12–14px (`text-xs`/`text-sm`, matches the one-line "For …" text it replaces) | regular 400 (checkout/account main-token surfaces) or existing `text-muted-on-inverse` weight (cart drawer, unchanged) | 1.5 |

## Component Anatomy

All values below are token classes only; no hex, no `rgb()`. Every new element reuses an existing
container/spacing convention already established in the files it lives in.

### `GiftCardRecipientForm` (new, `components/product/GiftCardRecipientForm.tsx`)

Rendered by `ProductDisplay.tsx` **in place of** the existing `{available ? <button>Add to Cart</button> : <p>Coming soon</p>}` block only, when `product.type === 'gift_card'` — the amount `Select`, price/on-sale display, and "In stock"/"Coming soon" text above it are unchanged (D-05). Since Phase 9 CAT-04 guarantees gift-card variants are never out of stock, `available` is passed through defensively but is expected to always be `true`.

Field order (top to bottom), inside a `space-y-4` column matching `ShippingForm`'s rhythm:

1. **Send to myself** — `Checkbox` + `Label`, `flex items-center gap-2`, rendered only when `useUser().isSignedIn` (D-08). Checking it sets recipient email from `user.primaryEmailAddress.emailAddress` and recipient name from `user.fullName` (blank if Clerk has none); both stay editable afterward; unchecking does not clear already-typed values.
2. **Recipient email** — `Input type="email" inputMode="email" required`, `Label` above.
3. **Recipient name** — `Input`, `Label` above, character counter below-right (`flex justify-between` row: `Label` left, counter right, matching a common shadcn form pattern not yet used elsewhere in this codebase — first instance).
4. **Gift message** — `Textarea rows={3} maxLength={500}` (soft backstop; the per-field validator, not `maxLength`, is authoritative), `Label` above, counter below.
5. **Delivery date** — native `<input type="date" min={todayISO} max={oneYearFromTodayISO}>` styled with the same border/radius/focus classes `Input` uses (no shadcn date-picker exists in inventory; a native control is the only option without adding a dependency), `Label` above, helper text below (Copywriting Contract).
6. **Add to Cart** — `Button` (`default` variant), `w-full sm:w-auto` matching the physical button it replaces, `disabled` until all four per-field validators pass (email required+valid; name/message/date valid-if-present).

Validation timing: each field validates on blur first (no red state on initial render); once a field
has been blurred once, it re-validates live on every change. Error text renders as
`<p role="alert" id="{field}-error" className="mt-1 text-xs text-danger">` directly under its field,
with the input carrying `aria-invalid` and `aria-describedby` pointing at that id — this is exactly
the pattern `Input`/`Textarea`'s own `aria-invalid:border-danger` CSS already expects, so no new
error-state styling is written, only the wiring.

### Shared recipient block — `GiftCardRecipientBlock` (new, `components/gift-cards/GiftCardRecipientBlock.tsx`)

```
interface GiftCardRecipientBlockProps {
  customization: GiftCardCustomization;
  tone?: 'default' | 'inverse'; // default: main tokens (checkout/confirmation/account); inverse: cart drawer
}
```

Renders exactly the three D-10 lines (see Copywriting Contract), each a `<p>` with `mt-1` between
them:

| Tone | "To:" line class | "Deliver:"/message line class |
|---|---|---|
| `default` (checkout `OrderItemCard`, confirmation modal, account order page) | `text-foreground` | `text-muted-foreground` |
| `inverse` (cart drawer `CartItemCard`) | `text-on-inverse` | `text-muted-on-inverse` |

Both share `text-xs` sizing, matching the one-line "For …" text each replaces. The message line
carries `title={message}` (untruncated) so hover/assistive tooling can surface the full text without
a new interactive affordance — this resolves the truncated-message affordance with zero new
component surface. Truncation is a plain 80-character substring cut with a trailing `…`, not a CSS
`line-clamp` (matches D-10's literal "truncated to about 80 characters with an ellipsis" wording,
which is a character count, not a line count).

`CartItemCard.tsx` replaces its existing inline "For …" `<p>` with `<GiftCardRecipientBlock
customization={item.giftCardCustomization} tone="inverse" />`; `OrderItemCard.tsx` replaces its
identical inline block with the same component at `tone="default"` (or the default, since `default`
is the prop default).

### Billing details step + digital-only progress bar (D-01, D-02)

A cart is **digital-only** when `items.every((item) => item.giftCardCustomization !== undefined)` —
the same signal CONTEXT.md's Specific Ideas section names as the only thing template code may key
off (never a slug or id). This is computed once in `CheckoutClient.tsx`.

**`ProgressBar.tsx`** gains an optional `steps?: string[]` prop, defaulting to the existing four
labels. `CheckoutClient.tsx` passes `['Billing details', 'Payment', 'Order Submitted']` for a
digital-only cart, unchanged four-label array otherwise (D-02) — same component, no new file, no
per-preset branching. The numeric `step` index passed alongside shifts from the existing
`shipping→0 / payment→2 / confirmation→3` mapping to `shipping→0 / payment→1 / confirmation→2` for
the 3-label case.

**The Billing details step is `ShippingForm.tsx` itself, reused byte-identical — not a new or
slimmed-down form.** Russell chose this over a slim four-field Contact step specifically because
`normalizeAddress` (`app/api/payment-intent/route.ts`) and Stripe Tax
(`checkout-pricing.ts` lines ~685–699) both require non-empty `line1`, `city`, `region`,
`postal_code`, and `country` — values a slim form could not honestly collect (D-01, superseding the
earlier Contact-step design). `ShippingForm` gains two optional props, `heading?: string` (default
`"Shipping Address"`) and `helperText?: string` (default none, rendered as a `text-sm
text-muted-foreground mb-4` line under the heading when present) — every field, the field order, every
placeholder, the country `Select`'s three options, and the **Use Address** submit button stay exactly
as they already render for a physical cart; only these two strings differ. `CheckoutClient.tsx`
passes `heading="Billing details"` and `helperText="Nothing ships — we need this for your receipt and
tax."` for a digital-only cart (both headings — the outer wrapper's `<h3>` in `CheckoutClient` and
`ShippingForm`'s own internal `<h2>`, an existing pre-Phase-10 duplication this phase does not fix —
render the same "Billing details" string for consistency). For a signed-in shopper, Full Name and
Email prefill from Clerk and remain editable (D-03); the rest of the address fields stay blank exactly
as they do today for a guest. Submitting calls `createPaymentIntent` directly with
`shippingMethodId: 'digital'` — the intermediate `/api/shipping-options` fetch and the
`ShippingOptions` panel are skipped entirely for a digital-only cart (D-01); they are not rendered
because `shippingOptions` state is simply never populated on this path, not because of new
conditional JSX.

After submit, the existing recap-card pattern renders unchanged in shape (`bg-surface p-4 rounded-lg
border-l-4 border-success`, heading + "Edit" link), retitled **Billing details** and showing the same
full address recap the physical flow already renders (recipient, line1, line2, city/region/postal) —
not a shortened summary.

**Resolved (previously flagged as an open gap, now closed by design):** digital-only checkout posts a
complete address via the existing `ShippingForm` fields; no placeholder values are sent. Every field
`normalizeAddress` and Stripe Tax require is a real, shopper-entered value collected by the same form
the physical flow already validates and submits today.

### Order confirmation modal items list (D-11)

`OrderConfirmationModal.tsx` gains an `items?: StableCartItem[]` prop, rendered as a new section
(heading **Order items**) between the existing order-ID block and the footer buttons, using the same
compact-row shape `OrderItemCard` already establishes (`flex items-center gap-3 ... bg-surface`, name
+ qty × price on one line) plus `<GiftCardRecipientBlock tone="default" />` under any line carrying
`giftCardCustomization`. Since the pending-checkout payload (`lib/checkout/order-payload.ts`) carries
only `{ orderId, paymentIntentId, savedAt }` and `POST /api/orders` returns only `{ id }` — no new API
per D-11 — `CheckoutClient.tsx` must snapshot the cart store's `items` into local component state
**immediately before** each of its two `clearCart()` calls (the `noCash` branch and
`handlePaymentSuccess`), then pass that snapshot as the modal's `items` prop. If the snapshot is ever
empty when the modal renders (not reachable in the normal synchronous flow), the items section is
omitted entirely rather than showing an empty-state message — see `## UI Considerations`.

### Account order detail gift-card block (D-12)

`app/account/orders/[id]/page.tsx`'s existing `<li>` item row (currently a single `flex justify-between`
line) becomes `flex flex-col gap-1 py-3` when the item carries a persisted `gift_card` value: the
existing name/quantity/price row stays the first child, followed by a
`<div className="text-sm text-muted-foreground space-y-0.5">` block rendering the same "To: /
Deliver: / message" lines as `GiftCardRecipientBlock` at `tone="default"` (full message,
`whitespace-pre-line`, no 80-character truncation — this is a detail page, not a compact card).
Physical items are visually unchanged.
