<objective>
Close DEBT-06: a digital-only order (a gift-card-only purchase) currently gets **no
confirmation email and no merchant notification at all** — `buildFulfillmentOrderData`
returns `null` for it, and `sendOrderConfirmation` reports `{ success: true, skipped: true }`.
Fix the read-side guard, display the billing address the shopper already typed, and label
it honestly on both the email and the account order-detail page.

Purpose: this is the one item in Phase 18 with a real end-to-end user path — persisted
order row → `order-confirmation` service → email template → account page. It is the phase's
tracer: it proves the `addressLabel` threading works across every layer this phase touches
before any other plan builds on the same idea.

Output: a gift-card buyer receives a receipt, the merchant is told about the sale, and both
surfaces name the address correctly.
</objective>

<interface_contract>
Added to `OrderData` in `lib/utils/email.ts` and therefore to `MerchantOrderData` and
`FulfillmentOrderData` (both derived by `Omit`):

```ts
addressLabel?: 'shipping' | 'billing';
```

Present only when `shippingAddress` is present. `'shipping'` for every order that has a real
`order.shipping_address`. `'billing'` only when `order.shipping_address` is absent and the
order is legitimately addressless, so `order.billing_address` was used in its place.

`OrderStatusUpdateData` is **not** changed — see Task 2.
</interface_contract>

say to *replace* the `extensions.subscription_shipping_required === false` check with

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-18-01 | Information disclosure | `app/account/orders/[id]/page.tsx` | high | mitigate | The billing address is a new PII surface on this page. It is read only from the order already loaded by `getOrderByCustomerAndId(userId, id)`, which scopes the row to the signed-in customer. Task 3 forbids adding any other read path; the existing ownership assertions in the source-contract test are kept as the guard. |
| T-18-02 | Information disclosure | `lib/services/order-confirmation.ts` | high | mitigate | The confirmation email is addressed from `order.extensions.email`, the same order row the address came from, so a billing address can only ever reach the buyer of that order. The address source is chosen inside `buildFulfillmentOrderData` from that one order object; no cross-order lookup is introduced. |
| T-18-03 | Tampering | `lib/utils/email.ts` | medium | mitigate | Address values are shopper-supplied. All five fields keep flowing through the existing `escapeHtmlText` calls — the diff touches heading text only, never a value interpolation, so no new unescaped injection point is created. |
| T-18-04 | Denial of service | `lib/services/order-confirmation.ts` | medium | mitigate | Widening the guard makes the service send for order shapes it previously skipped. `resolveOrderLineImages` is already bounded at `MAX_IMAGE_PRODUCT_IDS`; sends remain one-per-order behind the existing idempotency key, so no new unbounded work is added. |
| T-18-05 | Repudiation | `lib/services/order-confirmation.ts` | medium | accept | The subscription-renewal regression risk is covered by test, not telemetry: the existing renewal case in `order-confirmation.test.ts` fails loudly if the guard is written as a replacement. No runtime signal is added for a case a unit test catches at commit time. |
| T-18-06 | Spoofing | `app/api/payment-intent/route.ts` | low | accept | The billing address is whatever the shopper typed at checkout; it is display data on a receipt, never an authorisation input. Confirmed read-only in this plan — the route is not modified. |
