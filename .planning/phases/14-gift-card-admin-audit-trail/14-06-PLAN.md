<objective>
Ship the three read/create routes an admin's browser talks to: card detail, merged
timeline, and a list that can be searched and paged, plus create-a-card.

These are thin. Every one of them is auth, then the honor gate, then a call into the
modules waves 2 and 3 built, then a typed JSON body. No route in this plan contains a SQL
statement, a code, or a money decision.

Purpose: GCA-01, GCA-02 and GCA-07 become reachable over HTTP.
Output: two new route files, one extended route file, two test files, one contract list
extended.
</objective>

  <behavior>
    - An unauthenticated request returns 401 with code `unauthorized`.
    - A request for an unknown id returns 404 with code `gift_card_not_found`.
    - With both feature flags off and the honor guard clear, the route returns 404 with code `gift_cards_unavailable`.
    - With both flags off but the honor guard active, the route serves normally.
    - A successful response carries the card's id, masked code, code suffix, issued amount, available balance, status, created and disabled timestamps, issuing order id, recipient email, purchaser label, delivery status and attempt count, and its reservations each with a classification.
    - A successful response carries a `capabilities.codeRevealEnabled` boolean read from the stored setting, so the UI's reveal control and the reveal route's own gate come from one source.
    - A successful response contains no code hash, ciphertext, nonce, key version, claim token, email idempotency key or ledger business key.
    - A database failure returns 503 with code `gift_cards_read_failed`.
  </behavior>
  <action>
Create `app/api/admin/gift-cards/[id]/route.ts` exporting a single `GET(request, { params })` with the Next.js async-`params` signature.

Sequence, per D-13 and D-16, in this order:
1. `checkAdminPermissions(request)`; on failure return `jsonError('unauthorized', ..., 401)`.
2. Resolve the environment through `getCloudflareContext({ async: true })` and read the flags with `giftCardAdminFlags`. Throw and fall through to the 503 catch when the `DB` binding is absent, matching the existing list route.
3. Ask the honor gate exactly as `app/api/admin/gift-cards/route.ts` does: when `giftCardSurfacesHidden(flags)` and `await resolveHonorEffective(environment.DB, flags, nowSeconds)` is false, return `jsonError('gift_cards_unavailable', ..., 404)`. Call `resolveHonorEffective` directly in this file. It is the single owner of that decision (D-16) and the Phase 13 ownership contract names its callers by path, so the call belongs here rather than behind a helper.
4. Read the card: `findAccountById`, then a single-row read through the extended presentation projection for the display fields, then `findReservations` mapped through `classifyGiftCardReservation`. An absent account is `jsonError('gift_card_not_found', ..., 404)`.
5. Read `getSettings('gift_cards')` and derive `capabilities.codeRevealEnabled` as a strict boolean comparison against `true` for `gift_cards.code_reveal_enabled`, so the UI's reveal control in plan 14-08 and the reveal route's own gate in plan 14-07 read the same stored setting rather than two. A missing key is off. This route only reads the setting; nothing in this phase writes `admin_settings` outside the existing generic settings route (D-16).
6. Return `NextResponse.json({ card, reservations, capabilities })` built field by field from the presentation and the classified reservations. Do not spread an account row or a delivery row into the body — both carry code material, and a spread is exactly how it escapes.
7. Wrap steps 2-6 in the same try/catch shape the list route uses, returning `jsonError('gift_cards_read_failed', ..., 503)`.

Create `tests/unit/app/api/admin-gift-card-detail-routes.test.ts` covering every behavior bullet, reusing the mock scaffolding from `gift-card-presentation-routes.test.ts`. Assert the last bullet by serialising the response body to JSON and checking it against the forbidden name list exported from `lib/gift-cards/events.ts`, so the test reads from the same single list the source contract does.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous internet -> every route in this plan | `checkAdminPermissions` is the first statement in each handler |
| admin browser -> `POST /api/admin/gift-cards` | untrusted JSON creating real stored value |
| D1 row -> JSON response | the last place a full row could leak into a response body |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-31 | Elevation of Privilege | non-admin access to the three new routes | high | mitigate | `checkAdminPermissions` first in every handler; a unit case per route asserts 401 for an unauthenticated caller |
| T-14-32 | Spoofing | cross-origin POST to admin-create | high | mitigate | `checkAdminPermissions` already refuses a cookie-authenticated POST from a foreign origin; the route does not bypass it or accept a bearer token path for creation beyond the existing service-token branch |
| T-14-33 | Information Disclosure | code material in a detail or timeline response | high | mitigate | Bodies are built field by field, never spread from a row; a unit case serialises a success body and checks it against the shared forbidden-name list; the source contract from plan 14-04 greps this directory |
| T-14-34 | Denial of Service | oversized JSON body on create | medium | mitigate | `readBoundedJsonBody` caps at 4096 bytes and returns 413 |
| T-14-35 | Tampering | duplicate admin-create minting two cards | medium | mitigate | The client-supplied `requestId` becomes the deterministic card id inside `issueAdminGiftCard`, so a double-submit converges (D-19); a unit case asserts one card for two identical posts |
| T-14-36 | Elevation of Privilege | a bookmarked detail URL outliving the surface | medium | mitigate | Every route asks `resolveHonorEffective`, so the detail route 404s in exactly the states the list route does; the ownership contract's asker list now names them |
| T-14-37 | Repudiation | a card created with no recorded reason | medium | mitigate | `reason` is required and validated before the write, and the `admin_created` event carrying it is written in the same handler (D-07) |
</threat_model>
