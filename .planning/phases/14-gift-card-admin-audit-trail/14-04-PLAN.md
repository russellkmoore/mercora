<objective>
Build the read and audit layer: the event writer, the four-source timeline merge, and the
extended admin list projection with search.

thin wrappers over these three modules. It is also where the forbidden-column rule becomes
a test rather than a habit.

Purpose: one definition of "what happened to this card" and one definition of "what an
admin may see about a card", both enforced by tests rather than review.
Output: two new modules, one extended projection, one new source contract, unit and
integration coverage.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| D1 row -> admin JSON response | the projection and timeline are the last code that sees a full database row before it becomes a response body |
| admin input -> `gift_card_events.details` | free-form detail payloads are written by route handlers and read back onto a screen |
| admin input -> `q` search parameter | untrusted text reaching a SQL WHERE clause |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-19 | Information Disclosure | `PRESENTATION_SELECT`, `buildGiftCardTimeline` | high | mitigate | Details objects are built field by field from an allow-list, never spread from a row; `admin-gift-card-forbidden-columns.test.ts` greps the projection, timeline, events and route files for every forbidden column name |
| T-14-20 | Information Disclosure | `gift_card_events.details` written by a route | high | mitigate | `assertGiftCardEventDetails` throws on any forbidden key before the insert, so a careless route cannot persist code material into the audit log |
| T-14-21 | Tampering | SQL injection through `q` | high | mitigate | The search WHERE fragment uses bound parameters only; no user text is interpolated into SQL |
| T-14-22 | Information Disclosure | purchaser identity in the list | medium | mitigate | The projection returns a resolved display label parsed from the customer `person` JSON, never the raw customer id (D-22) |
| T-14-23 | Repudiation | unattributed timeline entries | medium | mitigate | Every entry carries `actorType`/`actorId`; admin ids resolve to a display name through `admin_users`, and ledger entries produced by an order are attributed to that order rather than left blank (D-04) |
| T-14-24 | Denial of Service | unbounded timeline or list read | medium | mitigate | `listGiftCardEvents` and `buildGiftCardTimeline` clamp their limit; the list projection keeps its existing limit/offset bounds |
</threat_model>
