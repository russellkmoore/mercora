<objective>
Build the screens: a real gift-card list and a card detail page with a timeline and an
action bar.

Russell's words on the current screen were "I can't see the number, I can't invalidate it
and create a new one, I can't see the recipient — this admin panel is next to useless."
The list has to answer which card is this, who has it, and what is left on it, at a glance.
The detail page has to answer what happened to it and let an admin act.

The admin dashboard keeps its own fixed palette and is deliberately excluded from the
storefront token contract (D-17); `npm run scan:tokens` never descends into an `admin`
directory. Do not convert these files to tokens. Per D-18 there is no UI-SPEC for this
phase — the orders admin surfaces are the pattern.

Purpose: GCA-01, GCA-02, GCA-03 and GCA-08 become things a person can do.
Output: one new page, four new components, one rewritten component, one page test.
</objective>

Per D-17 and D-22, use `AlertDialog` for the consequential confirms and `Dialog` for the ones that take input:

- Disable: `AlertDialog` with a required reason field, wording that says redemption stops and the ledger is preserved and there is no undo. Shown only for an active card.
- Reissue: `AlertDialog` with an optional alternative recipient address, wording that names the remaining balance being moved to a new card and that this can happen once. Shown only for a disabled card.
- Resend: `Dialog` with an optional alternative address, wording that says the same code is emailed again. Shown only when the delivery status is `sent` or `needs_review`.
- Re-queue: `AlertDialog`, shown only when the delivery status is `needs_review`.
- Release hold: `AlertDialog` per reservation, offered only on reservations the API classified open; a committed-unsettled reservation renders as awaiting settlement with no control.
- Reveal: rendered only when the detail response's `capabilities.codeRevealEnabled` is true, so the control's presence and the reveal route's own gate read the same stored setting. Its `AlertDialog` states in plain words that revealing writes a permanent audit entry naming the admin who asked, and that the code is bearer material. On confirm, post `{ confirm: true }` and display the returned code in the dialog with a copy button; never write it into component state that outlives the dialog, never log it, and clear it when the dialog closes.

Every outcome is a `sonner` toast: the success message names what happened, and the failure message uses the API's own error text so a 409 explains itself. Disable each button while its request is in flight.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server render -> anonymous request | `app/admin/layout.tsx`'s Clerk session gate stands in front of every page here; the detail page adds the surface-existence gate |
| API response -> browser DOM | the only place a bearer code is ever rendered is the reveal dialog |
| admin click -> money-moving mutation | a confirm dialog is the last step before a disable or reissue |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-52 | Information Disclosure | anonymous read of the detail page's server render | high | mitigate | `app/admin/layout.tsx`'s server-side Clerk admin session gate (added in Phase 13 as T-13-42) already covers every page beneath it; this page adds no data fetch of its own to the server render |
| T-14-53 | Elevation of Privilege | a bookmarked detail URL outliving the surface | high | mitigate | The page calls `resolveHonorEffective` and `notFound()`s in exactly the states the list page and the list API do; the Phase 13 ownership contract now names its path |
| T-14-54 | Information Disclosure | a revealed code persisting in the page | high | mitigate | The code lives only in the dialog's own state, is cleared on close, is never logged, and the response that carried it is marked no-store by the route |
| T-14-55 | Information Disclosure | masked code rendered from plaintext | medium | mitigate | The browser only ever receives `codeSuffix`; `maskGiftCardCodeSuffix` builds the display string from those four characters, and a null suffix renders an em dash |
| T-14-56 | Tampering | double-submit creating two cards or two reissues | medium | mitigate | The create dialog mints one `requestId` per submission and reuses it on retry; every action button disables while its request is in flight; the server-side guards are the real backstop |
| T-14-57 | Repudiation | an action taken with no visible record | medium | mitigate | Each success refreshes the timeline, so the admin sees the audit entry their action created before they leave the page |
</threat_model>
