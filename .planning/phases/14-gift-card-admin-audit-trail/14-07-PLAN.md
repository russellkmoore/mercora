<objective>
Ship the seven mutation routes: disable, notes, requeue, release-hold, resend, reissue and
reveal.

repository or service call, one audit event, a typed response — over machinery waves 2 and
3 already built and tested. The two that are not routine are reissue, which moves money
and must happen once, and reveal, which is the only path in the product that returns a
bearer code to a screen.

Purpose: GCA-03 through GCA-06 and GCA-08 become reachable over HTTP.
Output: seven route files, two unit test files, one D1 integration file.
</objective>

Order: auth, actor, bounded body, honor gate, then generate the new card's material the way `issueAdminGiftCard` does — a code, its digest, its suffix, and a ciphertext AAD-bound to the new card id and its delivery id, where the new card id comes from `giftCardReissueId(oldId)` so a retry converges. Hand all of it to `repository.reissue`, which owns the ordering: status and reservation checks, then the drain-out adjustment under `giftCardReissueAdjustmentBusinessKey(oldId)`, then `issueAccount`. Map `GiftCardUnavailableError` to 404 and `GiftCardConflictError` to 409 `gift_card_reissue_blocked`, passing through the message so the response names why. The new card is delivered by the existing cron drain exactly like a purchase; do not add a send here.

Create `reveal/route.ts` per D-12 and GCA-08. Order matters and each step must precede the next:
1. `checkAdminPermissions`; failure is 401.
2. `readBoundedJsonBody`; require `confirm === true` or return 400 `invalid_body`.
3. Read `getSettings('gift_cards')` and require `gift_cards.code_reveal_enabled` to be strictly `true`; otherwise 403 `code_reveal_disabled`. A missing key is off.
4. `await isSuperAdminActor(auth)` or return 403 `forbidden`. Do not substitute `checkAdminPermissions` alone — `isSuperAdminActor` is what refuses a service token and the development bypass, and that refusal is the whole point of the gate.
5. Honor gate, then load the delivery row; 409 `code_unavailable` when any of the three ciphertext columns is absent.
6. Write the `code_revealed` event, with details naming nothing but the fact of the reveal — no code, no ciphertext, no key version. If this write throws, return 503 and do not decrypt.
7. Only then `parseGiftCardDeliveryKeyRing(environment)` and `decryptGiftCardDeliveryCode` with the AAD taken from the row's own gift-card and delivery ids. Do not write a new AES-GCM call site; these two exported helpers zeroize key material in their own `finally` blocks.
8. Return the code in a `NextResponse.json` body with `Cache-Control: no-store` set on the response headers. Never log it, never attach it to telemetry, never put it in an error.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous internet -> seven mutation routes | `checkAdminPermissions` is the first statement in each |
| authenticated admin -> super-admin-only reveal | a second, stricter gate inside an already-authenticated request |
| service token / dev bypass -> reveal | header-only identities that must not be able to read a bearer code |
| admin-typed address -> outbound email | fraud recovery that doubles as a possible exfiltration path |
